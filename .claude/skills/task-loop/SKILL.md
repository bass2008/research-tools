# Петля исполнения LLM-задач

Ты — **диспетчер**: узнаёшь, что появились джобы, и раздаёшь их суб-агентам. Задачи не выполняешь
и данные их не смотришь — данные забирает сам агент. Через твой контекст проходят только `job_id`
и `type`.

## 1. Preflight (один раз, перед стартом петли)

Проверь и, если что-то не так, **скажи пользователю и не начинай**:

- **MCP-сервер `taskworker` подключён** — виден инструмент `status`; вызови его. Инструментов нет →
  проверить регистрацию MCP (`claude mcp list`) и что пакет `task-worker-mcp` установлен.
- **Сервер приложения поднят** — это покажет тот же `status`. Адрес берётся из `APP_URL` в `.env`.
- **Режим сессии подходит для `analyze`** — нужна Opus с 1M-контекстом и высоким effort: агенты
  `analyze` наследуют режим сессии, модель им намеренно не задаётся. Если сессия не такая —
  предупреди (`claude --model opus` + `/effort xhigh`) и спроси, продолжать ли: `classify` и
  `score` отработают нормально, пострадает только качество `analyze`.

## 2. Инструкция петли

Прочитай **`task-worker-mcp/prompts/orchestrator.md`** — это полная и единственная инструкция:
петля, команда ожидания, маппинг «тип джоба → модель», шаблон задания суб-агенту, правила ошибок.

Дальше действуй строго по ней. Если что-то в ней противоречит этому файлу — права она.

## 3. Во время работы

- Петля бесконечная: пустой список джобов — нормальный простой, снова становись в ожидание.
- Не спрашивай пользователя после каждой пачки и не завершай сессию сам.
- **Сам данные джоба не запрашивай** (`get_job` — дело агента): иначе твой контекст забьётся
  выдачами и списками узлов.
- Упавший джоб не останавливает петлю: агент вернул ошибку — работаешь дальше, без ретраев.
- Отчитывайся коротко: сколько джобов взял, каких типов, чем закончились.
