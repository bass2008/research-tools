# infra/terraform — раскладка, доставка, стоимость

Путь «terraform apply → работающий сайт» и флаги скриптов — в `../README.md`. Здесь то, что за
этим стоит: почему раскладка такая, как доставляется артефакт, сколько это стоит и что из
написанного проверено запуском.

```
infra/terraform/
  server/                VM, сеть, IP, A-записи, cloud-init: node + FastAPI + Postgres + nginx
  site/                  бакет ассетов + deploy.sh + check.sh
  modules/static-site/   бакет, публичное чтение, при желании CNAME, сертификат и CDN
```

## 1. Node-раскладка: что изменилось против статики в бакете

Решение владельца (`docs/api-contract.md`, «Раскладка деплоя — решено») и его следствия для
инфраструктуры:

| было | стало | почему |
|---|---|---|
| `arcana-sense.ru` → CNAME на бакет | **A-запись на VM** | CNAME и A на одном имени не сосуществуют; страницы печатает node |
| TLS: сертификат Certificate Manager на бакете | **certbot на nginx** | сертификат CM прикрепляется к бакету, CDN и балансировщику, но не к nginx |
| весь `out/` в бакет | **`_next/static` и `public` в бакет**, страницы на диске VM | бакет кода не выполняет: `Set-Cookie` по телу запроса он сформировать не может |
| `trailingSlash: true` обязателен | не нужен | node отдаёт и `/path`, и `/path/` (проверено: `/encyclopedia/arcanum/14/` → 308 на канонический адрес) |
| одна служба (FastAPI) | **две службы** + nginx как единая точка входа | `/` и `/api/` уходят на node, BFF сам ходит в FastAPI на `127.0.0.1:8010` |

Порт API — `8010`, а не 8000: так записано в контракте и так же по умолчанию в `web`
(`API_INTERNAL_URL`) и в `api/run.sh`. Значение отдаёт `terraform output api_internal_url`.

Бакет остался, но стал хранилищем ассетов без домена: доступ по path-style
`https://storage.yandexcloud.net/<bucket>/…` под общим сертификатом Object Storage
(`terraform output asset_base_url`). Пока `assetPrefix` в `next.config` не задан, браузер берёт
чанки с сайта, а бакет — холодный резерв и origin для CDN, если он однажды понадобится.

## 2. Как доставляется артефакт

**`infra/deploy.sh` + `rsync` по ssh, вне графа Terraform.** Terraform владеет машиной, сетью,
DNS, бакетом и ключом; артефакт сборки кладёт скрипт. Причина та же, что и раньше, только цифры
другие: артефакт — это 5 858 файлов HTML и 5 856 `.rsc` на 1,2 ГБ, менять их через state нельзя.

| вариант | цена одного релиза | что не так |
|---|---|---|
| `yandex_storage_object` / `aws_s3_object` + `fileset` | apply, `filemd5` по 12 тысячам файлов в каждом `plan` | страницы вообще не должны лежать в бакете: их печатает node |
| `null_resource` + `local-exec` | apply | императивный шаг внутри декларативного графа: дрейфа не видно, лог спрятан в вывод apply |
| образ VM с артефактом внутри (packer) | пересоздание машины | 1,2 ГБ в образе на каждую опечатку в тексте; база живёт на той же машине |
| **`rsync --link-dest` + `systemctl restart`** | секунды, только изменённые страницы | Terraform не знает про содержимое — это и есть цель |

`--link-dest` на предыдущий релиз обязателен: без него каждый релиз добавляет 1,2 ГБ, с ним
неизменные страницы становятся жёсткими ссылками и по сети едут только изменённые.

Заливка ассетов в бакет осталась на `rclone` (`site/deploy.sh`): `_next/static` — `copy` без
удаления (чанк с хешем в имени нужен вкладкам, открытым до релиза), `public` — `sync` с
исключением `_next/**`, чтобы один проход не съел другой. Сравнение по `--checksum`, а не по
времени: `next build` перезаписывает mtime у всех файлов.

## 3. Почему сборка не на машине

Замер на этом репозитории (`/usr/bin/time -v`, 32 ядра, локальный `next build` с
`output: standalone`):

| величина | значение |
|---|---|
| страниц сгенерировано | 5 862 |
| время | 20 с при 189 с процессорного времени (параллельно) |
| пик RSS одного процесса | 628 МБ |

На 2 vCPU с гарантией 5 % те же 189 с процессорного времени растягиваются в минуты, а 628 МБ
рядом с Postgres на 2 ГБ — это OOM-killer. Поэтому машина получает готовый артефакт, а `npm`,
`node_modules` для сборки и тулчейн на неё не ставятся вообще.

## 4. Размер виртуалки и стоимость

### Что на самом деле весит артефакт

Контракт называет 95 МБ. Замер собранного `web` на 2026-08-13 даёт другое число:

| часть standalone | размер |
|---|---|
| `node_modules` (только то, что протрассировал Next) | 61 МБ |
| `content/` (JSON энциклопедии и матриц) | 13 МБ |
| `.next/server` без страниц `/matrix/[slug]` | 24 МБ |
| **итого без предрендеренных матриц** | **96 МБ** ← совпадает с контрактными 95 МБ |
| `.next/server/app/matrix` — 5 544 страницы по ~124 КБ HTML + ~67 КБ `.rsc` | **1 063 МБ** |
| **всего** | **1 159 МБ** (205 МБ в виде `tar.gz`) |

Плюс не входящие в standalone `_next/static` — 2 МБ и `public` — 0,4 МБ, их копирует деплой.

То есть 95 МБ — это машина **без** дерева 5 544 матриц. С ним артефакт в двенадцать раз больше,
и это меняет две вещи: диск и тип диска. На RAM это не влияет — страницы читаются с диска, а не
держатся в памяти процесса.

### Замеры потребления

| процесс | RSS | как замерено |
|---|---|---|
| node, standalone, после 500 запросов страниц | **244 МБ** | локальный прогон `node server.js` с `--max-old-space-size=384` |
| uvicorn + FastAPI (sqlite) | **84 МБ** | работающий процесс `api` на 8010 |
| Postgres | ~350 МБ | не замерено: локально Postgres нет. Оценка по `shared_buffers` 245 МБ + бэкенды |
| ОС, nginx, journald | ~250 МБ | оценка |
| **сумма служб** | **~930 МБ** | |

На 2 ГБ остаётся около 1 ГБ под страничный кэш — этого хватает на лендинг, энциклопедию (18 МБ)
и горячие матрицы, но не на всё дерево в 1,06 ГБ. Отсюда вывод про диск.

### Диск: SSD, а не HDD

Дерево матриц читают краулеры — это последовательный обход 5 544 холодных URL, то есть худший
случай для медленного диска. Производительность сетевого диска в Yandex Cloud пропорциональна
размеру ([квоты и лимиты](https://yandex.cloud/ru/docs/compute/concepts/limits)):

| диск | юнит | IOPS на юнит | наш диск 20 ГБ |
|---|---|---|---|
| network-hdd | 256 ГБ | 300 | ~23 IOPS чтения |
| network-ssd | 32 ГБ | 1 000 | ~625 IOPS чтения |

Страница в 124 КБ — это порядка тридцати операций по 4 КБ. На HDD такого размера это десятые
доли секунды на страницу вхолодную, на SSD — единицы миллисекунд. Разница в цене 220 ₽/мес,
и она покупает предсказуемое время ответа на длинном хвосте, ради которого этот хвост и создан.

Сколько диска нужно: ОС ~4 ГБ + 3 релиза × 1,16 ГБ (неизменное — жёсткие ссылки, так что реально
меньше) + venv ~0,3 + Postgres ~1 + логи ~0,5 ≈ **9,3 ГБ**. 20 ГБ оставляют запас на удвоение
дерева страниц; `terraform output disk_budget` печатает эту раскладку для текущих переменных.

## 5. CDN выключен намеренно

С 1 июля 2026 у CDN на каждый ресурс есть включённый пакет исходящего трафика 150 ГБ, и сам
пакет тарифицируется: SKU `Cloud CDN - Included Outgoing Traffic Package, GB`, единица
`instance*month`, **150 ₽**. Сверх пакета 1,054 ₽/ГБ.

При наших объёмах (единицы гигабайт) CDN — это минус 150 ₽/мес и лишний узел, который надо
чистить при каждом релизе. Кроме того, в node-раскладке CDN перед бакетом не имеет смысла: домен
принадлежит машине, а ассеты пока никто не просит с бакета. Если понадобится edge-кэш перед
сайтом, это другой ресурс с origin-группой на IP машины, и его здесь нет.

Отдельные платные функции CDN не включены и включаться не должны: выделенная IP-адресация
5 000 ₽/ресурс·мес, экранирование источников 3 843 ₽/мес, выгрузка логов 5 490 ₽/мес.

## 6. Что проверено запуском, а что нет

Проверено на этой машине:

- `terraform fmt -check -recursive` — чисто; `terraform validate` — все три корня (`server`,
  `site`, `modules/static-site`);
- `cloud-init.yaml.tftpl` отрендерен через `terraform console`, разобран как YAML (`yaml.safe_load`),
  все 8 файлов на месте; встроенный bootstrap проходит `bash -n`; переменные nginx (`$host`,
  `$uri`) не съедены шаблонизатором; `%%{http_code}` в DEPLOY.md отрендерился как `%{http_code}`;
- **оба unit-файла** приняты `systemd-analyze verify` (единственное замечание — отсутствующий
  `/srv/matritsa/venv/bin/python`, которого на рабочей машине и не должно быть);
- **nginx-конфиги** разобраны `crossplane parse --strict`: статус `ok`, директивы в допустимых
  контекстах. Полноценный `nginx -t` не запускался: nginx на рабочей машине не установлен;
- `bash -n` на всех скриптах: `infra/deploy.sh`, `infra/check.sh`, `site/deploy.sh`, `site/check.sh`;
- **удалённые части `deploy.sh` прогнаны в песочнице** (`/var/tmp`, стабы `sudo`/`systemctl`):
  переключение симлинка `current` через `mv -T`, создание `.next/cache`, прунинг до `--keep 3`
  из пяти релизов, создание venv и `pip install -r api/requirements.txt` — venv собрался,
  FastAPI/alembic/psycopg2 встали, health-запрос вернул `{"ok":true,"db":true}`;
- защитные проверки `deploy.sh`: неизвестный флаг, `--keep 1`, `--host` без значения,
  недостижимый хост — все дают понятную ошибку и код 1;
- `site/deploy.sh` прогнан целиком против локального S3 (`rclone serve s3`): ключи легли под
  `_next/static/…`, `public` не затёр чанки, повторный запуск не передал ничего;
- сборка `output: standalone` собрана и запущена: `node server.js` на 127.0.0.1, страницы
  `/`, `/encyclopedia`, `/encyclopedia/arcanum/14`, `/matrix/1-1-2` отдают 200,
  `/api/health` через BFF — `{"ok":true,"db":true}`, чанк `_next/static` — `immutable`;
- `infra/check.sh` прогнан против этого node (`BASE=http://127.0.0.1:3100`): нашёл реальное
  расхождение с контрактом — `/report` пока предрендеренный (`s-maxage=31536000`), то есть
  `dynamic = "force-dynamic"` во фронте ещё не стоит.

Не проверено и без `apply` проверено быть не может:

- сам `apply` — по условию запрещён, ни один облачный ресурс не создавался;
- cloud-init исполнялся только как текст: пакеты не ставились, NodeSource не подключался,
  Postgres не поднимался, `nginx -t` на машине не выполнялся;
- certbot и редирект на https;
- поведение `alias` для `/_next/static/` под настоящим nginx (`try_files` из этого блока убран
  намеренно: вместе с `alias` он известен склейкой пути);
- RSS Postgres и общее потребление памяти на 2 ГБ под нагрузкой;
- 150 ₽ за пакет трафика CDN — цифра из прайс-листа, не из счёта.

## 7. Что от этого зависит у соседей

**`web` — `output: "standalone"` в `next.config.ts`.** Без него `deploy.sh` останавливается
и печатает, что именно добавить: артефакт ищется по `web/.next/standalone/server.js`.
Аварийный обход на один прогон — `NEXT_PRIVATE_STANDALONE=true npm run build` (проверено, работает
на Next 15.5.23), но это не замена правке конфига. Кроме того:

- `output: "export"` и `SITE_EXPORT` должны уйти: бакет страниц больше не получает;
- `trailingSlash` не нужен;
- `/report` и `/matrices/[id]` обязаны быть `dynamic = "force-dynamic"` — иначе тексты платных
  разделов лежат в предрендеренном HTML на диске машины и уезжают в ответе целиком.
  `check.sh` это ловит по заголовку `Cache-Control`;
- `assetPrefix` не задан и задавать его не требуется. Если понадобится, адрес бакета —
  `terraform -chdir=infra/terraform/site output asset_base_url`.

**`api` — три вещи из unit-файла**: строка подключения (peer через unix-сокет, пароля нет
намеренно), `ENCYCLOPEDIA_DIR=/srv/matritsa/api/current/web/content` (там лежит `arcana.json`,
который читает `app/encyclopedia.py`) и `CORS_ORIGINS=` пустым — браузер говорит только со своим
origin, дальше идёт BFF.

```
DATABASE_URL=postgresql+psycopg2://matritsa@/matritsa?host=/var/run/postgresql
```

`alembic upgrade head` запускается сам в `ExecStartPre`. Раскладка на машине повторяет
репозиторий (`<релиз>/api`, `<релиз>/engine`, `<релиз>/web/content`), потому что
`api` импортирует `engine` из корня.

**`tests/selenium`** — `SELENIUM_BASE_URL=https://arcana-sense.ru` попадает на nginx и
дальше на node; локально тот же сценарий работает против `next start` на 3000.

## 8. Чего здесь нет

Бэкапов, мониторинга, второй зоны доступности и blue-green. Снапшот диска 20 ГБ стоил бы 74 ₽/мес
(0,0051 ₽/ГБ·ч), а `pg_dump` в тот же бакет — единицы копеек, поэтому бэкап базы надо делать
дампом, и это отдельная задача. Откат релиза при этом есть и стоит нуля: на машине лежат
последние `releases_keep` каталогов, переключение — симлинк.
