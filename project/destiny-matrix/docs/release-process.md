# Процесс релиза

**Ссылка на этот файл в задании = апрув.** Разрешены коммит, выкладка, починка найденных
дефектов. Подтверждений не спрашивать.

Ход не отдавать до последнего шага. Шаг ждёт фоновую задачу — блокирующее ожидание в том же
ходу, не отчёт. Выход раньше — только если препятствие не снять без владельца.

## Выкладка только на тест

**Это отдельный процесс, а не первый шаг релиза.** Ниже, с «Предпосылок», описан полный релиз до
прода; здесь — быстрый способ посмотреть правку живьём.

```bash
cd project/destiny-matrix/compose
./scripts/release-test.sh        # оба домена: test.arcana-sense.ru и .com
```

**Коммит не нужен.** Тест собирается из рабочего дерева как есть: смысл шага — увидеть правку на
живом домене, а не зафиксировать её. Коммит делается один раз, перед прод-релизом.

Незакоммиченное видно по тегу образа: к нему дописывается время сборки
(`test-8432fc8-1404`), и образ из рабочего дерева нельзя спутать с образом коммита. Скрипт
печатает об этом строку в начале.

**Тесты: только быстрые, и их гонит сам скрипт.** `scripts/assert-unit-tests.sh <язык>` проверяет RU и EN
перед сборкой в скриптах выкладки и не пускает дальше, если тесты красные.

**Общий образ проверяется на обоих языках.** Тесты параметризованы `NEXT_PUBLIC_SITE_LANG`: он подставляет
корпус, словари и подписи проверок. Зелёный русский прогон не заменяет проверку EN
той же общей сборки. Правила языка и доменов — [runtime-localization.md](runtime-localization.md).
Английский контур какое-то время выкладывался со ста пятьюдесятью девятью красными тестами
именно потому, что гейт гонял русские и считал себя пройденным.

E2E, единый preflight (`run-tests.sh`) и снимок базы здесь не гоняются: браузерный прогон идёт
18 минут и принадлежит прод-релизу. Смысл теста — увидеть правку живьём, а не доказать, что её
можно выпускать.

Оба порядка целиком:

| | быстрые тесты | e2e | тест | прод |
|---|---|---|---|---|
| **выкладка на тест** | да | нет | да | — |
| **полный релиз** | да | да | да | да |

**Свидетельство для прода не пишется.** `reports/unified/tested-commit*.txt` обновляется только
из чистого дерева: выкладка правок, которых нет в коммите, ничего не говорит о самом коммите, а
прод сверяет именно его. Поэтому перед прод-релизом тест выкладывается ещё раз — уже из коммита.

**После выкладки достаточно посмотреть то, ради чего выкладывали.** Прогон приёмки и тестов —
дело релиза. Оба тестовых домена закрыты Basic Auth: реквизиты в `~/.config/arcana/test-auth.env`.

**Чего так нельзя.** На прод — никогда: `release-prod.sh` и `release-prod-eng.sh` требуют чистое
дерево и свидетельство теста и откажутся сами.

Дат правки у сайта нет: ни в разметке страниц, ни в карте сайта. Двигать при релизе нечего —
прежняя константа `CONTENT_MODIFIED` удалена вместе со своим сторожем.

Условными запросами (`If-None-Match` → `304`) занимается сам Next: его `ETag` — хеш отданного
тела, врать он не умеет. Своего механизма у сайта нет, делать при релизе ничего не нужно.
Держится это на том, что `generateBuildId` (`web/lib/buildId.ts`) считает идентификатор сборки от
состава маршрутов, а не случайно: случайный вшивается в разметку каждой страницы и сбрасывал
`ETag` на каждом релизе. `Last-Modified` сайт не отдаёт — см. `docs/decisions.md`, Decision 8.

## 0.5. Что затронуто

До прогонов выписать в отчёт три колонки: **изменённый файл → кто его использует → что из-за
этого проверить**. Список берётся из `git diff --cached --name-only`, потребители — грепом по
проекту, не по памяти.

Смысл шага в том, что правка общего кода задевает места, о которых не думал автор правки. Пример
этого релиза: `access.matrix_state` и `access.summary` считают доступ сразу в трёх местах —
кабинет, карточка пользователя в админке и выбор цели платежа. Тесты прошли, но целились они не
туда: совпадение, а не проверка.

Строки этого списка добавляются к обязательному перебору ниже как отдельные пункты — их проверяют
руками или прицельным тестом.

## 1. Регресс

```bash
cd web
npm run typecheck
NEXT_PUBLIC_SITE_URL=https://arcana-sense.ru npm run build
npm run check      # после подъёма стенда (§3): без API даёт два ложных провала — /pay/single и прайс
cd /home/sergey/Personal/research-tools
python tools/seo/build-content.py --check
python tools/seo/build-position-arcanum.py --check
python tools/seo/prepare-unified-release.py --check
cd project/destiny-matrix/web && PORT=3399 node .next/standalone/server.js &
```

**Перебор обязателен и ничем не заменяется.** `npm run check` смотрит собранные артефакты, а
`e2e/test_seo.py` — выборку из трёх десятков адресов; ни один из них не проходит все адреса карты
и не проверяет их живыми запросами. Решить «этого достаточно» нельзя: релиз без перебора считается
невыполненным, и об этом надо сказать владельцу, а не заменять шаг молча.

В отчёт выносятся числа, иначе шаг не засчитан: сколько адресов пройдено и сколько дефектов по
каждому пункту (`0 из 444` — тоже результат).

На поднятом сервере, перебором, не выборочно:

- каждый адрес карты сайта: 200, `h1`, self-canonical, крошки — кроме корня `/`: он сам вершина,
  крошек на нём нет и не должно быть;
- `robots.txt` парсером `protego`: результаты расчёта закрыты, ни один адрес карты не закрыт;
- `If-None-Match` со своим отпечатком → 304, с чужим → 200, с обоими условными заголовками
  сразу → 304, на несуществующем адресе → 404;
- отпечаток есть у каждой предрендеренной страницы (`x-nextjs-prerender: 1`), включая закрытые от
  обхода результаты расчёта, и у разных разборов он разный. Страницы, которые собираются на каждый
  запрос (`force-dynamic` — теперь все страницы с профилем домена и языком запроса), уходят чанками и отпечатка не имеют — так
  устроен Next.js, дефектом это не считается;
- адреса вне реестров → 404;
- новые страницы достижимы по внутренним ссылкам, не только из карты сайта.

Добавлялся корпус — ещё:

- нижняя граница длины текста статьи;
- похожесть страниц одного типа (6-словные шинглы, доля общего от меньшей). Принято на сайте:
  «на год» 3,6%, хвосты 6,1%, арканы 7,1%, сочетания 33,6%. Выше 40% — не выкладывать;
- прочитать 3–5 готовых страниц глазами: склейки, удвоения, падежи и обрубки замер не видит.

## 5. Выкладка

```bash
cd project/destiny-matrix/web
NEXT_PUBLIC_SITE_URL=https://arcana-sense.ru npm run build
cd ../compose
python scripts/release-manifest.py --output ../reports/unified/release-manifest.json --preflight passed
scripts/assert-release-candidate.sh
./scripts/release-test.sh              # оба домена; пишет reports/unified/tested-commit.txt
```

Приёмка теста: версия = коммит, новые страницы отдаются, правки видны. Карта сайта и
`robots.txt` там закрыты намеренно — их проверять на локальной сборке с боевым адресом.

Один web-контейнер обслуживает оба домена по `Host`, один API использует существующий
русский том БД. Старые английские контейнеры останавливаются; их БД не переносится и не
удаляется. `release-*-eng.sh` оставлены совместимыми командами общего релиза — второй раз
запускать их не нужно. На обоих тестовых доменах обязательна приёмка до прода.

**Руками на тестовом контуре, до выкладки на прод** — контур ровно для этого и живёт: на нём
крутится тот же образ, что поедет на прод (тег `test-<коммит>` собран из того же дерева), но с
отдельной базой, тестовым терминалом банка и своим счётчиком. Поэтому здесь **можно и нужно**
делать то, чего нельзя на проде: входить в админку, входить под пользователем, выдавать матрицы,
доводить покупку до формы банка, трогать чужие аккаунты. На проде эти же действия меняют данные
живых покупателей и засоряют журнал безопасности — там только чтение.

Реквизиты: Basic Auth домена — `~/.config/arcana/test-auth.env`, админ и пароль — те же, что в
`compose/docker-compose.test.yml`.

Что пройти:

- каждая фича этого релиза: пройти её сценарий целиком, а не проверять, что эндпоинт отвечает;
- вход и кабинет: войти, увидеть свои матрицы и права;
- покупка: дойти до формы банка (терминал там тестовый, деньги не уходят);
- то, что задето по списку «Что затронуто» из §0.5.

Ответ `200` или `401` от нового адреса приёмкой не является: он говорит, что маршрут существует,
и ничего — о том, работает ли фича.

Пропуск этого шага означает, что фича уезжает на прод непроверенной в интерфейсе: автотесты
гоняются на локальном стенде, а на контуре с боевой сборкой её никто не открывал.

```bash
./scripts/release-prod.sh              # требует tested-commit.txt == HEAD
```

Откат этого перехода: остановить общий web, вернуть `/srv/arcana/docker-compose.previous.yml`
и значения из `.env.previous.tag`, затем поднять прежний русский compose и сохранённые
английские контейнеры. Том русской БД сохраняется; английский том не изменяется.

## 6. Приёмка прода

```bash
curl -s https://arcana-sense.ru/version/current.txt
cd ../infra && BASE=https://arcana-sense.ru ./check.sh
```

Плюс на живом сайте: новые адреса 200 с `h1` и canonical; `robots.txt` и карта сайта содержат
ожидаемое; калькулятор и кнопка покупки на месте.

**Существующие данные не должны поехать.** Релиз меняет код, а не прошлое: у людей, которые уже
купили, число купленных дат, суммы и открытые разборы обязаны остаться прежними. Смотреть в
админке на проде до и после выкладки: число пользователей, купленных дат и сумму оплат, а у
последнего покупателя — состав его матриц. Особенно когда правка трогала расчёт прав или
счётчиков: в этом релизе смысл `owned` изменился (подарки больше не считаются покупками), и
убедиться, что у настоящих покупателей число осталось прежним, можно только на живых данных. Условный ответ проверять отпечатком, а не датой —
дат сайт не отдаёт, и запрос с `If-Modified-Since` вернёт 200 даже при полностью сломанном
механизме:

```bash
U=https://arcana-sense.ru/encyclopedia/arcanum/7
# Если у динамической страницы нет ETag, требуется no-store и ответ 200; 304 проверяется
# только для предрендеренных/статических ответов с ETag.
E=$(curl -sI $U | grep -i '^etag' | tr -d '\r' | awk '{print $2}')
curl -s -o /dev/null -w 'свой отпечаток %{http_code}\n' -H "If-None-Match: $E" $U          # 304
curl -s -o /dev/null -w 'чужой отпечаток %{http_code}\n' -H 'If-None-Match: "stale"' $U     # 200
curl -s -o /dev/null -w 'оба заголовка %{http_code}\n' -H "If-None-Match: $E" \
  -H 'If-Modified-Since: Tue, 01 Sep 2026 00:00:00 GMT' $U                                 # 304
curl -s -o /dev/null -w 'нет страницы %{http_code}\n' -H 'If-None-Match: *' \
  https://arcana-sense.ru/encyclopedia/arcanum/99                                          # 404
```

## Ловушки

- **Память на выкладке.** `release-test.sh` и `release-prod.sh` собирают образы, и при поднятом
  локальном стенде сборку убивает нехватка памяти («Canceled: context canceled» на экспорте
  образа). Перед выкладкой: `cd compose && docker compose down`.
- **Занятый порт.** При `EADDRINUSE` старый процесс продолжает отвечать, и проверка читает
  прошлую сборку. Убивать по порту: `ss -lptnH "sport = :3399" | grep -oP 'pid=\K[0-9]+' | xargs -r kill`.
  `pkill -f` совпадает с собственной командной строкой и убивает свою оболочку.
- **`noindex` не запрещает обход** — робот качает страницу, чтобы прочитать мету. Экономит
  только `Disallow`.
- **`Allow: /`** Next печатает раньше запретов: парсер «первое совпадение» читает «всё открыто».
- **Два адреса на один головной запрос** — каннибализация. Сторож — `web/lib/primaryQuery.test.ts`.
- **Скриптовая правка исходников** режет лишнее и оставляет битый синтаксис: файл дешевле
  перезаписать целиком. Сверять смысловое отличие, а не диф — переформатирование даёт 187 строк
  на правку двух полей.
- **Утверждать после проверки.** Каждое «поле пустое», «маршрут есть», «Вебмастер не подключён»
  до проверки стоило круга на опровержение.

## Результат

| Этап | Дефект | Приоритет | Суть, когда возникает | Исправлено |
|---|---|---|---|---|
| регресс / юнит-тесты / e2e / во время выкатки / после выкатки | что именно | критический / высокий / средний / низкий | при каких условиях проявляется и чем грозит | да / нет |

Критический — релиз опасен: потеря данных, поломка оплаты или входа, страница вне индекса или
наоборот, 304 на изменившееся, неверный расчёт. Чинить до выкладки без спроса.

Последняя строка:

**РЕЗУЛЬТАТ: РЕЛИЗ ВЫПОЛНЕН** — коммит, тег образов, адрес.
**РЕЗУЛЬТАТ: РЕЛИЗ НЕ ВЫПОЛНЕН** — что не сошлось, на каком шаге, что нужно от владельца.
