## Главные грабли

### 1. «Нет в базе» не значит «не ищут»

На этом обожглись дважды: в итерации 6 записали «231 страница пар была ошибкой», и
09.09 на том же основании предложили их удалить. Оба вывода неверны.

Причины две, и обе структурные:

- **База — краул от корня, а не перепись запросов.** Фраза попадает в `node` только если
  встретилась в пуле уже запрошенной фразы. Проверено на парах арканов: «8 аркан в матрице
  судьбы» запрошена, дала 36 уточнений (все ≥ 155 показов) — формы «8 и 11 аркан» среди них нет;
  «матрица судьбы совместимость» (57 045) дала 318 уточнений — тоже нет. Во всех 186 574 фразах
  форма «N и M» встречается **9 раз**, и всегда про нумерологию, не про арканы.
- **Это статистика только Яндекса.** А 26 из 35 наших поисковых визитов идут из Google, и
  конкретно на страницы пар — **14 из 15**. Форма запроса, живущая в Google-спросе, в Вордстате не
  появится никогда.

**Как проверять правильно.** Ноль в Вордстате — повод искать второе подтверждение, а не вывод.
Для существующих страниц истина в GSC: он показывает наш реальный хвост. Для новых — ноль в
Вордстате остаётся веским доводом «страницу не делать»: планировать набор адресов по фразам,
которых не видно ни одним замером, — это и есть история 231 страницы пар.

### 2. `FLOOR = 50` — граница рекурсии, а не порог видимости

Фразы ниже 50 показов в базе **есть**: 25 864 узла с частотой 1–9 и 76 841 с 10–49, всего 102 735
(55% базы). Не сделано только одно — не запрашивался их собственный пул уточнений (`queried=1`
лишь у 207 из них), потому что краул ниже 50 вглубь не бурит.

Это правильное решение, менять не надо: уточнения фразы с частотой 20 дают фразы с частотой 2.
И бурение вглубь не решает грабли №1 — нужных форм там нет ни на каком уровне частоты.

### 3. Числовые фразы: считать вхождения, а не множество

`«матрица судьбы 18 9 9»` — это тройка (кармический хвост), но уникальных чисел в ней два.
Разбор через `set()` смешивает тройки с парами и даёт завышенный «спрос на пары». Считать надо
позиции: `len(re.findall(r"\d+", phrase))`.

### 4. Годы рождения ломают числовой разбор

`«матрица судьбы 2010»` при поиске чисел 1..22 распадается на 20 и 10 и попадает в «пары
арканов» с 436 показами. Фильтровать: `re.search(r"(19|20)\d\d", phrase)`.

### 5. Сумма частот по поддереву не складывается

Широкое соответствие родителя уже включает детей. `«расшифровка матрицы судьбы»` (28 575) и её
492 уточнения нельзя суммировать — получится кратный перебор. Складывать можно только фразы
одного уровня, не пересекающиеся по вхождению.

### 6. База общая на несколько тематик

Домены: `destiny-matrix` («матрица судьбы», 17 корней — включая нумерологию, совместимость,
психоматрицу) и `pdf`. Топ-корни по числу детей — как раз `pdf` и `натальная карта`, к нашей ветке
они не относятся. Границы ветки: `domain_member` для корней либо маска — по
`phrase LIKE '%матриц%' OR '%аркан%'` выходит **7 074 фразы на 4 453 337 показов/мес**.

### 7. Оплаченные данные не пересоздавать

`cache` (48 576 ответов Вордстата), `serp`, `history` — куплены за деньги. `node` и `edge` —
производные, пересобираются из `cache`. Новая колонка в `node` — только `ALTER TABLE`: колонка,
попавшая в список «новых», заставляет пересобрать дерево и затирает работу LLM (уже случалось).

## Рецепты

```python
# все частоты в память — так быстрее, чем запрос на фразу
freq = {p: f for p, f in db.execute(
    "select phrase, freq from node where freq is not null")}

# топ фраз по маске
db.execute("""select phrase, freq from node
              where phrase like ? and freq is not null
              order by freq desc limit 20""", ("%деньг%матриц%",)).fetchall()

# объём кластера (осторожно с граблёй №5)
db.execute("""select count(*), sum(freq) from node
              where phrase like ? and freq is not null""", ("%чакр%",)).fetchone()

# запрошена ли фраза и сколько дала уточнений
db.execute("""select phrase, freq, queried, total_refinements from node
              where phrase = ?""", ("8 аркан в матрице судьбы",)).fetchone()

# уточнения фразы
db.execute("""select n.phrase, n.freq from edge e join node n on n.phrase = e.child
              where e.parent = ? order by n.freq desc""", ("матрица судьбы совместимость",)).fetchall()

# есть ли выдача в кэше (повторный разбор бесплатен)
db.execute("select engine, found from serp where phrase = ?", ("матрица судьбы ладини",)).fetchall()
```

**Сверить запросы страницы с реальным спросом** — этим ловятся страницы, целящиеся в
несуществующую формулировку (так нашлись 22 хвоста с нулём и три чакры):

```python
import json
items = json.load(open("web/content/karmic-tails.json", encoding="utf-8"))["items"]
for it in items:
    qs = (it.get("seo") or {}).get("queries") or []
    print(it["key"], freq.get(qs[0], 0), sum(freq.get(q, 0) for q in qs))
```

## Как купить выдачу

Платно, поэтому только под конкретную гипотезу. Ключи в `.env` корня репозитория
(`XMLRIVER_USER`, `XMLRIVER_KEY`, `XMLRIVER_YANDEX_URL`, `XMLRIVER_GOOGLE_URL`).

```python
import sys; sys.path.insert(0, "/home/sergey/Personal/research-tools")
import tasks
r = tasks._serp_request("yandex", "матрица судьбы ладини")   # или "google"
for d in r["docs"]:
    print(d["rank"], d["url"], d["title"])
```

Топ-10 (`SERP_TOP`), регион Россия (`YANDEX_LR = 225`, `GOOGLE_LOC = 2643`), три повтора при
транзиентной ошибке с паузами 10/30/60 с.

**Грабля: `_serp_request` в базу не пишет.** Он только ходит в сеть и разбирает XML. Пока
результат не сохранён, повторный запрос той же фразы — повторная оплата. Записывает
`wscore.save_serp(con, phrase, {"yandex": {...}, "google": {...}})`, и он требует **оба движка
сразу**: при отсутствии одного — `ValueError` и в базу не попадает ничего. То есть покупать надо
парой, иначе выдача останется незакэшированной.

**`XMLRIVER_CACHE_ONLY=1`** — промах кэша не идёт в сеть. Без него краул широкого узла уходит в
платные запросы тысячами.

Прочие константы краула: `LIMIT = 2000` (потолок пула у самого XMLRiver), `WORKERS = 6`.

## Чем мерить, кроме Вордстата

| Источник | Что даёт | Ограничение |
|---|---|---|
| **Подсказки Google** (XMLRiver, `setab=tips`) | какими словами тему спрашивают и в каком порядке; для английского поля это единственный доступный сигнал | объёмов не даёт вовсе. Оплата пофразная: пакет из 50 фраз стоит как 50 запросов. Кэш — таблица `suggest` в `semcore.db`, ключ «фраза + источник + регион»; сбор и сверка с корпусом — `tools/seo/suggest-keys.py` |
| **GSC** | наш реальный длинный хвост: показы, клики, позиции по фразам и страницам | выгружает владелец, история 3 месяца, редкие запросы скрыты (в замере 09.09 видно 48% показов). Нигде не хранится — каждая выгрузка пропадает после разбора |
| **Метрика** | визиты из поиска с разбивкой по поисковику и странице входа | API открыт, счётчик `111856670`; позиций не даёт |
| **Яндекс.Вебмастер** | «Страницы в поиске», исключённые с причинами, статистика обхода | только выгрузка владельцем: API с метрическим токеном отвечает `ACCESS_FORBIDDEN`, нужен свой scope |

### Подсказки: как собирают и когда останавливаются

Подсказка отдаёт продолжения корня, но не продолжения продолжений: «destiny matrix 10» приводит
«destiny matrix 10 center», а хвосты этой формы приходят, только если спросить её саму. Поэтому
сбор идёт волнами — формы прошлой волны становятся корнями следующей:

```bash
python tools/seo/suggest-keys.py --collect          # первая волна: корни из корпуса
python tools/seo/suggest-keys.py --expand           # волны по полученным формам
python tools/seo/suggest-keys.py                    # отчёт по тому, что в базе (бесплатно)
python tools/seo/suggest-keys.py --apply            # записать ключи в корпус
```

**Конец — не по числу проходов, а по исчерпанию источника:** два прохода подряд без единой новой
формы. Замер 20.09: 135 корней → волна 1 дала 236 новых форм, волна 2 — 17, волна 3 — ноль.
Куплено 586 фраз, собрано 674 формы; дальше источник молчит, и следующий сигнал — только GSC
через 3–4 недели после индексации.

Разложение форм по страницам решает **состав слов корня, а не их порядок**. Сначала сверка шла
по префиксу, и тогда «destiny matrix center 10» находила свою страницу, а «destiny matrix 10
center» оставалась ничьей: эти формы приходят от разных корней — позиции и аркана. Порядок слов
в подсказках произволен, тема одна; переход на сравнение множеств вернул страницам 156 форм за
один прогон.

Три правила отсекают чужое: тройка чисел принадлежит хвосту, а не аркану; число 1–22, которого
нет в корне страницы, — это номер аркана с её пересечения; название позиции («love line»,
«money line») в форме аркана или года означает страницу пересечения. Без них «destiny matrix 19
love line» осело бы на странице девятнадцатого аркана, а «destiny matrix center 5» — на странице
центра, уводя запрос у пересечения.

### Порогов показа больше нет

`SHOW_THRESHOLD` в `build-position-arcanum.py` и `publication.index` у кармических хвостов
закрывали от поиска готовые страницы, у которых Вордстат не показал частоту. Порог снят
20.09: текст уже написан, показ не стоит ничего, а Вордстат редкие формы просто не отдаёт —
закрывать по нему страницу значит доверять отсутствию данных больше, чем самому тексту.
Открыты все 90 пересечений и все 26 кармических хвостов на обоих языках.

Порог **заведения** (`THRESHOLD = 500`) остался: он про то, писать ли текст руками, и там довод
про стоимость работает.

### Намерение выдачи

Живая форма ещё не значит нашу: по запросу могут искать расчёт, а не чтение. Проверяется по
одному главному запросу на тип страницы, выдача ложится в тот же оплаченный `serp`:

```bash
python tools/seo/serp-intent.py --fetch    # докупить недостающее
python tools/seo/serp-intent.py            # отчёт из кэша
```

Считать калькуляторы по сниппету нельзя: сайты-калькуляторы пишут «free calculator» в описании
каждой своей страницы, включая статьи, и по сниппету калькулятором оказывается вся выдача.
Решает заголовок, и признак статьи сильнее признака расчёта. Замер 20.09 по шести типам: везде
в топ-10 есть статьи, чистой калькуляторной выдачи нет ни у одного типа.

Пример запроса к Метрике — визиты из поиска по страницам входа:

```bash
curl -sS -G "https://api-metrika.yandex.net/stat/v1/data" -H "Authorization: OAuth $TOKEN" \
  --data-urlencode "ids=111856670" \
  --data-urlencode "date1=2026-08-01" --data-urlencode "date2=2026-09-09" \
  --data-urlencode "metrics=ym:s:visits" \
  --data-urlencode "dimensions=ym:s:lastSearchEngineRoot,ym:s:startURLPathFull" \
  --data-urlencode "filters=ym:s:lastSearchEngineRoot!n" \
  --data-urlencode "limit=100" --data-urlencode "sort=-ym:s:visits"
```
