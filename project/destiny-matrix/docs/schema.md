# Схема базы

SQLite. Схема меняется миграциями: `python -m app.schema ensure` создаёт пустую базу сразу в
последнем виде, а живую проводит по `schema.MIGRATIONS` по порядку. Каждая миграция идёт одной
транзакцией с выключенными внешними ключами, проверяется `foreign_key_check` до COMMIT и
записывается в `schema_migrations`; при сбое база остаётся прежней.

```
python -m app.schema ensure   # создать недостающее, применить миграции, наполнить справочник
python -m app.schema reset    # снести всё и создать заново (стенд: уносит платежи)
```

Перед релизом с новой миграцией — снимок базы (его делает `release-prod.sh`). Это страховка
данных: старый код на новой схеме не работает, а откатов прода нет (`decisions.md`, Decision 17).

Для доменов одного окружения база общая. Языковая модель описана в
[runtime-localization.md](runtime-localization.md); ниже — её поля хранения:

- `readings.title = NULL` означает автоматическую подпись на языке запроса; ручные и прежние
  сохранённые названия остаются строками.
- `purchases.offer_body` содержит снимок предложения, `locale`, сайт и подключение оплаты —
  для писем и досверки. Отдельного пользователя или права доступа для каждого языка нет.
- `report_jobs.locale` — язык PDF, учитываемый при поиске готового отчёта и дедупликации.

Полный актуальный состав таблиц задаёт `api/app/models.py`; ниже — обзор.

Две настройки соединения обязательны и включены в `models.py`: `PRAGMA foreign_keys=ON` — без него
`ON DELETE CASCADE` не работает вовсе, и `journal_mode=WAL` — без него читатель блокирует
писателя. Плюс `busy_timeout=5000`, чтобы конкурентная запись ждала, а не падала.

## Модель

| Таблица | Что это |
|---|---|
| `users` | аккаунт: почта, хеш пароля, последнее появление |
| `readings` | разбор: продукт (`personal`, `pair`), ввод JSON, `subject_key` для повторов, подпись |
| `offers` | цена продукта в канале: продукты (`*` — все, включая будущие), на один разбор или на любые, хранение без лимита, срок, витрина |
| `purchases` | заказ: снимок предложения, разбор, сумма, канал; оплата и возврат — его факты |
| `payments` | попытка оплатить заказ у провайдера: номер у банка, ссылка на форму, банковский статус |
| `entitlements` | право: продукты, разбор или «любые», хранение, сроки, отзыв; ссылается на заказ |
| `report_jobs` | печать PDF разбора на языке |
| `work_tasks` | задача исполнителя (MCP `arcana-tasks`): тип, статус `queued → signalled → done/failed`, разбор, причина, параметры |

Продукт — это код (`api/app/products.py`, `web/lib/pair/`): какие данные вводят, когда два ввода —
один разбор, как его подписать и где напечатать. Деньги, права, печать, кабинет и админка от
продукта не зависят.

Номера разборов совпадают с номерами прежней таблицы `matrices`, номера заказов — с номерами
прежних платежей (миграция `001_products`): старые адреса `/matrices/<id>`, `/report?m=<id>`,
ссылки в письмах и ключи PDF в хранилище остались верными.

Авторизованный `pulse` приходит раз в 45 секунд, но `last_seen_at` не пишется на каждый запрос:
API хранит последнее время по `user_id` в памяти и раз в час обновляет весь накопленный пакет одним
коммитом. Поэтому значение в админке может отставать от фактического присутствия не более чем на
час. Во всех контурах по умолчанию используется `PRESENCE_FLUSH_SECONDS=3600`.

Сессия админа, вошедшего под пользователем, присутствие не отмечает: её токен помечен `gho`, и
`pulse` такую отметку не копит. `last_seen_at` — появление самого человека, а не того, кто смотрел
его кабинет.

## Связи

```
users ─┬─< readings      (CASCADE)
       ├─< purchases     (CASCADE)
       ├─< payments      (CASCADE)
       └─< entitlements  (CASCADE)

purchases ─< payments.purchase_id        (CASCADE — попытка без заказа бессмысленна)
readings  ─< purchases.reading_id        (SET NULL — заказ переживает удаление разбора)
readings  ─< entitlements.reading_id     (CASCADE — право без разбора бессмысленно)
purchases ─< entitlements.purchase_id    (SET NULL — право переживает чистку заказов)
readings  ─< report_jobs.reading_id      (CASCADE)
readings  ─< work_tasks.reading_id       (SET NULL — задача сохраняется после удаления разбора)
```

## Предложения

| id | name | price | продукты | на разбор | срок |
|---|---|---|---|---|---|
| `single` | Полный разбор одной даты | 39 000 (390 ₽) | `personal` | да | бессрочно |
| `pair` | Совместимость пары | 39 000 (390 ₽) | `pair` | да | бессрочно |
| `month` | Подписка на 3 месяца | 59 000 (590 ₽) | `*` | нет, плюс хранение без лимита | 90 дней |

Витрина — `public = 1` и канал запроса; оба продукта включены всегда, флага включения нет.
`GET /api/tariffs?product=pair` — витрина продукта, без параметра — личного
разбора. Цену из браузера сервер не принимает: браузер присылает код предложения.

Как человек доходит до оплаты — [`payments.md`](payments.md).

Цены меняются `UPDATE offers`, пересборка не нужна. Новая цена попадает и в снимок заказа —
`purchases.offer_body` пишется на момент покупки, поэтому история не переписывается.

## Как считается доступ

Ни `users`, ни заказ не решают, что открыто, — решают действующие права (`api/app/access.py`).
Право действует, если `revoked_at IS NULL`, `starts_at` уже прошёл и `expires_at` либо пуст, либо
в будущем.

- `can_open` — разбор открыт правом на этот разбор или правом без разбора на его продукт
  (подписка). Разовое право без разбора не открывает ничего, пока его не привяжут.
- `can_open_unsaved` — расчёт без сохранения открывает только право без привязки к разбору.
- `storage_limit` — без ограничения при праве с хранением; иначе один разбор продукта бесплатно
  плюс по одному за каждое купленное разовое право. Повторное сохранение того же ввода место не
  тратит.
- `reading_state` — для кабинета: `forever`, `granted`, `subscription` с `access_until`, `locked`.
- `holdings` — единственная сводка прав для экранов (`/auth/me` → `access.holdings`, строки
  админки): подписки, затем разборы по продуктам, купленное и выданное отдельно. Строка «Доступ»
  в кабинете и админке только выводит её (`web/lib/holdings.ts`); `plan_label` — подпись в шапке
  разбора по тому же состоянию права. В PDF подписи доступа нет: файл живёт дольше прав.
- `refund_outcome` — что станет с доступом без прав заказа: текст окна возврата в админке и письма
  о возврате. Обещаний «разбор закроется» заранее нигде нет.
- Все сочетания «продукт × откуда открыт × порядок возвратов» перебирает
  `api/tests/test_access_matrix.py`; ожидания там записаны по правилам этого раздела.
- `held` / `covering` — единственная проверка «такое право уже есть». Через неё идут `can_open`,
  отказ в продаже (уже открыто сейчас, подписка в том числе) и выдача админом (нет своего
  выданного права — выдаём, даже поверх подписки или покупки: выданное переживает их возврат).
  На разбор допускается одно купленное и одно выданное действующее право — два уникальных
  индекса (миграция `003_granted_beside_bought`); в кабинете купленное показывается купленным,
  пока его не вернули.

**Как разовое право находит свой разбор.** Разбор выбирает человек на экране оплаты, и наверх
уходит его номер или ввод, который сервер сохранит сам. Право без разбора (купленное до правила о
привязке) привязывается один раз — к первому сохранённому после оплаты разбору того же продукта
(`access.bind_unbound`).

Подписчику сайт ничего не продаёт: кнопки покупки, тарифы и цены в текстах скрыты, а расчёт без
сохранения открыт целиком: полные тексты приходят по числам карты (`/api/sections?slug=`,
`/api/pair/units?keys=`), без подписки эти адреса отвечают 404. Исключение —
`/api/sections?slug=…&preview=locked`: закрытые разделы без толкований (карты позиций и заглушка
вместо текста чакр), его получает любой посетитель. Решает это один режим посетителя
во фронте — `useOfferMode` (`free`, `subscription`, `sell`); компоненты флаги сами не сверяют. Вторую подписку API не продаёт
(409). Админ выдаёт дату, пару и подписку из карточки пользователя; выданное помечено как выданное
и покупкой не считается.

Купленная пара не трогает личный разбор: верхние поля `GET /auth/me` (`scopes`, `matrices_limit`,
`owned`) считаются только по правам, покрывающим `personal`; по каждому продукту — `access.products`.

Следствие, которое стоит держать в голове: подписка истекает через 90 дней, и разборы
закрываются, а записи в кабинете остаются. Купленный разовый разбор не истекает никогда.

## Корпус разбора пары

Тексты пары — `web/content/<язык>/pair-units.json`, юнит на ключ `<сфера>:<числа>` (`meet:14+15`,
`money:22-5-10`, `parents:J:9`, `characters:dual:5`, `business:base:11`). Какие ключи вообще бывают,
считает перебор `web/lib/pair/reachable.ts`: все даты 1900 — текущего года и все пары значений тех
личных точек, из которых складывается ключ (сумма пары симметрична). Выборка пар для этого не
годится: редкие сочетания она пропускала, и у такой пары сфера уходила в заглушку.

- Полноту стерегут тесты: `web/lib/pair/corpus.test.ts` — юнит на каждый достижимый ключ на каждом
  языке, поля по типу и объём по эталону (`web/lib/pair/unitCheck.ts`), запреты `text-policy`,
  повторы заголовков и «Главного» внутри семейства; `web/lib/corpusParity.test.ts` — у остальных
  корпусов ключи на всех языках совпадают с русскими.
- Файл писателя проверяется тем же кодом: `npx tsx --tsconfig tsconfig.json
  scripts/check-pair-units.ts <файл> [ru|en]`.

**Совместимость в работе** — раздел того же разбора и той же покупки (Decision 16). Считается
по Лисовской (глава 5, «Сделка, бизнес-партнёр») не сложением матриц, а сложением дат: день с днём,
месяц с месяцем (без ограничения двенадцатью), год с годом; на «дату» строится обычная матрица
(`fromPoints` в `web/lib/matrix.ts`), блок предназначений не читается — `web/lib/pair/business.ts`.
Эталон — пример коллектива из книги (все точки) и пример сделки (точки, не зависящие от Д: в нём
опечатка издания, см. `library/lisovskaya/general/05-known-issues.md`). Без покупки открыты две
деловые сферы — `base` и `plus`; бесплатная часть приходит по числам (`/api/pair/preview?base=…&plus=…`).

`PDF_REVISION` поднят до `v8`: напечатанные PDF пар с заглушками перепечатываются при скачивании.

**Чакры пары** — готовый статический корпус. Тексты —
файлы `web/content/pair-chakras/<язык>/<чакра>/<тройка>.json` входят в образ сайта.
API, БД, MCP и S3 не участвуют в получении толкований. Открытый разбор получает восемь
готовых текстов из корпуса: семь чакр и общее энергополе. Файлы читаются по нужным ключам
и кешируются в памяти процесса сайта; платные тексты передаются только при наличии доступа.
Полноту всех достижимых ключей RU/EN и форму файлов проверяет
`web/lib/pair/chakraCoverage.test.ts`.

Миграция `008_static_pair_chakras` удаляет старые задания типа `pair_chakras` и таблицы
ожиданий/динамических текстов; остальные задания MCP сохраняются. Новая версия PDF
перепечатывает ранее сохранённые отчёты штатным механизмом ревизий.
