# Google-вход: общий аккаунт сайта и Android

Пользователь согласовал отдельную кнопку Google на сайте и в приложении, сохранение
парольного входа и гостевого доступа к расчёту, бесплатной части и встроенному примеру.
Google Play Billing и Google Sign-In — разные интеграции: установка APK не создаёт сессию Arcana.
iOS и Sign in with Apple в эту работу не входят.

## Как связываются аккаунты

Сервер проверяет подпись Google ID token, издателя, Web client ID, срок действия и одноразовый
nonce. Связь хранится по стабильному Google `sub`, а не по имени, фотографии или присланному
клиентом адресу. Веб получает обычную HttpOnly-сессию Arcana, Android — ту же сессию в защищённом
хранилище. Права и покупки принадлежат прежнему `user_id`.

Если связи ещё нет, совпадение подтверждённого адреса Gmail/Google Workspace с подтверждённой
почтой существующего аккаунта позволяет войти в него. Если существующий адрес никогда не
подтверждался или Google не является владельцем почтового сервиса, потребуется один раз
подтвердить пароль аккаунта либо восстановить его по письму. Это защищает от ситуации, когда
аккаунт заранее зарегистрировали на чужой адрес и сохранили известный постороннему пароль.
Административные аккаунты продолжают использовать парольный вход.

При отсутствии существующего аккаунта для подтверждённого Gmail/Workspace создаётся новый.
Для сторонней почты сначала нужна обычная регистрация и подтверждение адреса по письму:
одного старого Google `email_verified` недостаточно, чтобы исключить смену владельца этой почты.
Google-only пользователь может входить
Google-кнопкой на обеих платформах. Для операций, требующих текущий пароль, интерфейс предлагает
задать пароль по письму; это не отключает Google-вход. Удаление, период восстановления и права
общего аккаунта сохраняются. Восстановительная сессия не открывает обычный кабинет и покупку.

После входа приложение возвращает только на проверенный внутренний маршрут выбранного разбора
или покупки. Внешние адреса и неизвестные параметры не принимаются. Покупка сама не запускается.

## Что требуется настроить в Google Cloud

Настройки Console не создавались. Нужен проект Google Cloud с Google Auth Platform; Firebase
Auth и перенос базы пользователей не нужны. Для локальной проверки не требуется публикация
в Google Play. [Настройка Google Identity Services](https://developers.google.com/identity/gsi/web/guides/get-google-api-clientid).

1. В **Google Auth Platform → Branding** указать Arcana Sense, контакт поддержки и ссылки
   действующего сайта. В **Audience** выбрать подходящий тип аудитории; для тестового внешнего
   приложения добавить проверяющие Google-аккаунты в test users.
2. В **Clients** создать OAuth-клиент типа **Web application**. Его публичный `Client ID`
   вида `123…-abc….apps.googleusercontent.com` используется и сервером, и Android.
   Client secret приложению не требуется и в APK не помещается.
3. Для локального сайта добавить используемые **Authorized JavaScript origins**:
   `http://localhost`, `http://localhost:3000`, а для текущего локального профиля `.com` —
   `http://127.0.0.1` и `http://127.0.0.1:3000`. Использовать точный origin без `/ru`, `/en`
   и других путей. Сайт запускается в обычном `next dev`.
   Реальные origins `https://arcana-sense.com` и `https://test.arcana-sense.com` добавляются
   только когда понадобится соответствующий контур; добавление origin само по себе не выкладывает код.
4. Для выбранного popup/callback-сценария отдельный redirect URI не нужен. Одновременно
   необходимо разрешить официальный `https://accounts.google.com/gsi/client` и связанные
   источники Google в действующей политике страницы.
5. Создать второй OAuth-клиент типа **Android** в том же проекте:
   package name — `com.arcanasense.app`;
   SHA-1 текущей локальной подписи —
   `5E:8F:16:06:2E:A3:CD:2C:4A:0D:54:78:76:BA:A6:F3:8C:AB:F6:25`.
   Android client ID не подменяет Web client ID при проверке токена сервером.
   Для будущего APK из магазина понадобится отдельно зарегистрировать SHA-1 Play App Signing.

Серверная настройка: `GOOGLE_SIGN_IN_CLIENT_ID=<Web client ID>`. При пустом значении Google-вход
отключён; действующий парольный вход остаётся. После изменения переменной нужно перезапустить
локальный API штатным способом. Секреты и ID не требуется записывать в исходники.

Перед запуском нового серверного кода применяется миграция `015_google_sign_in`: поле
`has_password`, таблицы Google-связей и одноразовых запросов входа. Штатный `run-python.sh`
выполняет `python -m app.schema ensure` перед запуском API. Для отдельного запуска API выполните
эту команду из `api/` в правильном Python-окружении, предварительно проверив свой `DATABASE_URL`.
Миграция сохраняет существующие пароли и пользователей. Базу чужого временного стенда и его
процессы в этой задаче не меняли; тесты миграции выполнены на изолированных временных базах.

Android использует `react-native-nitro-google-signin` 2.3.1 и `react-native-nitro-modules` 0.37.2.
Credential Manager получает публичный Web client ID и nonce от API после нажатия кнопки,
перед открытием выбора аккаунта. Секрет Google, Firebase и фиктивная конфигурация iOS в APK не нужны.
Нативные модули подключаются через autolinking. Плагин библиотеки для Firebase/iOS в этой
Android-конфигурации не используется; требуется полноценная пересборка APK, одного Metro мало.
После установки этой сборки добавление Web client ID на сервере не требует новой пересборки:
он читается приложением перед входом.

Для Android локальный API может оставаться доступным по LAN-адресу компьютера, как описано
в [mobile/README.md](../mobile/README.md). Google-выбор аккаунта выполняется нативно;
LAN-адрес API не является JavaScript origin сайта.

## Проверка после настройки

- Новый Google-аккаунт: вход в Android, затем на сайте; один пользователь, одни сохранённые данные.
- Существующий подтверждённый Gmail: вход без создания второго аккаунта, прежние покупки доступны.
- Существующая неподтверждённая или сторонняя почта: запрос пароля/восстановления, без потери покупок.
- Отмена Google-окна и отсутствие сервисов Google: обычный парольный вход остаётся доступен.
- Выход и повторный вход; попытка открыть сохранённый разбор; возврат к обеим выбранным датам пары.
- Google-only аккаунт: задание пароля по письму, вход новым паролем и сохранение Google-входа.
- На отдельном тестовом аккаунте: удаление и восстановление в пределах установленного срока.

Настоящую связь с Google нельзя считать проверенной по замоканным токенам или успешной сборке.
Нужен вход с настроенными OAuth-клиентами на реальном устройстве и в браузере.
