# Энциклопедия: источник контента

Правила языков и устройства приложения — [runtime-localization.md](../docs/runtime-localization.md).
Ниже описан только конвейер контента. Для RU и EN он одинаков: исходный корпус плюс
редакционные материалы из `tools/seo/content/<lang>/`, затем проверка итоговых артефактов.
Английские собранные JSON не являются отдельным ручным источником; `prepare-content.sh en`
выполняет базовую сборку и редакционное обогащение, но не пересчитывает русский реестр спроса.

Текст живёт в JSON-файлах каталогов `data/ru/` и `data/en/`. В этих каталогах нет исполняемого
Python: базовые наборы читает и преобразует `source.py`, а `build.py` также переносит корпус
персональных чакр. Фронт читает не исходные наборы, а собранный JSON в `web/content/<lang>/` —
он и есть артефакт сборки. Для подготовки контента
используется одна команда из корня проекта:

```bash
compose/scripts/prepare-content.sh
```

Скрипт всегда выполняет полную обязательную последовательность:

1. собирает базовый корпус из `content/data/`;
2. накладывает редакционные статьи из `tools/seo/content/`;
3. для RU обновляет SEO-реестры и карточки аудита;
4. обновляет golden-векторы и полный parity-снимок расчёта;
5. проверяет, что итоговые файлы воспроизводимы и весь корпус проходит валидацию.

Запускать только `python -m content.build` для подготовки готового результата нельзя: этот
внутренний этап перезаписывает `arcana.json` и `positions.json` базовыми версиями, а полноценные
SEO-тексты возвращаются только на следующем шаге. Единый скрипт нужен, чтобы эта последовательность
больше не разрывалась.

Клиентский `points-catalog.json` короче каталога точек: в него идут только точки, у которых в
расчёте есть своё число. Партнёрская точка R1 (`love_middle`) живёт внутри линии отношений, и
таблица «Все позиции карты» читает матрицу по ключу — строки для неё быть не может. Страница в
энциклопедии и трактовки у точки при этом полные, как у остальных.

Внутренний `content.build` перезаписывает восемь файлов для выбранного языка: четыре базовых корпуса `arcana.json`,
`combinations.json`, `positions.json`, `chakras.json`, два клиентских каталога
`arcana-catalog.json`, `points-catalog.json`, политику `text-policy.json` и корпус персональных
толкований `chakra-personal.json`. Последний содержит тексты по точной тройке каждой чакры
и общие заключения по полной карте; он переносится из `data/<lang>/chakra-personal.json`.
После этого
единый скрипт обогащает результат и проверяет его. Сборка детерминированная, кроме явно
датированного parity-снимка, который обновляется по текущий день.

Отдельные команды ниже запускаются из корня репозитория `research-tools` и предназначены
только для диагностики и проверки уже подготовленного результата:

```bash
python tools/seo/prepare-unified-release.py --check
python tools/seo/build-content.py --check
```

Первый gate воспроизводит 26 ordered-хвостов, классификацию 603 запросов, миграцию 81 URL,
publication registry и карточки аудита. Второй не пропускает хвост вне `spec/method.json`,
переставленный `arcana[]`, noindex с SEO-запросами и дубли primary query.

## Что где лежит

| файл | что внутри |
|---|---|
| `data/<lang>/arcana.json` | 22 аркана: название, слаг, короткая фраза, значение, плюсы и минусы, ключи |
| `data/<lang>/in-positions.json` | 836 толкований: каждый из 22 арканов в 20 разделах и 18 точках карты |
| `data/<lang>/pairs.json` | 231 сочетание пар `a < b`: короткая фраза и два абзаца |
| `data/<lang>/sections.json` | 20 разделов: о чём раздел, как читать, SEO |
| `data/<lang>/points.json` | 18 точек карты: подпись в отчёте, формула, значение и привязка к разделам |
| `data/<lang>/chakras.json` | 7 чакр: значение уровня и смысл трёх колонок |
| `data/<lang>/chakra-personal.json` | персональные толкования по тройкам семи чакр и общие заключения по карте |
| `data/<lang>/text-policy.json` | общий для Python и frontend список: канцелярит (ошибка валидатора) и медицинские и гарантийные слова (предупреждение) |
| `source.py` | загрузка JSON, запрет дублирующихся ключей и адаптация ключей позиций и сочетаний |
| `seo.py` | заголовки, описания и запросы; описание сочетания берётся из его же текста |

## Правила, которые держит валидатор

- заголовки, вводки и доступ разделов не дублируются в контенте, а берутся из
  `engine.sections.SPEC`; ключи и порядок чакр — из `engine.matrix.CHAKRAS`;
- 22 аркана × 38 контекстов — без пропусков; 231 пара — вся сетка, без дублей и без
  перевёрнутых пар;
- проверяемый базовый набор содержит 299 страниц (22 + 38 + 231 + 7 + корень), у каждой есть
  входящая ссылка и хотя бы одна исходящая, все `href` ведут на существующие страницы.
  Это не полное число маршрутов сайта: редакционные статьи, каталоги и другие ветки
  проверяются также загрузчиком контента и frontend gate;
- ни одного повторяющегося текста и канцелярита из `data/<lang>/text-policy.json`; медицинские и
  гарантийные слова оттуда же — предупреждения, а не ошибки;
  уникальность зачина обязательна и для статей, и для всех 836 позиционных карточек;
- один поисковый запрос закреплён за одной страницей.

Нижние планки по длине (`MIN_*` в `validate.py`) — защита от заглушек, а не мера качества:
средняя длина сочетания сейчас 403 знака при пороге 350.
