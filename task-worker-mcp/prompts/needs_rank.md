# needs_rank — возможен ли здесь самостоятельный продукт (Opus / Sol, xhigh)

Перед тобой уже **принятая классификация** дерева потребностей. Она решила только, какие фразы
описывают одну работу. Теперь глубоко оцени каждую работу по другому вопросу:

> Насколько вероятно, что запросы выражают потребность в результате, который физически может
> дать самостоятельный сторонний продукт, а не статья, инструкция, поддержка или кнопка внутри
> чужой платформы?

Это дорогая задача для Opus / Sol с глубоким рассуждением. Прочитай классификацию и исходные
фразы целиком, затем отдельно перепроверь 20 самых частотных фраз каждой работы. Не торопись и
не переноси одну общую догадку на все работы.

## Жёсткая граница задачи

**Не анализируй конкурентов и не пытайся узнать, свободен ли рынок.** Не используй веб, поисковую
выдачу, названия существующих сервисов, SEO-сложность, цену трафика или свою память о том, кто
уже делает такой продукт. Наличие известного решения не понижает оценку: здесь проверяется
физическая возможность продукта, а не рыночная щель.

Оцени только то, что видно из работ и запросов:

- какой результат человек пытается получить;
- может ли сторонний продукт контролировать этот результат;
- ищет ли человек инструмент или, вероятнее, объяснение/кнопку/поддержку;
- можно ли описать конкретный вход и выход продукта;
- повторяется ли сценарий и даёт ли продукт ощутимую ценность.

Не меняй классификацию: не переименовывай, не объединяй и не разделяй работы, не перемещай
фразы. Верни ровно одну оценку на каждое исходное имя работы.

## Сначала выбери тип намерения

- `product` — нужен результат, который способен выдать отдельный инструмент.
- `mixed` — возможен инструмент, но значительная часть запросов, вероятно, ищет инструкцию или
  штатную кнопку.
- `information` — в основном хотят узнать «как», прочитать правило или инструкцию.
- `platform_action` — результат контролирует владелец чужой платформы: код входа, восстановление
  аккаунта, разблокировка, возврат взломанного аккаунта, изменение серверного состояния.
- `support` — диагностика или починка чужого продукта; сторонний продукт не может гарантировать
  сам результат.
- `navigation` — ищут вход, раздел, кнопку, настройку или конкретный экран.
- `unclear` — из классификации всё ещё не понятен требуемый результат.

Тип — это cap, а не готовая оценка:

| intent | максимум |
|---|---:|
| `product` | 100 |
| `mixed` | 60 |
| `information` | 30 |
| `support` | 20 |
| `platform_action` | 15 |
| `unclear` | 10 |
| `navigation` | 5 |

Если не можешь назвать конкретный самостоятельный продукт, итог дополнительно ограничен 25.

## Шесть факторов

Для каждой работы поставь целое число 0–100 по каждому фактору. Оцени их независимо; не
подгоняй всё под заранее понравившийся итог.

1. `external_control` — может ли сторонний продукт сам выдать обещанный результат? Ноль, если
   результат может совершить только Telegram, банк, маркетплейс или владелец аккаунта.
2. `tool_intent` — насколько фразы похожи на поиск инструмента, а не статьи, поддержки,
   инструкции, кнопки или настройки.
3. `outcome_clarity` — насколько однозначны пользователь, вход и требуемый выход.
4. `product_shape` — насколько конкретно можно описать самостоятельный продукт как
   `вход → обработка → результат`, не выдавая статью за продукт. Работа со списком разделов
   (`segments` с `kind: "section"`) — это **один** продукт с многораздельным выходом, а не
   склейка нескольких: разделы делят вход и обработку, и оценивать их надо вместе. Понижать
   оценку за то, что «одна позиция — слишком тонкий продукт», можно только когда у работы
   действительно один раздел.
5. `repeatability` — насколько сценарий повторяемый, а не разовая авария или редкая настройка.
6. `user_value` — сколько времени, ручного труда, денег или риска способен снять продукт.

Базовая оценка:

```text
round(
  external_control × 0.25 +
  tool_intent      × 0.20 +
  outcome_clarity  × 0.15 +
  product_shape    × 0.15 +
  repeatability    × 0.10 +
  user_value       × 0.15
)
```

Итоговый `score` — минимум из базовой оценки, cap намерения и 25, если `product = null`.
Сервер пересчитает число и отклонит ответ при несовпадении.

## Калибровка на Telegram

- «получить код входа в Telegram» — `platform_action`: код выдаёт Telegram, сторонний продукт
  не может выполнить обещание. Возможна статья, но это не продукт; оценка у дна шкалы.
- «получить доступ к Telegram при сетевой блокировке» — `product`: физически возможен внешний
  сетевой инструмент с ясным результатом; оценка может быть высокой. Конкурентов не обсуждай.
- «починить неработающий Telegram» — обычно `support`: диагностика может стать контентом, но
  сторонний продукт не контролирует починку чужого приложения; оценка низкая.
- «подготовить и опубликовать пост в Telegram» — `mixed`: часть людей ищет кнопку или инструкцию,
  но возможен редактор/планировщик. Оценка средняя и зависит от фактических фраз; не ставь 80
  только потому, что продукт можно вообразить.
- «вернуть взломанный аккаунт Telegram» — `platform_action`: решение контролирует Telegram;
  сторонний сервис не должен обещать возврат аккаунта.
- «расшифровать голосовое или видео из Telegram» — `product`: файл можно обработать вне
  Telegram, вход и выход ясны, продукт физически возможен. Не понижай оценку из-за того, что
  похожая функция может существовать внутри платформы: это уже вопрос конкуренции.

## Доказательство обязательно

`evidence` должен содержать 1–5 **точных фраз этой работы**, которые сильнее всего определили
тип намерения и факторы. Не выдумывай фразы и не ссылайся только на имя работы. В `score_why`
объясни итог через физический контроль результата и инструментальный/информационный интент.

`product` — одна конкретная форма самостоятельного продукта, если она действительно следует из
фраз, иначе `null`. Не называй статью, консультацию, инструкцию или службу поддержки продуктом.
`blocker` — главное ограничение; для высокой оценки может быть `null`.

## Вход

```json
{
  "model_family": "claude или codex",
  "source": {"root":"...","nodes":[{"phrase":"...","freq":123,"children":[]}],
             "head_nodes":[{"phrase":"...","freq":204741,"children":[]}]},
  "classification": {"condition":null,"works":[...],"excluded":[...]}
}
```

## Выход

```json
{
  "works": [
    {
      "name": "точное имя работы из classification",
      "intent": "product|mixed|information|platform_action|support|navigation|unclear",
      "factors": {
        "external_control": 0,
        "tool_intent": 0,
        "outcome_clarity": 0,
        "product_shape": 0,
        "repeatability": 0,
        "user_value": 0
      },
      "score": 0,
      "score_why": "почему это самостоятельный продукт или почему его здесь нет",
      "product": "конкретный вход → результат" | null,
      "blocker": "главное ограничение" | null,
      "evidence": ["точная исходная фраза"]
    }
  ]
}
```

Проверь перед отправкой: все работы присутствуют ровно по одному разу; имена не изменены;
факторы оценены независимо; `score` пересчитан по формуле и cap; evidence взят из соответствующей
работы; конкуренты и выдача нигде не использованы.
