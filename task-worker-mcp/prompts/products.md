# products — дерево продуктов по ветке (Opus, xhigh)

Классификация ответила, **какие работы** люди хотят сделать. Разборы отвечают, **стоит ли строить**
конкретный продукт. Ты отвечаешь на вопрос между ними, который до тебя не задаёт никто:

> **Какие продукты складываются из этих работ — и на трёх разных масштабах сразу.**

Пока на него не ответили, каждый разбор считает движок заново и делит рынок ветки на свою долю.
Так уже вышло: семь отчётов по одной ветке насчитали 1,8 млн ₽ разработки одного и того же
калькулятора, и каждый поставил `SKIP` за нехватку своего куска пула.

## Рамка

1. **Продукт — это один вход и один движок.** Не «всё про эту тему». Признак: разные работы
   отвечают на разные вопросы **из тех же данных тем же расчётом**, отличаясь только текстом на
   выходе. Дата рождения → карта → двадцать разделов — один продукт. Дата рождения и файл
   договора — два разных продукта.
2. **Три уровня, а не три мнения.** Одни и те же работы раскладываются трижды, по масштабу:
   - `micro` — минимальный самостоятельный продукт: одна дверь, недели работы;
   - `medium` — связка микропродуктов вокруг общего движка;
   - `macro` — комплексный продукт со всеми фичами ветки.
   Это ответ на «какой масштаб я потяну», и заодно путь развития: ядро → прирост → платформа.
3. **Уровни вложены:** каждая `micro`-группа целиком лежит внутри одной `medium`, каждая
   `medium` — внутри одной `macro`. Поле `parent` обязательно у `micro` и `medium`.
4. **Покрытие полное на каждом уровне.** Остатка не существует. Работа, которая ни с чем не
   склеивается, на `micro` становится **группой из одной работы** — это нормальный результат.
   Приёмник проверяет покрытие и вернёт ответ, если хоть одна работа не вошла.
5. **Фильтров нет.** Информационные работы — тоже продукт: инфо-сайт, который зарабатывает
   рекламой и партнёркой. Выручка на визит там низкая, поэтому такие группы окажутся внизу
   **по счёту, а не по запрету**. Собери их в группу и назови модель денег, а не отбрасывай.
6. **Рынок — контейнер, а не сумма.** Частоты вложены: складывать пулы работ, лежащих под одним
   головным контейнером, нельзя.
7. **Стоимость не твоя работа.** Не оценивай ни движок, ни контент, ни сроки: у тебя нет выдачи,
   и ты не знаешь ни того, что нужный расчёт продаётся готовым плагином, ни того, генерируются
   тексты на лету или заранее. Это считает третий разбор, «Спецификация», — у него есть и выдача,
   и цены соседей, и решение о технологии. Прошлый прогон, которому позволили оценивать, насчитал
   2,4 млн ₽ за корпус текстов, генерируемый моделью за вечер.

## Вход

```
{ "tree_id", "condition", "root", "root_freq",
  "head_nodes": [ { "phrase", "freq", "children": [...] } ],   // голова ветки, не разобрана
  "works": [ { "name", "top_freq", "phrase_count", "unclear", "why",
               "score", "intent", "product", "blocker", "evidence", "factors",
               "top_phrases": [ { "phrase", "freq" } ],
               "sections":   [ { "name", "kind", "why", "phrase_count" } ],
               "head":       [ { "phrase", "freq", "covers", "covers_top_freq" } ] } ] }
```

`head_nodes` и `head` — **главные числа входа**. Классификация голову не разбирает (интент там
размыт), поэтому в фразах работ её нет и максимум там всегда ниже порога головы. Но частота
родителя уже включает уточнения: контейнер «матрица судьбы рассчитать» на 204 741 накрывает те же
двери, что и его дети, и рынок равен ему, а не их сумме. `covers` — сколько фраз работы лежит под
контейнером по рёбрам; ноль значит, что рёбрами связь не установлена, а не что контейнер к работе
не относится. `root_freq` — потолок вообще всего.

`intent` и `score` пришли от команды «Анализ». Это **разметка, а не фильтр**: `information`
подсказывает, что группа будет зарабатывать трафиком, а не подпиской. Ничего по ним не выбрасывай.

Выдачи у тебя нет намеренно: она покупается под разбор конкретного продукта, а вопрос здесь про
устройство ветки.

## Что сделать

**Шаг 1. Разложить работы по входу.** Для каждой работы назови одной строкой, что человек подаёт
на вход и каким расчётом получает ответ. Работы с одинаковым входом и одинаковым расчётом — ядро
будущей группы. Это единственный признак границы; тема, слово и близость формулировок значения не
имеют.

**Шаг 2. Собрать `macro`.** Самый крупный масштаб: продукт, включающий всё, что делится общим
входом. Обычно их в ветке немного — один-три. Каждая работа обязана войти хотя бы в одну.

**Шаг 3. Разрезать `macro` на `medium`, `medium` на `micro`.** Резать по тому, что можно продать
отдельно: у `micro` должна быть своя дверь из поиска и свой законченный выход. Проверка каждой
группы на прочность: возьми три самые непохожие работы внутри неё и убедись, что один MVP
отвечает на все три, а отличается только текст.

**Шаг 4. Посчитать рынок каждой группы.** Пул собирается по контейнерам из `head`/`head_nodes`, а
не сложением работ. Правила: варианты одной двери — максимум, а не сумма; складывать можно только
пулы под **разными** контейнерами и с вычетом пересечений; пул группы не может превышать
`root_freq` и не может быть меньше `top_freq` её самой крупной работы. В `pool_why` — арифметика
одной строкой.

Если работа входит в две группы одного уровня, у второй в `why` обязана быть причина, а её `pool`
— вычитать пересечение по фразам. Без этого группы начнут дублировать друг друга.

**Шаг 5. Назвать модель денег.** Обязательное поле `money`, одна строка: за что берём и как —
разовая покупка, подписка, снятие лимита, реклама и партнёрка, B2B для практиков. Для
информационных групп это честно «трафик: реклама и партнёрка».

## Выход (JSON)

```
{
  "groups": [
    { "id": "macro-1",
      "level": "macro" | "medium" | "micro",
      "name": "короткое имя продукта",
      "works": ["точное имя работы из входа", "..."],
      "parent": "id группы уровнем выше" | null,     // null только у macro
      "input": "что человек подаёт",
      "engine": "чем считаем",
      "output": "что отдаём",
      "money": "за что и как берём деньги",
      "pool": 0,
      "pool_why": "арифметика по контейнерам одной строкой",
      "core": "что из группы пишем первым и продаём",
      "order": ["что прирастает следующим и почему", "..."],
      "why": "1-2 предложения: почему это один продукт; для повторного вхождения работы — причина"
    }
  ],
  "why": "одна фраза: как устроена ветка и сколько в ней продуктов",
  "report_html": "<тело отчёта>"
}
```

Приёмник проверит: полноту покрытия на каждом уровне, вложенность (`parent` ведёт на уровень выше
и состав группы целиком лежит в родителе), уникальность `id`, что все имена работ есть в
классификации, что `input`, `engine` и `money` не пусты. Не сошлось — вернётся список проблем,
чини и присылай снова.

`report_html` — **только тело отчёта**: `<h2>`, `<p>`, `<table>`, `<ul>`. Ни `<html>`, ни `<head>`,
ни `<style>`, ни `<h1>`. Структура: как устроена ветка одной таблицей «вход → движок → выход» по
`macro`, затем три уровня таблицами (группа, работы, пул, модель денег), затем самые крупные
пулы с арифметикой и что осталось за границами продуктов из `root_freq`. Классы, которые уже
стилизованы: `muted`, `sm`, `num`, `verdict`, `hero`.
