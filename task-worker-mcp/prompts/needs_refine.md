# needs_refine — второй проход классификации дерева потребностей

Перед тобой уже готовый первый вариант дерева потребностей и тот же полный исходный набор фраз.
Это не новый анализ рынка. Твоя задача — **перепроверить классификацию**, убрать загрязнение и
вернуть полностью исправленное дерево в той же схеме.

## Вход

```json
{
  "model_family": "claude или codex",
  "source": { "root": "...", "nodes": [{"phrase":"...","freq":123,"children":[]}] },
  "draft": { "condition": null, "works": [...], "excluded": [...] }
}
```

`source` — источник истины. `draft` — гипотеза первого прохода: сохраняй удачные решения, но не
защищай их от исправления. Используй только фразы из `source`; не ищи новые фразы и не обращайся
к вебу или выдаче.

## Что проверить

### 1. Не угадывать неясное намерение

Если из самой фразы и её положения в исходном дереве нельзя однозначно понять требуемый
результат, она должна лежать в отдельной работе `unclear: true`. Категория уже существует — не
создавай `unresolved`, `quarantine` или другую новую сущность.

Для `unclear: true` обязательны:

- честное имя «что-то … — результат из фразы не ясен»;
- `score` от 0 до 10;
- `gap_candidate: false`;
- `occupied_by: null`;
- `needs_serp: false`, `serp_question: null`;
- двусмысленные фразы не остаются в конкретных работах и не завышают их `top_freq`.

### 2. Одна работа — один микро-продукт

Одна работа имеет **одного пользователя, один вход и один результат**. Один микро-MVP должен
закрывать все её основные однозначные формулировки. Мысленно опиши каждую работу как
`пользователь + вход → один результат`, затем перепроверь минимум 20 самых частотных её фраз.

Разделяй работы, если отличаются продукты, даже когда совпадает объект или слово:

- создать ≠ найти готовое ≠ купить ≠ удалить;
- обработать своё ≠ сохранить или посмотреть чужое;
- новый аккаунт ≠ восстановление существующего;
- штатная настройка платформы ≠ внешний инструмент;
- сделать бота ≠ найти бота ≠ отключить бота.

Сегмент оставляй только когда результат и продукт те же, а отличается аудитория, вход или
ограничение. Сегмент с другим продуктом становится отдельной работой.

### 3. Убрать загрязнение

Для каждой работы проверь:

- самая частотная фраза однозначно принадлежит заявленному результату;
- омонимы и общие головы не используются как доказательство размера конкретной работы;
- фразы не склеены лишь общим существительным (`бот`, `номер`, `запись`, `статус`, `аккаунт`);
- `phrase_count` равен фактическому числу фраз работы вместе с сегментами;
- `top_freq` равен максимальной частоте среди фактически назначенных ей фраз.

Если одна конкретная работа не выдерживает проверку своих top-20 фраз, не понижай ей score и не
пиши оговорку — **исправь классификацию**: раздели, перенеси в другую работу либо в существующую
`unclear`-работу.

### 4. Сохранить полноту

Каждая фраза `source.nodes` должна встретиться ровно один раз:

- в `phrases` конкретной работы;
- либо в `phrases` её сегмента;
- либо в `phrases` работы `unclear: true`;
- либо в `excluded`, если это действительно не работа (`brand`, `catalog`, `consumption`,
  `broken`, `condition`, `other`).

Не теряй, не дублируй и не выдумывай фразы. Не переноси двусмысленное в `excluded`: это
реальный спрос с неясным результатом, его место в `unclear: true`.

## Выход

Верни **полное исправленное дерево**, а не diff и не список замечаний, точно по схеме первого
прохода:

```json
{
  "condition": "..." | null,
  "works": [
    {
      "name": "...", "phrases": ["..."], "top_freq": 0, "phrase_count": 0,
      "score": 0, "score_why": "...", "unclear": false,
      "segments": [{"name":"...","phrases":["..."],"gap_candidate":false,"why":"..."}],
      "occupied_by": null, "gap_candidate": false, "needs_serp": false,
      "serp_question": null,
      "why": "почему это один пользователь, вход и результат"
    }
  ],
  "excluded": [{"phrase":"...","why":"brand|catalog|consumption|broken|condition|other","note":"..."}]
}
```

Ответ проверяется на полное покрытие исходных фраз. Если у джоба объявлен `result_file`, запиши
JSON ровно туда и вызови `submit_result(job_id)` без `result`; иначе передай JSON значением.
Успех — только `accepted: true`.
