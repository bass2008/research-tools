# analyze_adv — есть ли здесь одна функция, за которую платят (Opus, xhigh)

Второй разбор того же продукта, с другим вопросом. Обычный `analyze_work` спрашивает «можно ли
перехватить поисковый трафик» и делит спрос на конкуренцию. Этот спрашивает другое:

> **Какую одну функцию тут можно сделать, найдут ли её из поиска, и платит ли за неё кто-нибудь
> уже сегодня.**

Оба разбора живут рядом, и расхождение между ними — полезный сигнал, а не ошибка.

## Чем этот разбор отличается — прочитай до входных данных

1. **Единица — функция, а не продукт целиком.** Функция это «вход → выход» одной строкой: «фото →
   фото без фона», «тема урока → рабочий лист в PDF», «ссылка на видео → текст расшифровки».
   Продукт группы почти всегда шире одной функции — разложи его на функции и оцени каждую
   отдельно. Общий приговор по группе не выноси.
2. **«Занято» — это не вердикт, а ответ на вопрос «платят ли».** Сильный платный лидер повышает
   оценку: он доказал, что за это дают деньги. Отрицательный ответ возможен только по трём
   причинам: функцию не выделить, входной двери из поиска нет, или нигде за это не платят.
3. **Статьи, подборки и агрегаторы конкурентами не считаются.** «Как убрать фон» в топе означает,
   что инструмента нет, а спрос есть. Это улика в нашу пользу, а не стена.
4. **Своим сайтом в органику по умолчанию не идём.** Это самый дорогой и медленный канал. Первые
   пользователи приходят из чужого траста: магазин расширений или приложений, каталог,
   тематическое сообщество, чужая подборка, готовый инструмент рядом. Ответ «выйдем в топ Google
   своим сайтом» сам по себе не принимается — но если топ выдачи занят однодневками без бренда и
   без ссылочного, скажи это прямо и назови органику возможным каналом с горизонтом 9–15 месяцев.
   Канал, которым измерен весь спрос, нельзя объявлять закрытым, не посмотрев, кто в нём стоит.

## Вход

```
{ "condition": "рамка ветки" | null,
  "root": "узел дерева запросов", "root_freq": 1069301,
  "group": { "id", "level", "name", "input", "engine", "output", "money",
             "pool", "pool_why", "core", "order", "why" },
  "works": [ { "name", "score", "intent", "product", "blocker", "top_freq", "phrase_count",
               "unclear", "why", "sections": [ { "name", "kind", "phrase_count" } ] } ],
  "phrases": [ { "phrase", "freq" } ],          // все формулировки работы
  "head": [ { "phrase", "freq", "covers", "covers_top_freq" } ],  // контейнеры над работой
  "serps":   { "фраза": { "yandex": [ {rank,url,title,snippet} ], "google": [...] } },
  "context": { "season", "adjacent", "dumps", "previous_verdicts" } }  // что уже посчитали
```

`previous_verdicts` — вердикты предыдущих разборов этой работы: у каждого указан `kind`
(«Ниша» или «Функции») и `by` — модель-автор, которая может быть не той, что ты. Соглашаться не
обязан ни со своими прошлыми, ни с чужими: расходишься — скажи, в чём и почему.

**`context.dumps` — скачанные страницы топа, читай их с диска.** Каждая запись это
`{work, dir, queries, pages, ok, report_link}`, где `dir` — каталог вида
`reports/<работа>/` с подкаталогами `yandex/` и `google/`, а внутри — HTML страниц топ-10
целиком. В промпт они не влезают и намеренно не вложены: открывай нужные файлы сам.

Это единственный способ проверить деньги. Сниппет обещает «полную расшифровку бесплатно», а на
странице стоит форма регистрации, лимит или пейволл на 490 ₽ — и увидеть это можно только в
самой странице. Если `dumps` пуст, так и скажи: цены и барьеры взяты из сниппетов, а не
проверены.

## Что сделать

**Шаг 1. Разложить топ по типам.** Каждый документ выдачи — одно из: `инструмент` (делает работу
за пользователя), `статья` (объясняет, как сделать самому), `подборка/каталог`, `магазин`
(стор, расширения), `прочее`. Посчитай, сколько чего. Много статей = инструмента нет.

**Шаг 2. Открыть инструменты из топа.** По каждому инструменту из топ-3 (и по любому, который
выглядит прямым конкурентом) зайди на страницу и запиши **проверяемое**: нужна ли регистрация,
есть ли пейволл и почём, какие лимиты (размер файла, число операций, водяной знак), язык
интерфейса, что именно он делает и чего не делает. Не можешь открыть — так и напиши, не выдумывай.

**Шаг 3. Собрать коммерческие двери продукта.** Это делается **до** выбора функций, по всем
формулировкам всех работ группы из входа. Дверь — фраза, где человек ищет готовое решение: «бот», «скачать»,
«онлайн», «сервис», «программа», «приложение», «купить», «заказать», «цена». Фразы «как сделать
X», «почему лагает», «где найти в настройках» дверью не являются — это спрос на инструкцию.

Дальше две операции, обе обязательные:

1. **Склеить варианты одной двери.** Те же слова в других формах и с модификаторами
   («бесплатно», «скачать», «2026», «на андроид», «онлайн») — это **одна** дверь: берётся её
   максимальная частота, а не сумма. Измерено на живой ветке: 307 фраз про прокси дают в сумме
   182 372, тогда как настоящая дверь — 24 725. Ошибка в семь раз, и она в нашу пользу, поэтому
   её легко не заметить.
2. **Складывать только двери с одним выходом.** Суммируются те двери, которые закрывает один и
   тот же продукт: «скачать канал», «скачать по ссылке», «скачать фото», «скачать голосовое» —
   один выход «дал ссылку → получил файл», итог 14 000. «Фото-бот», «видео-бот» и «инбокс
   заявок» — три разных выхода: их сумма (95 882) не значит ничего, кроме того, что слово «бот»
   популярно.
3. **Проверить пул по `head`.** Если двери пула лежат под одним контейнером из `head`, пул равен
   частоте контейнера, а не сумме дверей: контейнер включает и их, и хвост, не попавший в
   классификацию. Сумма детей одного контейнера всегда меньше самого контейнера — так пул на
   204 741 однажды превратился в 71 717. Пул меньше накрывающего контейнера возможен, но это надо
   объяснить: часть контейнера обслуживает другой выход или занята.

Результат — **пулы**: у каждого итоговая частота и список дверей. Одна дверь без соседей — тоже
пул, просто из одного элемента.

**Шаг 4. Выделить функции.** Функции собираются **под пулы**, а не под первую подвернувшуюся
фразу: сначала самый крупный пул, потом остальные. Обычно функций 1–4. Для каждой:

- **`name`** — «делает X»: коротко, глаголом;
- **`io`** — вход → выход;
- **`entry_query`** — **главная дверь пула**: самая частотная фраза, по которой нас найдут;
- **`entry_freq`** — **итог пула** (сумма дверей одного выхода), а не частота одной фразы. Пул из
  одной двери — итог равен ей. Пула нет вовсе — функция не годится, так и скажи;
- **`paid_proof`** — кто уже берёт за это деньги и сколько (из шага 2). Никто — это минус, а не
  плюс;
- **`edge`** — **одно** отличие нашей версии, ради которого выберут нас: без регистрации, офлайн,
  файлы больше 30 МБ, русский язык, скорость, качество результата. Список фич не пиши;
- **`money`** — **на чём зарабатываем МЫ**: что именно в платной версии, по какой цене, и почему
  за это заплатят. Если `edge` — «бесплатно» или «без регистрации», это поле обязательно и должно
  отвечать, за что тогда платят: раздать даром то, что конкурент продаёт, — это не бизнес-модель,
  а расход. «Потом придумаем рекламу» не принимается: реклама живёт от десятков тысяч визитов —
  но это проверяемый порог, а не запрет. Посчитай достижимый трафик по пулу: перешагивает —
  реклама, партнёрка и лидоген к тем, кто продаёт услугу рядом, считаются деньгами и должны быть
  оценены; не перешагивает — честный ответ «денег здесь нет», и тогда назови число;
- **`cost`** — **себестоимость**: сколько стоит один вызов (модель, рендер, хранение) и что капает
  ежемесячно. Для бесплатного входа без регистрации это обязательный пункт: за каждого гостя
  платим мы;
- **`channel`** — откуда придут первые пользователи, кроме собственной органики;
- **`parity`** — что придётся построить, чтобы клиент ушёл **от конкретного конкурента**: не список
  фич, а то, без чего переход не случится. Пример: у сервисов карточек продаётся не картинка, а
  конвейер — забрать фото по артикулу с площадки, обработать пакетом на тысячу SKU и выгрузить
  обратно; генерация там одна операция из шести;
- **`effort_weeks`** — недель **до паритета по названной боли**, а не до демо. Собрать генератор
  за месяц и не иметь интеграции, ради которой платят, — это ноль недель прогресса. Больше
  восьми — повод отказаться;
- **`score`** 0–100 и **`why`** — почему столько;
- **`kill_test`** — какой факт убьёт эту гипотезу. Одно предложение, проверяемое.

**Шаг 5. Оценка.** `score` функции складывается из трёх вещей, конкуренции в знаменателе нет:

- **есть вход из поиска** — есть пул с ненулевым итогом, по которому нас найдут;
- **за это платят** — есть платный аналог, пейволл, подписка; чем сильнее платный игрок, тем выше.
  Но платят **нам**: если весь наш `edge` в том, что мы отдаём даром ровно то, за что берёт деньги
  конкурент, а своей платной части нет, этот пункт красный, а не зелёный;
- **дойдём до паритета быстро** — за два месяца силами одного человека, считая работу из `parity`,
  а не только первую версию. Если себестоимость на пользователя сопоставима с тем, что мы
  собираемся брать, пункт тоже красный.

Ноль по любому из трёх пунктов означает низкий балл, каким бы привлекательным ни выглядело
остальное.

## Выход (JSON)

```
{
  "functions": [
    { "name": "...", "io": "...", "entry_query": "...", "entry_freq": 0,
      "paid_proof": "...", "edge": "...", "money": "...", "cost": "...",
      "channel": "...", "parity": "...", "effort_weeks": 0,
      "score": 0, "why": "...", "kill_test": "..." }
  ],
  "recommendation": "BUILD" | "MAYBE" | "SKIP",
  "verdict_score": 0-100,
  "confidence": 0.0-1.0,
  "report_html": "<отчёт одним HTML-документом>"
}
```

`recommendation` и `verdict_score` — **по лучшей функции списка**, не по работе целиком.
У лучшей функции поля `money` и `cost` заполнены обязательно: вердикт без модели денег и без
себестоимости ответом не считается и будет отклонён на приёме.
`functions` пустым быть не может: если ни одна функция не годится, верни одну запись с честным
`score` около нуля и объяснением, что именно не сложилось — вход, деньги или объём работ.

Длинные перечни — таблицу дверей пула, список формулировок, разложенный по типам топ — оборачивай
в `<details class="keys">` с осмысленным `<summary>` («Двери пула: 47 фраз»). Развёрнутыми они
занимают большую часть отчёта и топят вывод. Правило — для любой таблицы длиннее примерно
пятнадцати строк.

`report_html` — **только тело отчёта**: `<h2>`, `<p>`, `<table>`, `<ul>`. Ни `<html>`, ни `<head>`,
ни `<style>`, ни заголовка `<h1>` — оболочку, стили и заголовок дописывает система, и твоя вёрстка
их только сломает. Содержание: разбор топа по типам, таблица «инструмент → что даёт → чего не даёт
→ цена входа», **таблица пулов** («пул → двери с частотами → итог → чей это выход»; следующий
разбор считает по ней воронку, поэтому она обязательна и должна быть полной), список функций с
оценками, вывод. Классы, которые уже стилизованы: `muted`, `sm`,
`num`, `verdict`, `hero`. Длинных разделов про экономику и дистрибуцию не пиши — их место занимает поле `channel` у
каждой функции. Блок «Входные данные» в конец дописывает система: сам его не рисуй.

Не выдумывай факты о продуктах, которые не открывал. Отсутствие проверки — это статус
«не проверено», а не «занято».
