# Tech design: конвейер `drill` (как строим)

> **Область документа.** Это технический дизайн, а не код.
>
> **Здесь:** архитектура и верхнеуровневые решения; **все публичные методы и их контракты** (§6) —
> HTTP-эндпоинты, сообщения WebSocket, MCP-инструменты, CLI-команды: что принимают, что
> возвращают, какие ошибки; требования, проверяемые снаружи; порядок работ.
>
> **Не здесь:** код и псевдокод, сигнатуры внутренних функций, внутренние структуры данных и
> имена переменных, конфиги и команды запуска.
>
> Граница: **публичный интерфейс — да, его внутреннее устройство — нет.**

Пара к `design-plan.md`: **design = ЧТО** (поведение, FSM, принципы), **этот док = КАК**
(архитектура, контракты, порядок работ). Где расходятся — прав `design-plan.md`.

Обратимые решения — в **§10**.

---

## 0. Архитектура

Нагрузка I/O-bound (запросы к XMLRiver + ожидание LLM) и однопользовательская на localhost,
поэтому **брокер и отдельные воркер-процессы не нужны**: всё серверное живёт в одном процессе
FastAPI на asyncio.

Три процесса:

```
┌─────────────┐   команды (HTTP POST)     ┌──────────────────────────────┐
│  React SPA  │ ───────────────────────►  │          FastAPI             │
│ (frontend)  │ ◄───── чтение (WS) ─────  │  API + очередь задач + шина  │
└─────────────┘                           │  событий + SQLite + статика  │
                                          └───────┬──────────────▲───────┘
                              забрать задачи      │              │  вернуть результат
                                                  ▼              │
                                          ┌──────────────────────┴───────┐
                                          │      task-worker-mcp         │
                                          │   транспорт задач к Claude   │
                                          └───────────────┬──────────────┘
                                                          │ MCP
                                          ┌───────────────▼──────────────┐
                                          │        Claude Code           │
                                          │   петля: забрал → агенты →   │
                                          │   вернул результат (§7.1)    │
                                          └──────────────────────────────┘
```

- **FastAPI** — команды, WebSocket-чтение, очередь фоновых задач, шина событий, SQLite,
  раздача фронта и готовых отчётов.
- **task-worker-mcp** — тонкий транспорт: отдаёт Claude накопившиеся LLM-задачи и принимает
  результаты. Своего интеллекта не имеет, к Anthropic API не ходит.
- **Claude Code** — и есть LLM: запускается с промпт-инструкцией (§7.1), разбирает задачи
  суб-агентами, выбирая модель под тип.

**Почему одного процесса хватает.** Тяжёлое — снаружи: краул ждёт XMLRiver, LLM-шаги ждут Claude
в отдельном процессе. Своей вычислительной работы у сервера почти нет, а ожидание внешнего ответа
почти ничего не стоит. Узкое место — лимиты XMLRiver и скорость LLM, и оно одинаково при любой
инфраструктуре. Требование к этому решению одно: **одна долгая операция не должна тормозить
остальные и подвешивать UI**.

## 1. Окружение

- Python-окружение — существующее `research3.12`.
- Доставить: поддержку WebSocket для uvicorn; пакет `task-worker-mcp` (зависимости — MCP SDK и
  HTTP-клиент). **Redis и Celery не нужны.**
- Обновить `requirements.txt` соответственно.
- **Предусловие для LLM-шагов:** установлен и залогинен Claude Code. Без запущенной петли (§7.1)
  LLM-задачи не выполняются — см. «LLM offline» в §6.

Новое в `.env` (в дополнение к `XMLRIVER_USER`/`XMLRIVER_KEY`):
| Переменная | Зачем |
|---|---|
| `XMLRIVER_YANDEX_URL`, `XMLRIVER_GOOGLE_URL` | эндпоинты выдачи для `search` |
| `APP_URL` | адрес FastAPI, куда ходит task-worker-mcp |
| `INTERNAL_TOKEN` | общий секрет для внутренних эндпоинтов (§6) |

Модели агентов (classify=Sonnet, score=Haiku, analyze=Opus) задаёт **промпт-инструкция Claude
Code** (§7.1) — ни сервер, ни `prompts/*.md` их не знают.

## 2. Модель исполнения

- **Очередь задач — в памяти процесса.** Команда ставит задачу и сразу отвечает ack; выполнение
  фоновое, прогресс — по WebSocket.
- **Одновременных операций может быть много** — ожидание внешнего ответа дёшево. Ограничивать
  нужно только обращения к XMLRiver: источник платный и не любит наплыва.
- **Долгие LLM-операции не останавливают конвейер** — несколько идущих `analyze` не должны
  блокировать `classify`/`search` по другим узлам.
- **Источник истины и аудит — SQLite** (таблица `task`); очередь в памяти рестарт не переживает.
- **После рестарта не остаётся «залипших» узлов.** Незавершённые на момент падения задачи
  считаются проваленными, блокировки снимаются. Согласовано с design §0: узел остаётся в последнем
  согласованном статусе, недоделанная операция = ошибка в лог.

## 3. Обмен с LLM

Поток: задача → очередь LLM-задач → Claude забирает пачкой → возвращает результат → задача
дописывает модель.

1. Задача формирует входные данные и кладёт их в очередь LLM-задач, затем ждёт результат с
   таймаутом.
2. Claude (через `task-worker-mcp`) забирает **пачку** задач — чтобы разбирать их суб-агентами
   параллельно (design §5). Если задач нет, получает пустой список и повторяет.
3. Результат возвращается тем же путём обратно; задача разблокируется, пишет `node`/`serp`,
   переводит статус и публикует события.

Правила:
- **Крупные операции режутся на части** — одна операция = несколько обращений к LLM:
  - `classify` — порциями по ~120 узлов: поддерево бывает в тысячи узлов, целиком в запрос не
    влезет, да и на длинном списке качество разметки падает к концу. Резать безопасно, потому что
    каждый узел самодостаточен (несёт свою фразу, частоту и своих детей) и классифицируется
    независимо — зависимостей между порциями нет.
  - `score` — пачками по 8–15 фраз: на каждую фразу идут две выдачи топ-10 с заголовками и
    сниппетами, это объёмно. Пачка держит запрос вменяемого размера и позволяет оплатить длинную
    рубрику оценки один раз на несколько фраз, а не на каждую.
  - Размер порции — компромисс: мельче → на каждый узел заново шлётся вся инструкция (дорого и
    медленно); крупнее → хуже качество на хвосте и больше потерь, если порция упала.
  - **Одна операция = одна строка `task`.** Дробление — деталь транспорта: пользователь нажал
    `Classify` на узле и должен видеть одну строку, а не семнадцать. Операция считается
    выполненной, только когда вернулись все её части, иначе часть узлов осталась бы без разметки
    при уже сменившемся статусе.
  - **Часть операции = «джоб», у него свой `job_id`** — это единица обмена с LLM: именно `job_id`
    фигурирует в контрактах границы (§6.3), и по нему сервер понимает, к какой операции и к каким
    узлам относится пришедший результат. У операции из одной части (`analyze`) джоб один. Как
    именно `job_id` устроен и как хранится соответствие «операция ↔ джобы» — дело реализации;
    наружу видно только то, что он уникален и что Claude обязан вернуть результат с тем же
    `job_id`.
- **Крупная операция не должна падать по таймауту при нормальной работе** — ожидание учитывает
  объём (число частей), а не фиксировано на одну порцию. Порядок величин: минуты для
  `classify`/`score`, десятки минут для `analyze`.
- **Забор задачи — без резервирования и переочередей.** Если Claude упал, задача не вернётся в
  очередь: страховка — таймаут (задача `FAILED`, узел не тронут). Ретраев нет (design §0).
- **Опоздавший результат** (пришёл после таймаута или рестарта) отбрасывается с предупреждением
  в лог — сервер при этом не падает.
- **Любой отказ** (таймаут, ошибка агента, невалидный JSON) → `task=FAILED`, запись в лог,
  **узел остаётся как был**. `drill` ловит падение шага, логирует и продолжает остальное поддерево.

## 4. Операции

| Операция | Класс | Что делает | Переход |
|---|---|---|---|
| `load` | не-LLM | загружает пул одной фразы — один уровень вниз (браузинг) | `NEW` → `LOADED` |
| `full_load` | не-LLM | краул поддерева до конца (§5) | → `FULLY_LOADED` на корне и всех узлах поддерева |
| `search` | не-LLM | выдача Яндекс+Google, топ-10, в `serp` | `TRANSACTIONAL` → `SEARCHED` |
| `classify` | LLM | размечает поддерево по интенту (чанки) | `FULLY_LOADED` → `TRANSACTIONAL`/`CATEGORY`/`INFORMATIONAL`/`NAVIGATIONAL` |
| `score` | LLM | оценка по выдаче (батчи); пишет итог, сырые `competition_*`, веса | `SEARCHED` → `SCORED`/`LOW_SCORED` |
| `analyze` | LLM | разбор ниши; готовый HTML-отчёт на диск + строка `report` | `SCORED` → `ANALYZED` |
| `drill` | оркестратор | гонит поддерево по цепочке до терминалов | см. ниже |

**Порог score:** `> 60` → `SCORED`, `≤ 60` → `LOW_SCORED` (граница 60 — в `LOW_SCORED`).
**`score = null`** (оценить нечего) — узел остаётся `SEARCHED`, ошибка в лог; отдельного терминала
нет (design §2).

**`search` без частичной выдачи** (инвариант design §0): пишем обе выдачи или ни одной. Падение
любого движка → в `serp` ничего не попадает, узел остаётся `TRANSACTIONAL`, ошибка в лог.

**`score` логирует** по каждой фразе сырые входы и итог (`y=…, g=…, веса → score`). Сырые
`competition_yandex/google` и веса лежат в `node` — достаточно, чтобы перекалибровать формулу
позже без повторного прогона LLM.

**`drill`** — последовательность внутри одной задачи: `full_load` → `classify` → по каждому
`TRANSACTIONAL` в поддереве `search` → `score` → по каждому `SCORED` `analyze`. Отдельной
ручки-порога для `analyze` нет: планку задаёт порог `score`, поэтому `drill` доводит до терминала
всё, что смог. Кандидаты
обрабатываются пачками с ограничением ширины. Каждый шаг изолирован: падение → лог, идём дальше.
Идемпотентность: узлы, уже находящиеся в целевом статусе, пропускаются (повторный `drill`
продолжает с текущего места).

**Прогресс и блокировки в `drill`.** Во вкладке Task виден ход по шагам, а не один непрозрачный
`drill` на несколько часов. Пока шаг работает, занят тот узел, с которым он работает; корень
`drill` занят до конца всей операции.

**Групповые операции читаемы в журнале.** `classify` и `score` работают по множеству узлов, а
запись в журнале одна — заголовок должен быть понятен человеку (для `classify` — корень поддерева,
для `score` — фраза и число остальных в пачке).

## 5. Требования к слою данных

Что должно выполняться; как устроено внутри — дело реализации.

- **Схема заводится без миграции — пока можно.** Нужны новые колонки `node` и таблицы `serp`,
  `task`, `report` (design §3). Пайплайн ещё ни разу не работал, поэтому в `node`/`edge` нет ничего
  незаменимого: всё содержимое (18k узлов, 22k связей) восстанавливается из `cache`. Значит вместо
  миграции — расширенная схема плюс пересбор модели из кэша.
- **Неприкосновенны `cache` и `keywords`.** За `cache` платили деньгами, `keywords` — отдельная
  legacy-ветка. Их не пересоздаём и не чистим никогда.
- **Пересбор из кэша даёт то же дерево** — те же узлы и связи, узлы получают дефолтный статус;
  повторный запуск ничего не ломает.
- **С первого прогона пайплайна изменения схемы — только аддитивные.** Как только появятся `score`,
  `verdict`, выдача в `serp`, отчёты и ручные пометки `note`, они станут невосстановимыми (за них
  заплачено LLM, XMLRiver и ручным трудом) — с этого момента пересоздание таблиц недопустимо и нужен
  migration-код.
- **Кэш ответов XMLRiver продолжает работать.** Он уже есть и прямо экономит деньги: повторное
  обращение к той же фразе не должно уходить в сеть — в том числе когда краул идёт параллельно.
- **Краул проходит поддерево до конца:** ниже `FLOOR=50` не углубляется, но сам узел и связь с
  родителем сохраняет; фраза, встречающаяся у нескольких родителей, загружается один раз;
  повторный запуск не дублирует данные и не тратит запросы заново.
- **После краула всё поддерево имеет статус `FULLY_LOADED`** — включая листы ниже `FLOOR`, иначе
  `classify` не сможет их обработать. Смысл статуса: «загружено настолько, насколько разрешает
  `FLOOR`», а не «у каждого узла запрошен свой пул».
- **Ход краула виден в реальном времени** — прогресс уходит в события, а не появляется только по
  завершении.
- **Данные для `classify`** — узлы поддерева со своими прямыми детьми, без дублей (дерево — DAG).
- **Любая смена статуса наблюдаема:** изменение в базе и событие в UI не расходятся.
- **`Fix kind` меняет метку и статус вместе** — промежуточного состояния «новый `kind`, старый
  статус» быть не должно (§6).
- **Целостность при конкурентной работе.** Параллельные операции не портят данные и не смешивают
  записи; частичная запись недопустима (см. `search` в §4).

## 6. Публичные контракты

Три интерфейса: **HTTP-команды** (фронт → сервер), **WebSocket-чтение** (сервер → фронт) и
**граница сервер ↔ task-worker-mcp**. Внутренние функции и структуры сюда не входят.

### 6.1 Команды — HTTP

| Метод и путь | Тело запроса | Ответ |
|---|---|---|
| `POST /api/node/load` | `{phrase}` | `{task_id}` |
| `POST /api/node/full-load` | `{phrase}` | `{task_id}` |
| `POST /api/node/op` | `{phrase, op}`, `op` ∈ `classify\|search\|score\|analyze` | `{task_id}` |
| `POST /api/node/drill` | `{phrase}` | `{task_id}` |
| `POST /api/node/kind` | `{phrase, kind}`, `kind` ∈ `transactional\|informational\|navigational\|category` | `{phrase, kind, status}` — синхронно, без задачи |
| `POST /api/logs/clear` | — | `{ok: true}` |
| `GET /api/estimate?phrase=…` | — | `{nodes, requests}` — нижняя оценка объёма |
| `GET /reports/{id}.html` | — | HTML-файл отчёта (статика) |

Команды, ставящие задачу, отвечают сразу (ack); результат и прогресс приходят по WebSocket.

Ошибки — одинаковым телом `{error, detail}`:
| Код | Когда |
|---|---|
| `404` | фраза неизвестна (нет узла) |
| `409` | узел или его предок заняты другой операцией |
| `422` | операция недопустима из текущего статуса (design §2) или неизвестный `op`/`kind` |

### 6.2 Чтение — WebSocket `/ws`

Клиент → сервер:
| Сообщение | Смысл | Ответ сервера |
|---|---|---|
| `{action:"subscribe"}` | подписка на поток событий | `roots` — список корней-кандидатов, плюс хвост лога (§6 «Правила») |
| `{action:"root", phrase}` | сделать фразу корнем дерева (кнопка «Загрузить корень») | `snapshot` — дерево целиком заменяется |
| `{action:"expand", phrase}` | раскрыть уже загруженное | `children` — дети дописываются к узлу |

`root` и `expand` — **чистое чтение**: данные не подгружают. Если фраза не загружена, поддерево
придёт пустым; подгрузка — только явная команда. Это осознанное CQRS-изменение против нынешнего
авто-фетча в `/api/expand` (он на шаге 3 удаляется).

**Корни-кандидаты** — узлы, ни разу не встречавшиеся как чей-то ребёнок (то есть с которых
начинали исследование), по убыванию частоты, ограниченным числом. Нужны, чтобы при открытии
приложения было что показать до ввода фразы.

Сервер → клиент, конверт `{type, data}`:
| `type` | `data` | Что делает клиент |
|---|---|---|
| `roots` | `{roots: [node]}` — без вложенных `children` | показывает список отправных фраз |
| `snapshot` | `{root, children: [node]}` | **заменяет** дерево целиком |
| `children` | `{parent, children: [node]}` | **дописывает** детей указанному узлу |
| `node` | объект узла (см. ниже) | обновляет один узел на месте |
| `progress` | `{stage, node, done, total}` | показывает ход долгой операции |
| `log` | `{ts, level, stage, node, msg}` | добавляет строку на вкладку Лог |
| `task` | `{id, type, node, status, created_at, started_at, finished_at, error}`; `status` ∈ `QUEUED\|RUNNING\|DONE\|FAILED` | обновляет строку на вкладке Task |
| `report` | `{id, node, title, verdict, verdict_score, link, created_at}` | добавляет отчёт на вкладку «Отчёты» |
| `log_cleared` | `{}` | чистит вкладку Лог |
| `llm_status` | `{online, last_seen_at}` | обновляет индикатор LLM-петли |

**Прогресс против дельт.** Ход краула идёт событием `progress` (агрегированно), а не отдельной
`node`-дельтой на каждый из тысяч узлов — иначе канал затопит. `node`-дельты шлём на значимые
изменения: смена статуса, появление скора, вердикта, блокировки, ошибки. Массовую простановку
`FULLY_LOADED` по поддереву клиент получает как завершение `progress` плюс обновление корня, а не
как поток дельт.

**Смысл `total` в `progress`.** У краула это **не** финальное число: сколько всего узлов в
поддереве, заранее неизвестно — фронтир растёт по ходу. `total` — текущая известная оценка, она
может **увеличиваться** между событиями. Клиент обязан это учитывать (не считать `done/total`
монотонной шкалой и не показывать «осталось N» как обещание); признак завершения — не `done ==
total`, а последнее `progress`-событие операции.

Объект узла (`node` и элементы `children`):
`{phrase, freq, status, kind, score, verdict, verdict_score, report_link, task_id, error, cached, childCount, children?}`
— где `status`/`kind` по design §2–3, `task_id ≠ null` означает «занят операцией», `cached` и
`childCount` питают двухцветный `+`, `report_link` присутствует только при наличии отчёта.

### 6.3 Граница сервер ↔ task-worker-mcp

**Принцип: тяжёлые данные не попадают в контекст диспетчера.** Он только узнаёт, что появилась
работа, и раздаёт её агентам; сами данные (для `classify` — сотня узлов с детьми, для
`score`/`analyze` — полные выдачи) забирает уже агент, который с ними и работает. Поэтому ожидание
возвращает **короткий сигнал**, а payload выдаётся отдельно, по `job_id`.

HTTP-эндпоинты сервера (закрыты секретом `INTERNAL_TOKEN`, обращается к ним только
`task-worker-mcp`):
| Метод и путь | Запрос | Ответ |
|---|---|---|
| `GET /internal/llm/watch` | `?max_jobs=&timeout=` — блокируется, пока джобов нет | `[{job_id, type}]` — только сигнал; пусто — `[]` |
| `GET /internal/llm/job/{job_id}` | — | `{job_id, type, params, prompt}` — полные данные джоба |
| `POST /internal/llm/result` | `{job_id, ok, result?, error?}` | `{accepted}` — `false`, если джоб просрочен или неизвестен |

**CLI-команда** (её Claude запускает в фоне, §7.1) — ожидание работы:
| Команда | Поведение | Вывод |
|---|---|---|
| ожидание джобов | блокируется, пока джобов нет; завершается сразу, как они появились | `[{job_id, type}]` в stdout — короткий список, без данных |

**Инструменты MCP** (их видят Claude Code и его суб-агенты):
| Инструмент | Параметры | Возврат | Кто вызывает |
|---|---|---|---|
| проверка связи | — | доступен ли сервер, сколько джобов ждёт | диспетчер |
| взять джоб | `job_id` | `{job_id, type, params, prompt}` | **агент-исполнитель** |
| вернуть результат | `job_id`, `result` или `error` | `{accepted}` | **агент-исполнитель** |

**Результат отправляет сам агент, а не диспетчер.** Иначе весь смысл короткого сигнала теряется:
`report_html` и прочие объёмные результаты снова пошли бы через контекст диспетчера. Диспетчер
знает только `job_id` и `type`, следит за фактом завершения агента и логирует его падение — данных
джоба он не видит вообще.

**Время жизни джоба.** Выдача сигнала снимает джоб с очереди ожидания (резервирования нет, §3), но
его данные остаются доступными по `job_id` до завершения операции или её таймаута — иначе агент не
сможет их забрать. После этого `взять джоб` и `вернуть результат` по этому `job_id` отвечают как на
неизвестный джоб (`accepted: false`).

Ожидание сделано командой, а не MCP-инструментом, — обоснование в §7.

`params` и ожидаемая форма `result` по каждому типу задачи заданы в **design §6** и в
`prompts/{type}.md` — здесь не дублируются.

### Правила

- **Блокировка на время операции.** Блокировка ставится на узел, с которым работает шаг. Design
  §8 требует запретить действия и в поддереве — это выводит фронт: узел заблокирован, если занят
  он сам или любой его предок. Массово помечать поддерево в БД не нужно.
- **`Fix kind` меняет и статус.** Иначе узел, исправленный из `CATEGORY` в `transactional`,
  залипнет в терминале и пайплайн его не подхватит. Ранее собранные выдача/скор/отчёт не
  удаляются — статус просто откатывается, повторный проход идемпотентен.
- **LLM offline.** Сервер помнит, когда Claude последний раз приходил за джобами. Если больше
  минуты — публикует `llm_status` с `online: false` и пишет предупреждение в лог; при постановке
  LLM-задачи в такой момент в лог идёт отметка, что она провалится по таймауту. Задачи не
  отклоняются — петлю могут поднять в любой момент.
- **Отчёт — исключение из CQRS:** это файл на диске, отдаётся статикой; в БД только ссылка.
  Имя файла и `report.id` — идентификатор `analyze`-**операции** (той, что видна во вкладке Task),
  а не отдельного джоба.
- **Логи** пишутся в `logs/drill.log` всегда, даже без открытого браузера, теми же полями, что
  и в событии `log`, — чтобы LLM/разработчик читал их сам. Ротации нет; при подключении клиент
  получает хвост файла (порядка последних нескольких сотен строк). Очистка — единственная
  операция, стирающая лог.

## 7. task-worker-mcp

Форк скелета `assistant-mcp` (`/home/sergey/Personal/assistant-mcp`): берём структуру пакета,
CLI и идиому stdio-MCP-сервера; выкидываем всё аудио. Добавляем HTTP-клиент к FastAPI.
Зависимости — MCP SDK и HTTP-клиент; **ни Anthropic SDK, ни Redis**.

Что он предоставляет: команду ожидания задач, инструмент возврата результата и проверку связи —
контракты в §6.3.

> **Решение: LLM-сторону делаем по образцу `/home/sergey/Personal/assistant-mcp`** — он уже
> обкатан на этой же идиоме (MCP-сервер + Claude Code в петле). Что берём (детали — §7.1):
> 1. **Ожидание работы — блокирующая CLI-команда, запускаемая Claude в фоне**, а не long-poll
>    MCP-инструмент. У них это `assistant … wait-question`: команда висит и завершается ровно
>    в момент появления работы, харнесс будит Claude по её завершению. Снимает таймауты
>    HTTP-клиента и лимит времени вызова инструмента, задержка нулевая.
> 2. **Отдельная пустая рабочая папка для Claude Code** (у них `root/`) — «намеренно пустая,
>    чтобы Claude Code не отвлекался на код проекта». Диспетчеру исходники не нужны, а из корня
>    репозитория его тянет «помочь» с кодом.
> 3. **Инструкция петли — в `README.md` этой папки**, с явным «выполнить сразу при чтении этого
>    файла», и читается на старте сессии. Инструкции задачам остаются отдельно (у них
>    `prompts/answer.md`, у нас `prompts/{classify,score,analyze}.md`).
> 4. **Регистрация MCP — user-scope** (`claude mcp add -s user …`), плюс в README раздел «если
>    MCP не виден» с командой починки и проверкой `claude mcp list`.
> 5. **Первым шагом петли — проверка связи с MCP** (у них шаг 1: вызвать `status`).

**Промпты живут в `task-worker-mcp/prompts/` и делятся на два вида:**
| Файл | Кто читает | Когда |
|---|---|---|
| `classify.md`, `score.md`, `analyze.md` | **сервер** — подставляет текст в поле `prompt` задачи | при постановке каждой LLM-задачи |
| `orchestrator.md` | **Claude Code** — как инструкция главного цикла | один раз при старте сессии (§7.1) |

Шаблон `templates/report.html` упоминается в `analyze.md` и нужен агенту-аналитику.
*(Открытый вопрос: серверу приходится читать файлы из каталога MCP-пакета. Можно поднять
`prompts/` и `templates/` в корень репозитория — тогда MCP останется чистым транспортом. На
поведение не влияет.)*

### 7.1 Как запускается LLM-петля — по образцу `assistant-mcp`

**Workflow-скрипта нет.** Петля описана прозой; суб-агентов Claude спавнит штатным инструментом
Agent, модель — параметр вызова, который он берёт из инструкции.

Устройство повторяет `assistant-mcp`:

| Элемент | В `assistant-mcp` | У нас |
|---|---|---|
| Рабочая папка Claude | `root/` — пустая, только README | отдельная пустая папка в проекте |
| Инструкция петли | `root/README.md`, «выполнить сразу при чтении» | README этой папки |
| Инструкции задачам | `prompts/answer.md` | `prompts/{classify,score,analyze}.md` (сервер подставляет в задачу) |
| Ожидание работы | фоновая блокирующая команда `assistant … wait-question` | фоновая блокирующая CLI-команда `taskworker` |
| Данные работы | приходят в выводе команды | приходит только `{job_id, type}`; данные забирает агент (§6.3) |
| Возврат результата | — | MCP-инструмент, вызывает **агент**, не диспетчер (§6.3) |
| Регистрация MCP | `claude mcp add -s user` | так же, user-scope |
| Шаг 1 петли | проверить MCP: вызвать `status` | проверить MCP так же |

**Роли разведены:** диспетчер только маршрутизирует, работу делает агент.

- **Диспетчер:** прочитал README → проверил MCP → запустил фоновую команду ожидания → она
  завершилась, харнесс разбудил → на каждый `job_id` из списка поднял отдельного суб-агента с
  моделью по `type` → снова запустил ожидание, не дожидаясь агентов. Падение агента — в лог, петля
  продолжается.
- **Агент-исполнитель:** взял джоб по `job_id` → получил `params` и `prompt` → выполнил → отправил
  результат или ошибку по тому же `job_id`.

Петлю не останавливать, пока не попросят.

**Что задаётся на уровне сессии, а не отдельного агента:** у Agent есть выбор модели
(sonnet/opus/haiku), но **нет** настройки усилий и **нельзя** запросить вариант с 1M-контекстом.
Поэтому сессию сразу поднимают на Opus с 1M и высоким effort, а для `analyze` модель **не
указывают** — суб-агент унаследует режим сессии.

Инструкция диспетчера задаёт: на каждый `job_id` поднимать отдельного суб-агента, всю пачку
параллельно; выбирать модель по `type` (`classify` → Sonnet, `score` → Haiku, `analyze` → не
указывать); в задании агенту велеть **сначала взять джоб по `job_id`**, затем действовать строго по
полученному `prompt` и вернуть результат тем же `job_id`; ошибку возвращать как ошибку — без
ретраев и без выдуманных данных; за следующей пачкой идти сразу.

**Задачные промпты не меняются.** `classify.md`/`score.md`/`analyze.md` остаются инструкциями «как
сделать работу» и про транспорт не знают. Преамбулу «возьми джоб — сделай — верни результат» даёт
диспетчер в задании агенту; так промпты остаются пригодны и для прогона вручную.

Маппинг «тип задачи → модель» живёт только в этой инструкции. *(Заголовки
`classify.md`/`score.md`/`analyze.md` упоминают модели — справочная подпись для человека,
программно она не читается.)*

## 8. Фронтенд

- Чтение переводится с HTTP на WebSocket: подписка, смена корня, раскрытие, применение дельт;
  реконнект с бэкоффом. Команды остаются HTTP.
- Четыре вкладки: Главная (дерево), Лог, Task, Отчёты.
- Кнопки узла — строго по статусу (design §2). Узел заблокирован, если занят он или его предок.
- `Drill`/`Full load` — диалог подтверждения с оценкой объёма (нижняя граница, предупреждаем что
  может вырасти).
- Вкладка Лог — живой поток плюс хвост при открытии, кнопка «Удалить всё».
- Вкладка Отчёты — список с сортировкой по `verdict_score`; `Link` открывает готовый HTML в новой
  вкладке (на узле кнопка видна только при наличии отчёта).
- Индикатор состояния LLM-петли.
- Двухцветные `+` (локальные из пула / реально загруженные) сохраняются.

## 9. Порядок работ

| # | Шаг | Готово, когда |
|---|---|---|
| 1 | Схема + пересбор модели из кэша | новые колонки/таблицы есть, дерево пересобралось и работает как раньше, `cache`/`keywords` целы |
| 2 | Каркас: очередь задач, шина событий, снятие зависших блокировок при старте | сервер стартует, поставленная задача проходит очередь, событие доходит до подписчика |
| 3 | WebSocket-чтение + лог-файл + перевод фронта на WS | дерево грузится и раскрывается по WS, «Загрузить корень» работает, лог пишется в файл |
| 4 | `full_load` + команда + прогресс | краул идёт, статусы капают в дерево в реальном времени, поддерево `FULLY_LOADED` |
| 5 | `search` + `serp` | `TRANSACTIONAL` → `SEARCHED`; падение движка не оставляет частичной выдачи |
| 6 | `task-worker-mcp` + регистрация MCP + внутренние эндпоинты + рабочая папка с инструкцией петли (§7.1) | задача доходит до Claude и возвращается; опоздавший результат не роняет сервер |
| 7 | `classify` + `score` | поддерево размечено по интенту и оценено, статусы обновлены |
| 8 | `analyze` + отчёт + вкладка «Отчёты» | `SCORED` → `ANALYZED`, отчёт открывается и есть в списке |
| 9 | `drill` + диалог подтверждения + блокировки + `Fix kind` | один `Drill` доводит поддерево до терминалов |

Каждый шаг самодостаточен: его результат виден в работающем приложении до перехода к следующему.
План проверки — в `testing-plan.md`, здесь не описывается.

## 10. Принятые решения (можно отменить)

1. **Без Redis и Celery** — всё в одном процессе на asyncio. Нагрузка I/O-bound и
   однопользовательская; брокер не даёт выигрыша. *(Понадобится многомашинность — вернуть
   брокер и вынести воркеры; контракты задач и таблица `task` это переживут.)*
2. **Долгие LLM-операции не блокируют конвейер** — идущие `analyze` не мешают работать остальным
   узлам.
3. **Забор LLM-задач без резервирования и ретраев;** страховка — таймаут. Соответствует design §0.
4. **Крупные операции режутся на части** (classify — чанки, score — батчи), но остаются одной
   строкой `task`.
5. **Блокировка ставится на рабочий узел;** запрет по поддереву выводит фронт.
6. **`Fix kind` синхронно правит статус;** собранные данные не удаляются.
7. **Промпты — в `task-worker-mcp/prompts/`:** задачные (`classify`/`score`/`analyze`) подставляет
   в задачу сервер, `orchestrator.md` читает Claude Code при старте.
8. **Чтение по WS не мутирует;** подгрузка — только явная команда.
9. **Отчёт — готовый HTML-файл,** отдаётся статикой; в БД только ссылка.
10. **`drill` — оркестратор внутри одной задачи,** шаги идут последовательно и изолированно.
11. **Ожидание работы — фоновая блокирующая команда, а не long-poll MCP-инструмент** (по образцу
    `assistant-mcp`, §7): нулевая задержка и никаких таймаутов вызова инструмента.
12. **Рестарт не оставляет заблокированных узлов** — незавершённые задачи считаются проваленными.
13. **Внутренние эндпоинты закрыты общим секретом.**
