# Tech design: архитектура и контракты

> **Область документа.** Это технический дизайн, а не код.
>
> **Здесь:** архитектура и верхнеуровневые решения; **все публичные методы и их контракты** (§6) —
> HTTP-эндпоинты, сообщения WebSocket, внутренние ручки, файловые контракты: что принимают, что
> возвращают, какие ошибки; требования, проверяемые снаружи.
>
> **Не здесь:** код и псевдокод, сигнатуры внутренних функций, внутренние структуры данных и
> имена переменных, конфиги и команды запуска.
>
> Граница: **публичный интерфейс — да, его внутреннее устройство — нет.**

Пара к `design-plan.md`: **design = ЧТО** (поведение, слои, модель), **этот док = КАК**
(архитектура и контракты). Где расходятся — прав `design-plan.md`. Проверка — `testing-plan.md`.

## 1. Карта

```
semcore.db          оплаченные данные (cache) + производное дерево (node/edge) + serp/task
wscore.py           слой данных: схема, нормализация, фетч Вордстата, краул, проекции, инварианты
tasks.py            операции: load, full_load, needs_build, needs_analyze (+ наследие, §8)
needs_layer.py      второй слой: чтение и запись файлов дерева потребностей, проекции для API
server.py           FastAPI: команды (HTTP), чтение (WS), очередь задач, шина событий, статика
frontend/           React: дерево запросов, дерево потребностей, лог, задачи, отчёты
task-worker-mcp/    мост к LLM-агенту (MCP stdio + CLI), промпты и лаборатория промптов (§7)
logs/needs-lab/     второй слой файлами
reports/            HTML-отчёты по работам
```

Единственное направление зависимостей: `server.py` → `tasks.py` → (`wscore.py`, `needs_layer.py`).
Рантайм (соединение с БД, шина, очередь, семафоры, обмен с LLM) создаётся в `server.py` и приходит
в операции объектом контекста — чтобы не было кольца импортов.

Три процесса:

```
┌──────────┐  команды (HTTP)   ┌────────────────────────┐   сигнал о джобах    ┌──────────────┐
│  браузер │ ────────────────► │  FastAPI: очередь,     │ ◄──────────────────► │ LLM-агент    │
│          │ ◄──── WS ──────── │  шина, операции        │  данные и результат  │ (Claude Code)│
└──────────┘   чтение дерева   └────────────────────────┘                      └──────────────┘
                                    │            │
                              semcore.db    logs/needs-lab + reports
```

## 2. Процесс

**Один процесс, один event loop, брокера нет.** Очередь задач — `asyncio.Queue`, шина событий — в
памяти, ожидание результата LLM — future.

Почему так: нагрузка I/O-bound (сеть XMLRiver и ожидание агента) и однопользовательская на
localhost. Брокер добавил бы инфраструктуру и точку отказа, не решая ни одной задачи.

Правила, которые из этого следуют:

- **соединение с БД используется только из loop-треда.** Блокирующая сеть уходит в executor;
- **ожидание LLM не блокирует разбор очереди** — каждая задача своя корутина;
- операция ставится командой, узел получает `task_id`, ручка сразу возвращает ack;
- на старте сервер снимает зависшие блокировки (процесс мог упасть) и **починяет инвариант
  `FULLY_LOADED`**, записывая в лог, сколько исправил.

Ограничители: одновременных обращений к XMLRiver вне краула — 4; одновременных краулов — 1 (внутри
каждого свои воркеры); очередь событий на клиента ограничена — переполнилась, значит клиент
слишком медленный.

## 3. Обмен с LLM

Система **не вызывает модель сама**. Работу забирает внешний агент (сессия Claude Code), и роли
разведены так, чтобы тяжёлые данные не попадали в лишний контекст:

- **диспетчер** узнаёт, что появились джобы (короткий сигнал `{job_id, type}`), и раздаёт их
  агентам-исполнителям. Данных задач не видит;
- **агент-исполнитель** забирает данные своего джоба, делает работу, возвращает результат.

Ожидание работы — не инструмент, а блокирующая команда: она висит, пока джобов нет, и завершается
ровно в момент их появления. Так петля не крутит поллинг и видна серверу живой.

**Индикатор «LLM: офлайн»** — сервер не видел ожидания дольше порога (4 минуты). Порог терпимый
намеренно: пока диспетчер раздаёт агентов, висящего ожидания нет, и при коротком пороге индикатор
мигал бы.

**Таймаут операции — единственная страховка.** Резервирования джобов и ретраев нет: не пришёл
результат — задача `FAILED`, данные не тронуты. Опоздавший ответ отбрасывается с предупреждением в
лог.

**Джоб = часть операции**, `job_id = "{task_id}:{n}"`. Обе LLM-операции одноджобовые: и сборка
ветки, и разбор работы требуют цельного контекста, дробить их нельзя.

Модель под тип работы задаётся **промптом петли** (`prompts/orchestrator.md`), а не конфигом
сервера: сервер не знает и не должен знать, какой моделью исполняется джоб.

## 4. Слои данных

**Первый слой — БД.** `cache` оплачен, `node`/`edge` пересобираются из него, если схема старая.
Поэтому **любая новая колонка добавляется через `ALTER TABLE`**, а не через пересборку: маркером
«схема новая» служит наличие колонки `status`. Прецедент: колонка, добавленная в список «новых»,
заставила пересобрать дерево и стёрла результаты работы LLM.

**Выдача — тоже оплаченный кэш**, ключ «фраза + движок». Одна точка покупки на всю систему: что
купил один шаг, бесплатно для другого. Инвариант «обе выдачи или ни одной» проверяется при записи.

**Второй слой — файлы** (`design-plan §5`). Каталог сборки хранит **вход рядом с результатом**: без
входа дерево нельзя ни проверить на полноту, ни показать частоты фраз. Разборы работ — отдельными
файлами в подкаталоге, поэтому добавление разбора не переписывает сборку.

**Копия БД для тестов делается через backup, а не `cp`:** база в режиме WAL, свежие коммиты лежат в
`-wal`, и файловая копия без него — устаревший снимок.

## 5. Требования к операциям

Не сигнатуры, а то, что операция обязана обеспечить.

**Общее:**

- одна операция — одна строка `task` (дробление на джобы — деталь транспорта);
- **статус задачи честен по факту работы:** пока джоб не забран исполнителем, задача стоит в
  `WAITING`, а не в `RUNNING`. Переводит её брокер — в момент выдачи данных джоба, потому что
  сигнал диспетчеру ещё не значит, что кто-то работает;
- переходы статусов строго по `design-plan §2`; недопустимый переход — отказ **до** постановки
  задачи;
- любой отказ → `task FAILED`, ошибка в лог, **данные остаются как были**;
- узел и его поддерево заблокированы на время операции; блокировка снимается всегда, в том числе
  при падении. Блокировка выводится по предкам, поэтому занятый предок блокирует поддерево;
- в БД пишем только из loop-треда.

**`load`** — пул фразы на уровень; повторный вызов не тратит фетчей (кэш).

**`full_load`** — идемпотентен: уже запрошенные узлы не перезапрашиваются; упавший фетч не
откатывает остальное поддерево, а пишет ошибку на свой узел. Прогресс публикуется не чаще, чем раз
в полсекунды, число узловых дельт за операцию ограничено — иначе широкая ветка забьёт канал.

**`needs_build`** — единица работы **ветка**; ответ принимается только целиком прошедшим проверку
полноты (каждая входная фраза ровно один раз); результат сохраняется файлами; **модель первого слоя
не меняется**. Диапазон входа — `FLOOR … 30000`: голова выше порога в сборку не идёт, но сам корень
ветки включается всегда, иначе непонятно, по чему собрано.

**`needs_analyze`** — сначала гарантирует выдачу по самым частотным формулировкам работы (из кэша
либо покупкой), затем один джоб Opus; принимает ответ только с валидным вердиктом, `verdict_score`
и непустым HTML; сохраняет отчёт файлом и запись разбора рядом с деревом. Два разбора одной работы
одновременно не запускаются. Узел первого слоя не трогается, поэтому и блокировать его незачем —
строка задачи подписана **именем работы**.

## 6. Контракты

### 6.1 Команды — HTTP POST

Тело — JSON, ответ — `{"task_id": "<hex>"}` (ack, операция фоновая).
Ошибки одной формы: `{"error": "<код>", "detail": "<человеку>"}`.

| Метод | Тело | Смысл | Коды |
|---|---|---|---|
| `POST /api/node/load` | `{phrase}` | пул фразы на 1 уровень | 404 нет узла · 409 занят узел или предок · 422 недопустимо из статуса |
| `POST /api/node/full-load` | `{phrase}` | краул поддерева | те же |
| `POST /api/needs/build` | `{phrase}` | собрать дерево потребностей по ветке | 404 · 409 · 422 (не `FULLY_LOADED`) |
| `POST /api/needs/analyze` | `{tree_id, work}` | разбор работы: выдача + Opus | 404 нет дерева или работы · 409 разбор уже идёт · 422 в работе нет фраз |
| `POST /api/logs/clear` | `{}` | очистить представление и файл лога | 422 файл не очищается |

Коды: `not_found` (404), `conflict` (409), `invalid` (422), `unauthorized` (401).
Необязательный `X-Caller` попадает в лог — видно, кто дёрнул операцию.

### 6.2 Чтение первого слоя — WebSocket `/ws`

Клиент → сервер:

| Действие | Смысл |
|---|---|
| `{action: "subscribe"}` | подписка: корни-кандидаты, хвост лога, накопленные задачи, состояние LLM |
| `{action: "root", phrase}` | заменить дерево на поддерево этой фразы |
| `{action: "expand", phrase}` | проекция реальных детей фразы |

**Все три — чистое чтение:** ничего не догружают и не пишут.

Сервер → клиент, конверт `{type, data}`:

| `type` | `data` |
|---|---|
| `roots` | `{roots: [узел, …]}` — фразы, ни разу не встречавшиеся ребёнком |
| `snapshot` | `{root: узел \| null, missing?: фраза, children: [узел, …]}` — **заменяет** дерево целиком; `root: null` = такой фразы в дереве нет |
| `children` | `{parent, children: [узел, …]}` — дописывает детей |
| `node` | дельта узла `{phrase, …изменившиеся поля}` — обновляет **все** вхождения фразы (DAG) |
| `progress` | `{stage, node, done, total}`; `total` может расти по ходу |
| `log` | строка лога или массив (хвост при подписке) |
| `task` | строка задачи или массив (накопленные при подписке); `status` = `QUEUED\|WAITING\|RUNNING\|DONE\|FAILED` |
| `log_cleared` | `{}` |
| `llm_status` | `{online, last_seen_at}` |

**Объект узла:** `{phrase, freq, status, task_id, error, cached, childCount, children?}`.
`cached` — свой пул запрошен (есть более глубокие уточнения); `childCount` — сколько уточнений в
пуле; `children` — **локальные** дети из пула родителя, зависят от контекста родителя и приходят
вместе с ним. Реальные дети — только событием `children`. `task_id ≠ null` — узел занят.

### 6.3 Чтение второго слоя — HTTP GET

Второй слой читается по HTTP, а не по WS: он живёт файлами и обновляется не потоком событий, а
завершением операции. Прецедент — `GET /api/estimate`.

| Метод | Ответ |
|---|---|
| `GET /api/needs/trees` | `{trees: [строка, …]}` — по одной на дерево |
| `GET /api/needs/tree/{tree_id}` | дерево целиком |
| `GET /api/needs/reports` | `{reports: [разбор, …]}` — все разборы работ, лучшие сверху |
| `GET /api/estimate?phrase=` | `{nodes, requests}` — нижняя оценка объёма `full_load`; 404 если узла нет |

**Строка таблицы деревьев:** `{id, root, root_freq, condition, works, segments, phrases, excluded,
gaps, occupied, needs_serp, analyzed, created_at, error}`. `error ≠ null` — файл дерева не читается;
строка всё равно отдаётся, чтобы битая сборка не роняла список.

**Дерево:** `{id, root, root_freq, condition, created_at, counts, works, excluded}`.

**Работа:** `{name, top_freq, phrase_count, occupied_by, unclear, gap_candidate, needs_serp,
serp_question, why, phrases: [{phrase, freq}], segments: [{name, gap_candidate, why, phrases}],
analysis}`.

**Разбор (`analysis`):** `{verdict, verdict_score, confidence, report_link, created_at, searched}`
либо `null`, если работу ещё не разбирали. `searched` — по каким фразам куплена выдача.

**Исключённая фраза:** `{phrase, freq, why, note}`.

`tree_id` **не склеивается с путём**: это ключ уже найденного набора файлов. Иначе строка из
запроса читала бы произвольный файл.

### 6.4 Внутренние ручки (только для LLM-агента)

Требуют `X-Internal-Token`; `X-Caller` пишется в лог, чтобы отличать диспетчера от исполнителя.

| Метод | Кто зовёт | Смысл |
|---|---|---|
| `GET /internal/llm/watch?max_jobs=&timeout=` | диспетчер | блокируется, пока джобов нет; отдаёт **только сигнал** `[{job_id, type}]` |
| `GET /internal/llm/job/{job_id}` | исполнитель | полные данные `{job_id, type, params, prompt}`; 404 если просрочен |
| `POST /internal/llm/result` | исполнитель | `{job_id, ok, result?, error?}` → `{accepted}`; `false` = джоб просрочен |
| `POST /internal/test/enqueue-job` | тесты | положить джоб без операции — проверять транспорт отдельно |

`prompt` инлайнится в джоб: агент работает строго по нему и **в репозиторий за промптами не
ходит**.

### 6.5 Файлы второго слоя

Публичный контракт, потому что их пишет и читает не только сервер (§7).

```
logs/needs-lab/<tree_id>/params.json          {root, root_freq, min_freq, max_freq,
                                               subtree_total, nodes: [{phrase, freq, children}]}
logs/needs-lab/<tree_id>/accepted.json        {condition, works: [...], excluded: [...]}
logs/needs-lab/<tree_id>/analysis/<slug>.json {work, verdict, verdict_score, confidence,
                                               report_link, task_id, created_at, searched, phrases}
reports/<id>.html                             отчёт по работе
```

Раскладка распознаётся двумя способами: **каталог сборки** (как выше) и **просто json-файл**,
положенный в папку руками — тогда частот у фраз нет, но дерево показывается.

### 6.6 Статика

`/` — собранный фронт (`frontend/dist`), `/reports/*` — готовые HTML-отчёты.

## 7. Лаборатория промптов (`task-worker-mcp`)

Пакет решает две задачи.

**Мост к агенту в бою:** MCP-сервер stdio с инструментами `status` (диспетчер), `get_job` и
`submit_result` (исполнитель) плюс блокирующая команда ожидания работы. Регистрация — user-scope,
не файлом в репозитории.

**Лаборатория:** прогон промпта на реальных данных **без конвейера**. Джоб лежит каталогом
локально, а интерфейс агента ровно тот же, что в бою (`get_job` / `submit_result` по префиксу
локального `job_id`) — проверяем то, что потом и поедет.

Решения лаборатории, которые стоит знать:

- **вход и ответ — файлами, не значениями.** Ответ сборки — десятки тысяч символов; через вызов
  инструмента он обрезается по длине молча, давая валидный JSON без хвоста. **Путь объявляет
  обвязка, не модель:** путь из ответа модели — это чтение произвольного файла по её указке.
- **хэш входа хранится в джобе** — «два прогона получили одно и то же» становится записанным
  фактом, а не утверждением.
- **ответ проверяется на приёме**: не прошёл — не принят, возвращается машиночитаемый список
  проблем (какие фразы потеряны, каких нет во входе, где не сходятся счётчики), попытка
  складывается для разбора.
- **сравнение сборок** — не по названиям работ (они у модели свои), а по **разбиению**: для каждой
  пары опорных фраз совпадает ли ответ «в одной работе или в разных». Отдельно — совпал ли выброс
  и изолированы ли узкие потребности. Эталон — ручная сборка в `reference/`.

Измеренная воспроизводимость сборки на одинаковом входе — **99.1%** по парам фраз (34 716 пар).

## 8. Наследие в коде

Честно, чтобы не искать в недоумении.

В `tasks.py` и `server.py` живут операции и ручки узлового пайплайна (`classify`, `search`, `score`,
`analyze`, `drill`, `POST /api/node/op`, `/api/node/drill`, `/api/node/kind`), в схеме — их колонки
и таблица `report`, в промптах — `classify.md`, `score.md`, `analyze.md`. Из интерфейса они
недостижимы: выводы делает второй слой, где единица — работа. Оставлены намеренно — удаление
тронуло бы схему, а схема развивается аддитивно (§4).

Оттуда же единственное событие WS вне таблицы §6.2 — **`report`** (его публикует узловой `analyze`).
Клиент его игнорирует: неизвестные типы событий по контракту пропускаются, и это ровно тот случай,
ради которого правило заведено.

Действующие промпты: **`needs.md`** (сборка ветки) и **`analyze_work.md`** (разбор работы), плюс
`orchestrator.md` — инструкция петле исполнения.
