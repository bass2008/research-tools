# Tech design: архитектура и контракты

> **Область документа.** Это технический дизайн, а не код.
>
> **Здесь:** архитектура и верхнеуровневые решения; **все публичные методы и их контракты** (§6) —
> HTTP-эндпоинты, сообщения WebSocket, внутренние ручки, файловые контракты: что принимают, что
> возвращают, какие ошибки; требования, проверяемые снаружи.
>
> **Не здесь:** код и псевдокод, сигнатуры внутренних функций, внутренние структуры данных и
> имена переменных, конфиги и команды запуска.
>
> Граница: **публичный интерфейс — да, его внутреннее устройство — нет.**

Пара к `design-plan.md`: **design = ЧТО** (поведение, слои, модель), **этот док = КАК**
(архитектура и контракты). Где расходятся — прав `design-plan.md`. Проверка — `testing-plan.md`.

## 1. Карта

```
semcore.db          оплаченные данные (cache, serp, history) + производное дерево (node/edge)
                    + probe (что куплено под замер) + task
wscore.py           слой данных: схема, нормализация, фетч Вордстата, краул, проекции, инварианты
tasks.py            операции: load, full_load, stopwords_scan, needs_build, needs_refine,
                    needs_rank, три разбора
                    (needs_analyze / needs_analyze_adv / needs_analyze_product),
                    needs_season, needs_adjacent, needs_dump (+ наследие, §8)
needs_layer.py      второй слой: чтение и запись файлов дерева потребностей, проекции для API
server.py           FastAPI: команды (HTTP), чтение (WS), очередь задач, шина событий, статика
frontend/           React: дерево запросов, дерево потребностей, лог, задачи, отчёты
task-worker-mcp/    мост к LLM-агенту (MCP stdio + CLI), промпты и лаборатория промптов (§7)
logs/needs-lab/     второй слой файлами
reports/            HTML-отчёты по работам
```

Единственное направление зависимостей: `server.py` → `tasks.py` → (`wscore.py`, `needs_layer.py`).
Рантайм (соединение с БД, шина, очередь, семафоры, обмен с LLM) создаётся в `server.py` и приходит
в операции объектом контекста — чтобы не было кольца импортов.

Три процесса:

```
┌──────────┐  команды (HTTP)   ┌────────────────────────┐   сигнал о джобах    ┌──────────────┐
│  браузер │ ────────────────► │  FastAPI: очередь,     │ ◄──────────────────► │ LLM-агент    │
│          │ ◄──── WS ──────── │  шина, операции        │  данные и результат  │ (Claude Code)│
└──────────┘   чтение дерева   └────────────────────────┘                      └──────────────┘
                                    │            │
                              semcore.db    logs/needs-lab + reports
```

## 2. Процесс

**Один процесс, один event loop, брокера нет.** Очередь задач — `asyncio.Queue`, шина событий — в
памяти, ожидание результата LLM — future.

Почему так: нагрузка I/O-bound (сеть XMLRiver и ожидание агента) и однопользовательская на
localhost. Брокер добавил бы инфраструктуру и точку отказа, не решая ни одной задачи.

Правила, которые из этого следуют:

- **соединение с БД используется только из loop-треда.** Блокирующая сеть уходит в executor;
- **ожидание LLM не блокирует разбор очереди** — каждая задача своя корутина;
- операция ставится командой, узел получает `task_id`, ручка сразу возвращает ack;
- на старте сервер снимает зависшие блокировки (процесс мог упасть) и **починяет инвариант
  `FULLY_LOADED`**, записывая в лог, сколько исправил.

Ограничители: одновременных обращений к XMLRiver вне краула — 4; одновременных краулов — 1 (внутри
каждого свои воркеры); очередь событий на клиента ограничена — переполнилась, значит клиент
слишком медленный.

## 3. Обмен с LLM

Система **не вызывает модель сама**. Работу забирает внешний агент (сессия Claude Code), и роли
разведены так, чтобы тяжёлые данные не попадали в лишний контекст:

- **диспетчер** узнаёт, что появились джобы (короткий сигнал `{job_id, type}`), и раздаёт их
  агентам-исполнителям. Данных задач не видит;
- **агент-исполнитель** забирает данные своего джоба, делает работу, возвращает результат.

Ожидание работы — не инструмент, а блокирующая команда: она висит, пока джобов нет, и завершается
ровно в момент их появления. Так петля не крутит поллинг и видна серверу живой.

**Индикатор «LLM: офлайн»** — сервер не видел ожидания дольше порога (4 минуты). Порог терпимый
намеренно: пока диспетчер раздаёт агентов, висящего ожидания нет, и при коротком пороге индикатор
мигал бы.

**Таймаут операции — единственная страховка.** Резервирования джобов и ретраев нет: не пришёл
результат — задача `FAILED`, данные не тронуты. Опоздавший ответ отбрасывается с предупреждением в
лог.

**Джоб = часть операции**, `job_id = "{task_id}:{n}"`. Сборка ветки, разбор работы и сезонность
одноджобовые — им нужен цельный контекст. Смежные ключи — исключение: там джобы идут **по кругу**
(`:0` предложить корни → система их измеряет → `:1` оценить измеренное и добрать пропущенный →
`:2`), потому что второй вопрос к модели зависит от того, что показали замеры.

Модель под тип работы задаётся **промптом петли** (`prompts/orchestrator.md`), а не конфигом
сервера: сервер не знает и не должен знать, какой моделью исполняется джоб.

## 3a. Два семейства моделей

Джобы разбора помечены `model_family` — `claude` или `codex`, и это **жёсткая привязка
исполнителя**: `watch` отдаёт петле только её джобы, поэтому задача на выключенное семейство
висит в `WAITING` до таймаута (снимается кнопкой отмены). Claude-петля — сессия Claude Code
(`taskworker wait-jobs`), Codex-петля — отдельный процесс-диспетчер (`taskworker.codex_dispatch`),
который сам поднимает свой `wait-jobs --model-family codex`.

Раздельно: артефакты разборов (у каждого свой `model_family`), оценки в строке работы, второй
проход классификации и рейтинг. Общее: дерево запросов, принятая классификация, купленная выдача,
сезонность и смежные ключи.

**Предыдущий отчёт читается любой.** Разбор получает последний артефакт каждого вида независимо от
автора, а автор приезжает в поле `by`: свежесть важнее авторства, а расхождение двух моделей —
самое полезное, что видит человек. Раньше цепочка была замкнута внутри семейства, и «Продукт» на
Claude падал, когда «Ниша» была сделана Codex.

## 4. Слои данных

**Первый слой — БД.** `cache` оплачен, `node`/`edge` пересобираются из него, если схема старая.
Поэтому **любая новая колонка добавляется через `ALTER TABLE`**, а не через пересборку: маркером
«схема новая» служит наличие колонки `status`. Прецедент: колонка, добавленная в список «новых»,
заставила пересобрать дерево и стёрла результаты работы LLM.

**Выдача — тоже оплаченный кэш**, ключ «фраза + движок». Одна точка покупки на всю систему: что
купил один шаг, бесплатно для другого. Инвариант «обе выдачи или ни одной» проверяется при записи.

**История частоты и замеры — тоже кэш.** `history` (ряд по месяцам, ключ «фраза») оплачена так же,
как `serp`. Пулы, купленные под замер смежных ключей, попадают в общий `cache`, но помечаются в
`probe`: пересборка `node` из `cache` их пропускает, иначе замер второго слоя превращается в факты
первого. Пометка одноразово восстанавливается по признаку «запрос в кэше есть, узла нет» — краул
пишет узел сразу после фетча, поэтому осиротеть может только покупка второго слоя.

**Второй слой — файлы** (`design-plan §5`). Каталог сборки хранит **вход рядом с результатом**: без
входа дерево нельзя ни проверить на полноту, ни показать частоты фраз. Артефакты работ — отдельными
файлами в подкаталоге, **по файлу на прогон**, поэтому ни новый разбор, ни повтор не переписывают
ни сборку, ни прошлый результат.

**Копия БД для тестов делается через backup, а не `cp`:** база в режиме WAL, свежие коммиты лежат в
`-wal`, и файловая копия без него — устаревший снимок.

## 5. Требования к операциям

Не сигнатуры, а то, что операция обязана обеспечить.

**Общее:**

- одна операция — одна строка `task` (дробление на джобы — деталь транспорта);
- **статус задачи честен по факту работы:** пока джоб не забран исполнителем, задача стоит в
  `WAITING`, а не в `RUNNING`. Переводит её брокер — в момент выдачи данных джоба, потому что
  сигнал диспетчеру ещё не значит, что кто-то работает;
- переходы статусов строго по `design-plan §2`; недопустимый переход — отказ **до** постановки
  задачи;
- любой отказ → `task FAILED`, ошибка в лог, **данные остаются как были**;
- узел и его поддерево заблокированы на время операции; блокировка снимается всегда, в том числе
  при падении. Блокировка выводится по предкам, поэтому занятый предок блокирует поддерево;
- в БД пишем только из loop-треда.

**добавление корня** — единственная команда, которая создаёт узел из строки запроса, а не из
пула родителя. Поэтому она и отделена от `load`: та работает по уже существующему узлу, иначе
опечатка превращалась бы в узел с платными кнопками. Новый корень ни от кого не зависит — рёбер
к нему нет, дерево запросов это лес, а не одно дерево.

**`load`** — пул фразы на уровень; повторный вызов не тратит фетчей (кэш).

**`full_load`** — идемпотентен: уже запрошенные узлы не перезапрашиваются; упавший фетч не
откатывает остальное поддерево, а пишет ошибку на свой узел. Прогресс публикуется не чаще, чем раз
в полсекунды, число узловых дельт за операцию ограничено — иначе широкая ветка забьёт канал.

**`stopwords_scan`** — отдаёт модели только слова, которых нет в сохранённых исключениях, и
принимает обратно только слова из своего же входа. Ничего не сохраняет: результат живёт в
`task.result` как предложение, пока человек не перенесёт слова в список. Отдельного хранилища у
предложения нет намеренно — ценность только у принятого.

**`needs_build`** — единица работы **ветка**; ответ принимается только целиком прошедшим строгую
проверку полноты и счётчиков (каждая входная фраза ровно один раз); результат сохраняется файлами;
**модель первого слоя не меняется**. `score`, `occupied_by`, щели и любые продуктовые поля в
классификации запрещены. Диапазон входа — `FLOOR … 30000`: голова выше порога в сборку не идёт,
но сам корень ветки включается всегда, иначе непонятно, по чему собрано.

**`needs_refine`** — второй проход всей классификации на Opus/Sol `xhigh`. Ответ проходит ту же
строгую проверку, заменяет `accepted.json` атомарно и увеличивает `_revision`; прежняя версия и
метаданные прохода остаются в `revisions/`.

**`needs_rank`** — один Opus/Sol `xhigh`-джоб по принятой классификации. Модель возвращает тип
намерения, шесть факторов, конкретную форму продукта, ограничение и точные опорные фразы. Сервер
проверяет полный набор работ, диапазоны и схему, сам пересчитывает score по весам и intent-cap.
Рейтинг сохраняется отдельно в `rankings/` с `tree_revision`; выдача и конкуренты не участвуют.

**`needs_analyze`** — сначала гарантирует выдачу по самым частотным формулировкам работы (из кэша
либо покупкой), затем один джоб Opus; принимает ответ только с валидным вердиктом, `verdict_score`
и непустым HTML; сохраняет отчёт файлом и артефакт рядом с деревом. На вход обязан отдать
**накопленное по работе** (сезонность, смежные ключи, прошлые вердикты), а в сохранённый отчёт —
дописать блок «Входные данные»: перечень того, что пришло и чего не было. Печатает его сервер,
потому что отчёт модели — не свидетельство о её собственном входе.

**`needs_analyze_adv`** — тот же вход, что у `needs_analyze` (общий сборщик), другой промпт и
другой приёмник: ответ без списка функций не принимается, вердикт берётся по лучшей функции.
Выдача идёт из кэша, поэтому по уже разобранной работе операция не тратит платных запросов.

**`needs_analyze_product`** — тот же сборщик входа плюс **тексты чужих отчётов**: к выдаче
добавляются последние артефакты `analyze` и `analyze_adv`, причём их HTML читается с диска и
кладётся в джоб очищенным текстом (модель обязана видеть выводы предшественников целиком, а не
только их оценки). Без единого предыдущего разбора операция отказывает. Приёмник требует `spec`
с непустыми `product`, `price`, `why_pay` и `forecast` — прогноз продаж по месяцам 1/2/3/6 с
допущениями, у каждого из которых указан источник, потолком, бюджетом, окупаемостью и
`invest_case`. Прогноз из одних нулей отклоняется: «не взлетает» выражается вердиктом, а не
пустыми числами. В артефакт кладутся все три оценки (`scores`) и прогноз, чтобы расхождение
разборов и цена вопроса были видны в строке работы.

**`needs_model_test`** — минутный тест связи с семейством: один джоб `model_test`, модель обязана
вернуть своё имя, и несовпадение с ожидаемым семейством — отказ. Нужен, чтобы отличать «петля не
на связи» от «петля есть, но отвечает не та модель».

**`needs_dump`** — единственная операция второго слоя **без LLM**: выбирает пять углов, докупает
по ним выдачу, качает страницы в два приёма (HTTP, при отказе или пустоте — headless-браузер) и
раскладывает по `reports/<работа>/<движок>/<запрос>/`. Недоступный угол пропускается, пустая
выгрузка — отказ.

**`needs_season`** — один джоб; ряд и сводку считает система, модель только толкует. Ряд просят у
источника **отдельным типом запроса** (история по месяцам), и у него две ловушки: будущая дата
конца отвергается, а без явного периода приходит три точки вместо двадцати четырёх.

**`needs_adjacent`** — многоджобовая (см. §3); измеряет пулы предложенных корней и **помечает их
как замер** (`probe`), иначе они уедут в дерево запросов при ближайшей пересборке.

Три действия второго слоя не трогают узел первого слоя, поэтому и блокировать его незачем — строка
задачи подписана **именем работы**. Занятость считается по паре «работа + действие»: повтор
запрещён, разные действия по одной работе идут параллельно.

## 6. Контракты

### 6.1 Команды — HTTP POST

Тело — JSON, ответ — `{"task_id": "<hex>"}` (ack, операция фоновая).
Ошибки одной формы: `{"error": "<код>", "detail": "<человеку>"}`.

| Метод | Тело | Смысл | Коды |
|---|---|---|---|
| `POST /api/node/root` | `{phrase}` | завести корень и загрузить его пул | 409 фраза уже в дереве · 422 пустая фраза или фраза под стоп-словом |
| `POST /api/node/load` | `{phrase}` | пул фразы на 1 уровень | 404 нет узла · 409 занят узел или предок · 422 недопустимо из статуса |
| `POST /api/node/full-load` | `{phrase}` | краул поддерева | те же |
| `POST /api/stopwords/scan` | `{phrase}` | разобрать слова ветки на исключения (предложение) | 404 нет узла · 409 узел занят |
| `POST /api/stopwords` | `{words: [{word, kind}]}` | принять слова в исключения | 422 пустое слово или неизвестная категория |
| `DELETE /api/stopwords` | `{words: [слово, …]}` | убрать слова из исключений | — |
| `POST /api/needs/build` | `{phrase}` | собрать дерево потребностей по ветке | 404 · 409 · 422 (не `FULLY_LOADED`) |
| `POST /api/needs/refine` | `{tree_id, model_family}` | второй проход принятой классификации всего дерева | 404 · 409 дерево занято · 422 нет исходного `params.json` |
| `POST /api/needs/rank` | `{tree_id, model_family}` | продуктовый шанс по всем работам без выдачи и конкурентов | 404 · 409 дерево занято · 422 нет исходника/работ |
| `POST /api/needs/{action}` | `{tree_id, work}` | действие по работе. Три разбора воронкой: `analyze` — «Ниша» (перехват трафика, выдача + Opus), `analyze_adv` — «Функции» (за что платят), `product` — «Продукт» (спецификация по выдаче и двум отчётам). Плюс `season` (история частоты), `adjacent` (смежные ключи), `dump` (выгрузка топ-10 страницами) | 404 нет дерева, работы или неизвестное действие · 409 это действие по работе уже идёт · 422 в работе нет фраз |
| `POST /api/needs/favorite` | `{tree_id, work, favorite}` | ручной лайк работы: отметка человека, на классификацию и рейтинг не влияет | 404 нет дерева или работы |
| `POST /api/logs/clear` | `{}` | очистить представление и файл лога | 422 файл не очищается |
| `POST /api/tasks/clear` | `{}` | удалить журнал задач целиком | — |
| `POST /api/task/{id}/retry` | `{}` | повторить **упавшую** задачу: вызывается та же ручка с теми же параметрами, поэтому проверки статуса и занятости работают как при первом запуске; старая строка остаётся | 404 нет задачи · 409 задача не `FAILED` · 422 операция не поддержана |
| `POST /api/task/{id}/cancel` | `{}` | снять задачу в `WAITING` — джоб лежит в очереди, работы не идёт. `RUNNING` не отменяем: агент вернёт результат, которому некуда лечь | 404 · 409 статус не `WAITING` |

Коды: `not_found` (404), `conflict` (409), `invalid` (422), `unauthorized` (401).
Необязательный `X-Caller` попадает в лог — видно, кто дёрнул операцию.

### 6.2 Чтение первого слоя — WebSocket `/ws`

Клиент → сервер:

| Действие | Смысл |
|---|---|
| `{action: "subscribe"}` | подписка: корни-кандидаты, хвост лога, накопленные задачи, состояние LLM |
| `{action: "root", phrase}` | заменить дерево на поддерево этой фразы |
| `{action: "expand", phrase}` | проекция реальных детей фразы |

**Все три — чистое чтение:** ничего не догружают и не пишут.

Сервер → клиент, конверт `{type, data}`:

| `type` | `data` |
|---|---|
| `roots` | `{roots: [узел, …]}` — фразы, ни разу не встречавшиеся ребёнком |
| `snapshot` | `{root: узел \| null, missing?: фраза, children: [узел, …]}` — **заменяет** дерево целиком; `root: null` = такой фразы в дереве нет |
| `children` | `{parent, children: [узел, …]}` — дописывает детей |
| `node` | дельта узла `{phrase, …изменившиеся поля}` — обновляет **все** вхождения фразы (DAG) |
| `progress` | `{stage, node, done, total}`; `total` может расти по ходу |
| `log` | строка лога или массив (хвост при подписке) |
| `task` | строка задачи или массив (накопленные при подписке); `status` = `QUEUED\|WAITING\|RUNNING\|DONE\|FAILED` |
| `log_cleared` | `{}` |
| `llm_status` | `{online, last_seen_at}` |

**Объект узла:** `{phrase, freq, status, task_id, error, cached, childCount, children?}`.
`cached` — свой пул запрошен (есть более глубокие уточнения); `childCount` — сколько уточнений в
пуле; `children` — **локальные** дети из пула родителя, зависят от контекста родителя и приходят
вместе с ним. Реальные дети — только событием `children`. `task_id ≠ null` — узел занят.

### 6.3 Чтение второго слоя — HTTP GET

Второй слой читается по HTTP, а не по WS: он живёт файлами и обновляется не потоком событий, а
завершением операции. Прецедент — `GET /api/estimate`.

| Метод | Ответ |
|---|---|
| `GET /api/needs/trees` | `{trees: [строка, …]}` — по одной на дерево |
| `GET /api/needs/tree/{tree_id}` | дерево целиком |
| `GET /api/needs/reports` | `{reports: [разбор, …]}` — все разборы работ, лучшие сверху |
| `GET /api/estimate?phrase=` | `{nodes, requests}` — нижняя оценка объёма `full_load`; 404 если узла нет |
| `GET /api/stopwords` | `{saved: [{word, kind, added_at}], suggestion, kinds}` — принятые исключения и последнее предложение модели |

**Строка таблицы деревьев:** `{id, root, root_freq, condition, works, segments, phrases, excluded,
ranked, analyzed, best_score, ranked_at, ranked_by, created_at, error}`. До отдельного анализа
`best_score = null` и `ranked = 0`; затем `best_score` — лучшая оценка **среди ещё не разобранных**
работ. `error ≠ null` — файл дерева не читается;
строка всё равно отдаётся, чтобы битая сборка не роняла список.

**Дерево:** `{id, root, root_freq, condition, created_at, revision, refined_*, ranked_*, counts,
works, excluded}`.

**Работа:** классификация `{name, top_freq, phrase_count, unclear, why, phrases, segments}` плюс
nullable-проекция отдельного рейтинга `{score, score_why, intent, product, blocker, evidence,
factors}` и `artifacts`, `analysis`. До рейтинга `score = null` и порядок классификации сохранён;
после рейтинга работы сортируются по `score`.

**Артефакт:** `{kind, created_at, report_link, task_id, verdict, verdict_score, summary}`, новые
сверху. `kind` — `analyze` | `analyze_adv` | `analyze_product` | `season` | `adjacent` | `dump`;
`summary` — одна строка для подсказки на ссылке. У разборов есть свои поля: `functions` у
`analyze_adv`, `spec`, `scores` и `forecast` у `analyze_product`. В проекцию артефакта добавлено
`mrr6` — ₽/мес шестого месяца прогноза: строка работы показывает цену вопроса, не открывая отчёт.

**Разбор (`analysis`):** последний `analyze`-артефакт как `{verdict, verdict_score, confidence,
report_link, created_at, searched}` либо `null`, если работу ещё не разбирали. Вердикты остальных
разборов берутся из `artifacts` по `kind` — в строке работы показываются все три сразу. `searched` — по каким
фразам куплена выдача.

**Исключённая фраза:** `{phrase, freq, why, note}`.

`tree_id` **не склеивается с путём**: это ключ уже найденного набора файлов. Иначе строка из
запроса читала бы произвольный файл.

### 6.4 Внутренние ручки (только для LLM-агента)

Требуют `X-Internal-Token`; `X-Caller` пишется в лог, чтобы отличать диспетчера от исполнителя.

| Метод | Кто зовёт | Смысл |
|---|---|---|
| `GET /internal/llm/watch?max_jobs=&timeout=` | диспетчер | блокируется, пока джобов нет; отдаёт **только сигнал** `[{job_id, type}]` |
| `GET /internal/llm/job/{job_id}` | исполнитель | полные данные `{job_id, type, params, prompt}`; 404 если просрочен |
| `POST /internal/llm/result` | исполнитель | `{job_id, ok, result?, error?}` → `{accepted}`; `false` = джоб просрочен |
| `POST /internal/test/enqueue-job` | тесты | положить джоб без операции — проверять транспорт отдельно |

`prompt` инлайнится в джоб: агент работает строго по нему и **в репозиторий за промптами не
ходит**.

### 6.5 Файлы второго слоя

Публичный контракт, потому что их пишет и читает не только сервер (§7).

```
logs/needs-lab/<tree_id>/params.json          {root, root_freq, min_freq, max_freq,
                                               subtree_total, nodes: [{phrase, freq, children}]}
logs/needs-lab/<tree_id>/accepted.json        {condition, works: [...], excluded: [...]}
logs/needs-lab/<tree_id>/revisions/*.json     прежние классификации и события второго прохода
logs/needs-lab/<tree_id>/rankings/ranking-<task_id>.json
                                              {tree_revision, model_family, works: [оценка, …]}
logs/needs-lab/<tree_id>/artifacts/<slug>/<kind>-<task_id>.json
                                              {work, kind, task_id, created_at, report_link, …}
                                              analyze: verdict, verdict_score, confidence, searched
                                              season:  series, stats, seasonal, phase, comment
                                              adjacent: keys, total_freq, ours, covered, comment
reports/<id>.html                             отчёт по работе
```

Раскладка распознаётся двумя способами: **каталог сборки** (как выше) и **просто json-файл**,
положенный в папку руками — тогда частот у фраз нет, но дерево показывается.

### 6.6 Статика

`/` — собранный фронт (`frontend/dist`), `/reports/*` — готовые HTML-отчёты.

## 7. Лаборатория промптов (`task-worker-mcp`)

Пакет решает две задачи.

**Мост к агенту в бою:** MCP-сервер stdio с инструментами `status` (диспетчер), `get_job` и
`submit_result` (исполнитель) плюс блокирующая команда ожидания работы. Регистрация — user-scope,
не файлом в репозитории.

**Лаборатория:** прогон промпта на реальных данных **без конвейера**. Джоб лежит каталогом
локально, а интерфейс агента ровно тот же, что в бою (`get_job` / `submit_result` по префиксу
локального `job_id`) — проверяем то, что потом и поедет.

Решения лаборатории, которые стоит знать:

- **вход и ответ — файлами, не значениями.** Ответ сборки — десятки тысяч символов; через вызов
  инструмента он обрезается по длине молча, давая валидный JSON без хвоста. **Путь объявляет
  обвязка, не модель:** путь из ответа модели — это чтение произвольного файла по её указке.
- **хэш входа хранится в джобе** — «два прогона получили одно и то же» становится записанным
  фактом, а не утверждением.
- **ответ проверяется на приёме**: не прошёл — не принят, возвращается машиночитаемый список
  проблем (какие фразы потеряны, каких нет во входе, где не сходятся счётчики), попытка
  складывается для разбора.
- **сравнение сборок** — не по названиям работ (они у модели свои), а по **разбиению**: для каждой
  пары опорных фраз совпадает ли ответ «в одной работе или в разных». Отдельно — совпал ли выброс
  и изолированы ли узкие потребности. Эталон — ручная сборка в `reference/`.

Измеренная воспроизводимость сборки на одинаковом входе — **99.1%** по парам фраз (34 716 пар).

## 8. Наследие в схеме

Код узлового пайплайна (`classify`, `search`, `score`, `analyze`, `drill`, ручки `/api/node/op`,
`/api/node/drill`, `/api/node/kind`, промпты `classify.md` / `score.md` / `analyze.md`, событие WS
`report`) **удалён**: выводы делает второй слой, где единица — работа, а не фраза.

В схеме от него осталось, и это намеренно:

- **16 колонок `node`** (`kind`, `score`, `verdict`, `verdict_score`, `competition_*`,
  `description`, `signals_json`, `meant`, таймстемпы шагов) и **пустая таблица `report`**;
- **статусы интента** в `wscore.STATUSES` (`TRANSACTIONAL`, `CATEGORY`, …): в боевых данных таких
  строк нет, но константа описывает то, что схема допускает.

Удалять нельзя по правилу §4: маркер «схема новая» — наличие колонки `status`, и любая правка
списка колонок приводит к пересозданию `node`/`edge` из кэша. Это уже стирало результаты работы
LLM, поэтому схема развивается только аддитивно.

Действующие промпты: **`needs.md`** (чистая классификация), **`needs_refine.md`** (второй проход),
**`needs_rank.md`** (физическая возможность продукта без конкурентов), три разбора — **`analyze_work.md`**
(«Ниша»), **`analyze_adv.md`** («Функции»), **`analyze_product.md`** («Продукт»), — плюс
**`season.md`**, **`adjacent.md`**, **`stopwords.md`**, **`needs_refine.md`**, **`needs_rank.md`**,
**`model_test.md`** (минутная проверка семейства) и `orchestrator.md` (инструкция петле
исполнения).
