# Web Studio Lab: устройство сайта, DNS и почты

Этот документ описывает production-инфраструктуру `webstudiolab.ru`: из каких
частей она состоит, почему выбрана именно такая схема, как её разворачивать,
обновлять, проверять и диагностировать.

## Что должно работать

- `https://webstudiolab.ru` открывает статический лендинг.
- В Object Storage публикуются только четыре production-файла:
  `index.html`, `styles.css`, `script.js` и `favicon.svg`.
- Письмо на `hello@webstudiolab.ru` принимает внешний форвардер ImprovMX и
  пересылает на личный ящик владельца.
- DNS, сертификат и сайт описаны Terraform-кодом. Из почты кодом описаны только
  записи зоны: MX, SPF, DMARC. Алиас живёт в панели форвардера.
- Будущая часто пересоздаваемая прикладная VM живёт в отдельном root
  `terraform/server` и не затрагивает сайт или DNS.

## Общая архитектура

Сайт и почта используют один домен, но технически являются независимыми
маршрутами. Своих вычислительных ресурсов ни один из них не требует.

```text
Браузер
   │
   ├─ DNS: webstudiolab.ru ANAME
   │      └─ Yandex Object Storage website endpoint
   │             └─ index.html + styles.css + script.js + favicon.svg
   │
   └─ TLS: сертификат Yandex Certificate Manager

Отправитель письма
   │
   └─ DNS: webstudiolab.ru MX → mx1/mx2.improvmx.com
                                  └─ пересылка на личный ящик
```

## Структура Terraform

### `terraform/bootstrap`

Создаёт только инфраструктуру удалённого state:

- service account `webstudiolab-tfstate`;
- статический S3-ключ;
- приватный бакет `webstudiolab-ru-tfstate-hjb4rfs`;
- versioning для защиты state от случайной перезаписи;
- роль `storage.admin`, необходимую Terraform для управления настройками
  бакета и versioning.

State самого bootstrap остаётся локальным. Удалять его нельзя, пока другие
Terraform roots используют созданный бакет.

### `terraform/webstudiolab.ru`

Постоянная инфраструктура домена:

- Object Storage и файлы лендинга;
- Yandex Cloud DNS;
- Certificate Manager;
- записи MX, SPF и DMARC;
- скрипт проверок.

Его state хранится в bootstrap-бакете по ключу
`webstudiolab.ru/terraform.tfstate`.

### `terraform/server`

Зарезервирован под будущую прикладную VM. Это отдельный Terraform root и
отдельный state. Поэтому уничтожение или пересоздание прикладного сервера не
удалит лендинг, DNS или почту.

## Как публикуется сайт

Исходники production-лендинга находятся в:

```text
terraform/webstudiolab.ru/site/index.html
terraform/webstudiolab.ru/site/styles.css
terraform/webstudiolab.ru/site/script.js
terraform/webstudiolab.ru/site/favicon.svg
```

Каталог один и называется `site`, потому что версия лендинга одна и она
окончательная. Черновиков `v1`…`v5` в репозитории нет: держать рядом с production
неиспользуемые версии — прямой путь опубликовать не то. Все четыре файла лежат
вместе, поэтому `index.html` ссылается на соседей относительными путями без `..`.

В `site.tf` объявлена явная карта `local.site_files`. Terraform загружает только
перечисленные в ней объекты. Другие каталоги или случайные локальные файлы не
могут попасть в production автоматически.

`etag = filemd5(...)` заставляет Terraform обновлять объект, когда содержимое
локального файла изменилось. Для обычного обновления лендинга достаточно изменить
файлы в `site/` и выполнить `terraform plan`, затем `terraform apply`.

### Объекты загружаются через S3-совместимый провайдер

Файлы описаны ресурсом `aws_s3_object` с провайдером `aws.storage`, направленным
на `https://storage.yandexcloud.net`, а не `yandex_storage_object`. Причина одна:
`yandex_storage_object` в провайдере `0.220.0` не имеет атрибута `cache_control`,
и без него браузер сам выбирает эвристический срок жизни копии.

Что даёт `Cache-Control: no-cache`:

- браузер обязан сверять `ETag` перед показом копии, поэтому обновление лендинга
  видно сразу и «очистить кэш» больше не нужно;
- ответ `304` дешёвый, файлов четыре, трафик мизерный.

Сверка идёт одним запросом: браузер кладёт сохранённый ETag в заголовок
`If-None-Match`, сравнение делает сервер и отвечает либо `304` без тела, либо
`200` с новым содержимым. Сам браузер хеш не считает.

Здесь ETag — честный MD5 файла, потому что его проставляет Terraform через
`filemd5`. Поэтому одинаковый файл даёт одинаковый ETag при любом деплое; у
дефолтного nginx-ETag из времени модификации и размера этого свойства нет.

Без этого заголовка Object Storage не отдаёт вообще ничего про кэш, и браузер
считает свежесть как 10% от возраста файла. Именно это заставило браузер после
включения HTTPS ещё час показывать сохранённый **HTTP**-ответ, полученный до
выпуска сертификата, — со предупреждением «соединение не защищено» и без запроса
к серверу, который уже отдавал 301 на HTTPS.

Бакет по-прежнему создаёт `yandex_storage_bucket`: через S3 API идёт только
загрузка объектов. Ключ доступа — тот же `webstudiolab-site`, отдельных прав не
нужно.

Проверка заголовков:

```bash
curl -sSI https://webstudiolab.ru/ | grep -iE 'cache-control|etag'
```

Object Storage настроен как website hosting:

- `index.html` — стартовый документ;
- `index.html` — fallback для неизвестного пути;
- публичное чтение объектов включено;
- просмотр списка файлов выключен;
- максимальный размер бакета ограничен 1 GiB;
- `force_destroy = false`, поэтому бакет нельзя случайно удалить вместе с
  содержимым.

У сайта нет backend-приложения. Ссылка `mailto:` открывает установленный у
посетителя почтовый клиент. Адрес, находящийся в статическом HTML, технически
виден поисковым роботам; скрыть его надёжно без серверного обработчика нельзя.

### Своего IP у сайта нет

Апекс домена — ANAME на хостнейм Яндекса, а не A-запись на собственный адрес.
Авторитативный сервер разворачивает цель сам и отдаёт браузеру обычную A-запись
`213.180.193.247`; тот же адрес отвечает за все бакеты-сайты региона, потому что
все их website-endpoint'ы — CNAME на общий `website.yandexcloud.net`.

Один адрес обслуживает много сайтов, потому что имя сайта едет внутри запроса:
в TLS-рукопожатии как SNI, в HTTP как заголовок `Host`. По ним фронтенд Яндекса
(в ответах виден как `Server: nginx`) выбирает сертификат и бакет. Он же делает
редирект `http` → `https` — в Terraform такого правила нет.

Отсюда два следствия. Первое: платить за публичный IPv4 не нужно, потому что
исключительного владения адресом нет. Второе: своих заголовков в ответ не
добавить — `Strict-Transport-Security` и CSP на этом слое поставить негде, через
метаданные объекта задаются только `Content-Type`, `Cache-Control` и подобные.
Понадобится HSTS — придётся ставить впереди CDN или балансировщик.

ANAME вместо CNAME нужен потому, что по RFC на вершине зоны CNAME запрещён: там
уже живут SOA и NS.

## Почему в REG.RU меняются только NS

REG.RU остаётся регистратором домена, но авторитетной DNS-зоной управляет Yandex
Cloud DNS. В REG.RU указаны только два DNS-сервера:

```text
ns1.yandexcloud.net
ns2.yandexcloud.net
```

После делегирования все записи создаёт Terraform в Yandex Cloud. Не нужно
дублировать A, MX, TXT или CNAME в панели REG.RU: после смены NS старая зона
REG.RU больше не является источником истины.

Основные записи:

| Запись | Назначение |
|---|---|
| `@ ANAME webstudiolab.ru.website.yandexcloud.net.` | Направляет корневой домен на Object Storage |
| `_acme-challenge CNAME ...cm.yandexcloud.net.` | Подтверждает домен для TLS-сертификата |
| `@ MX 10 mx1.improvmx.com.` и `20 mx2.improvmx.com.` | Направляет входящую почту на форвардер |
| `@ TXT v=spf1 include:spf.improvmx.com -all` | Единственный уполномоченный отправитель — форвардер, остальным отказ |
| `_dmarc TXT v=DMARC1; p=reject` | От имени домена не отправляет никто, подделки отбиваются |

Две MX-записи — это **один** RRset с двумя значениями в `data`, а не два ресурса:
набор MX для одного имени в DNS неделим. Точка на конце обязательна, иначе Yandex
DNS достроит к имени домен и получится `mx1.improvmx.com.webstudiolab.ru`.

Смена NS в реестре и очистка кэша — разные события. WHOIS может уже показывать
Yandex NS, а конкретный DNS-резолвер ещё несколько часов возвращать старые NS
REG.RU до истечения TTL.

### Старую зону в REG.RU надо удалить, а не просто перестать использовать

После смены NS зона в REG.RU продолжает существовать, и её серверы отвечают
**авторитетно**:

```text
dig @ns1.reg.ru webstudiolab.ru A   →  95.163.244.138  TTL 86400
dig @ns1.reg.ru webstudiolab.ru NS  →  ns1.reg.ru. ns2.reg.ru.  TTL 86400
```

`95.163.244.138` — парковка REG.RU: по HTTP отдаёт страницу-заглушку с
`<title>webstudiolab.ru</title>`, по HTTPS соединение не поднимается вообще
(`tlsv1 alert internal error`). Резолвер, успевший закэшировать старую
делегацию **до** переключения, продолжает спрашивать именно эти серверы: реестр
`.ru` отдаёт NS с TTL `345600`, то есть застрять можно почти на четыре суток.
Посетитель в этот момент видит парковку по HTTP и предупреждение «соединение не
защищено» — сайт при этом полностью исправен.

Отличить это состояние от поломки сайта:

```bash
dig +short A webstudiolab.ru          # ожидаем 213.180.193.247
dig @ns1.reg.ru +short A webstudiolab.ru   # если 95.163.244.138 — старая зона жива
```

Единственное лекарство — **удалить записи (или всю зону) домена в панели
REG.RU**: пока они там есть, никакой правкой в Yandex Cloud стухшие резолверы
не переубедить. Terraform на зону REG.RU не влияет.

### TXT-записи нужно брать во внутренние кавычки

Yandex Cloud DNS разбирает значение TXT как строку зоны: пробел — разделитель
character-string, а `;` начинает комментарий. Незакавыченное значение поэтому
портится в двух местах:

| Что задано в Terraform | Что отдаёт NS | Итог |
|---|---|---|
| `v=spf1 include:spf.improvmx.com -all` | `"v=spf1" "include:..." "-all"` | RFC 7208 склеивает строки **без** пробела → `v=spf1include:...-all`, запись невалидна |
| `v=DMARC1; p=reject` | `"v=DMARC1"` | всё после `;` отброшено, обязательный тег `p=` потерян |

Поэтому в `dns.tf` значения записаны с внутренними кавычками:

```hcl
data = ["\"v=spf1 include:spf.improvmx.com -all\""]
data = ["\"v=DMARC1; p=reject\""]
```

Проверка — значение должно быть **одной** строкой в кавычках:

```bash
dig +short TXT webstudiolab.ru
dig +short TXT _dmarc.webstudiolab.ru
```

Ошибка тихая: письма продолжают доходить, но SPF у получателя даёт `none` вместо
`pass`, а DMARC не имеет политики.

## Как работает HTTPS

Certificate Manager выпускает управляемый сертификат для
`webstudiolab.ru`. Terraform автоматически создаёт DNS CNAME challenge.

Первый apply выполняется с `enable_https=false`, поскольку нельзя прикрепить к
Object Storage сертификат в состоянии `VALIDATING`. После делегирования DNS
Certificate Manager видит challenge и переводит сертификат в `ISSUED`. После
этого `enable_https=true` добавляет сертификат в HTTPS-конфигурацию бакета.

Проверка статуса:

```bash
yc certificate-manager certificate get --id fpqrgphu2a56kcmu2hrm
yc storage bucket get-https --name webstudiolab.ru
```

Собственный домен по HTTPS поддерживается потому, что имя бакета содержит точку и
совпадает с доменом. Редирект HTTP → HTTPS Object Storage включает сам.

### Почему сертификат управляемый, а не свой

Статика не даёт процесса, который держал бы 443-й порт, поэтому TLS обязан
терминироваться на стороне облака. Бакет умеет принимать только `certificate_id`
из Certificate Manager: положить туда pem-файл нельзя.

Внутри происходит тот же ACME, что делал бы Caddy или certbot, — с валидацией по
`DNS_CNAME`. Разница в том, что валидацию и продление ведёт облако, а
валидационную запись Terraform кладёт в ту же зону автоматически. Приватный ключ
при этом остаётся у Яндекса; это цена управляемого TLS.

Сертификат выписан ровно на `webstudiolab.ru`. Для поддомена (например под
будущий API) нужен отдельный `yandex_cm_certificate` со своей валидационной
записью: добавление домена в существующий managed-сертификат означает новую
валидацию, а `dns.tf` берёт `challenges[0]` и на двух доменах потребует
`for_each`.

### Раскатка сертификата на edge занимает до получаса

После apply привязка видна в `bucket get-https` сразу, но узлы Object Storage
получают сертификат постепенно. Пока раскатка идёт, часть TLS-соединений отдаёт
дефолтный `*.storage-1.yandexcloud.net`, и браузер показывает «соединение не
защищено» — при этом другие запросы к тому же адресу уже проходят. Это ожидаемое
промежуточное состояние, а не ошибка конфигурации; менять что-либо не нужно.

Отличить раскатку от настоящей поломки помогает серия запросов, а не один:

```bash
for i in $(seq 1 10); do
  curl -sS -o /dev/null --max-time 15 -w '%{http_code}\n' https://webstudiolab.ru/
done
```

Смешанные `200` и `000` означают незавершённую раскатку; стабильные `000` —
реальную проблему.

## Почему приём почты отдан внешнему форвардеру

Приём письма требует постоянно открытого TCP/25 на предсказуемом адресе, на
который смотрит MX. Бессерверно в Yandex Cloud это невозможно: управляемого
сервиса входящей почты там нет, у функций нет TCP-слушателя, API Gateway понимает
лишь HTTP. Значит собственный приём — это круглосуточно включённая виртуалка с
открытым в интернет портом, разбором чужого ввода и постоянной платой за vCPU,
диск и статический IP. Для одного адреса, на который пишут несколько раз в месяц,
это несоразмерно, и она была бы единственным объектом в проекте, требующим
администрирования.

Поэтому приём отдан ImprovMX: MX смотрит на них, они принимают письмо и
пересылают на личный ящик. Ящика они не создают и почту не хранят — это транзит.

Что в этой схеме кодом **не** описывается: сам алиас `hello@webstudiolab.ru` и
адрес получателя. Terraform-провайдера у сервиса нет, алиас задаётся в их панели.
Catch-all включать не следует: иначе спам на любой адрес домена пойдёт в личный
ящик.

Своя SPF-запись пересылке не нужна: форвардер подставляет собственный конверт
(SRS), и получатель проверяет его SPF, а не наш. Поэтому домен закрыт наглухо —
`-all` в SPF и `p=reject` в DMARC означают, что за `webstudiolab.ru` не
отправляет никто, и подделать письмо от `hello@` нельзя.

Плата за это одна: отправлять **от** `hello@webstudiolab.ru` нечем, ответ уходит
с личного адреса. Это осознанный выбор, а не недоделка.

Известное свойство любой пересылки: форвардер сохраняет исходный `From` и
рассчитывает, что DKIM-подпись отправителя доживёт до ящика получателя. Обычно
доживает, но у строгих доменов письмо может попасть в «Спам» — это не поломка
схемы.

## Terraform: обычный рабочий цикл

Функция `tf` из `~/.bashrc` экспортирует Yandex Cloud token, cloud ID и folder ID
в переменные `TF_VAR_*`.

```bash
tf
cd /home/sergey/Personal/research-tools/terraform/webstudiolab.ru
source ../bootstrap/export-backend-env.sh
terraform init
terraform fmt -recursive ..
terraform validate
terraform plan
terraform apply
```

`export-backend-env.sh` читает S3-ключ state из локального bootstrap state и
экспортирует `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` только в текущий shell.
Значения ключей скрипт не печатает.

Локальный `terraform.tfvars` намеренно игнорируется Git и хранит активные
переключатели:

```hcl
enable_https = true
```

`*.tfstate`, `*.tfvars`, `*.tfplan` и `.terraform/` не должны коммититься.
Файл `.terraform.lock.hcl`, напротив, следует хранить в Git.

### Как выключать целые подсистемы

Состояния «ресурс выключен» в Terraform не существует: в state он либо есть, либо
нет, поэтому флаг с `count = 0` — это `destroy`, а не пауза. Флаги вида
`enable_https` уместны для **поэтапного подъёма**, когда порядок вынужденный
(сертификат нельзя прикрепить раньше валидации), но как долгосрочный
переключатель подсистемы они плохи: комбинаций становится `2^n`, ссылки обрастают
`[0]`, и один apply держит в руках сразу всё.

Правильная граница — **жизненный цикл, а не проект**: разные root-модули со своим
ключом state. Шов здесь очевидный: всё, что нужно любой части, — это `zone_id` и
`domain`, стабильный контракт из двух строк. Префикс `webstudiolab.ru/` в
`backend.tf` под такое разделение уже оставлен.

На то, что больно терять, стоит ставить `lifecycle { prevent_destroy = true }` —
случайный флаг тогда упадёт с ошибкой вместо тихого удаления.

## Проверки

### Сайт и DNS

```bash
cd /home/sergey/Personal/research-tools/terraform/webstudiolab.ru
./check.sh

dig +short NS webstudiolab.ru
dig +short A webstudiolab.ru
dig +short MX webstudiolab.ru
curl -I https://webstudiolab.ru/
```

`check.sh` печатает NS, A/ANAME, MX, SPF, DMARC, статус HTTPS и subject
сертификата, а также проверяет, что MX указывает на форвардер. Код возврата: `0`
— всё прошло, `1` — что-то провалилось.

### Доставка письма

Автоматической проверки нет намеренно: она требовала бы отправлять письма от
имени домена, чего схема не делает. Проверка ручная — отправить письмо на
`hello@webstudiolab.ru` с любого ящика и убедиться, что оно пришло на личный
ящик, включая папку «Спам».

Если письма перестали доходить: жив ли алиас в панели ImprovMX, отвечают ли MX
(`dig +short MX webstudiolab.ru`), не лежит ли письмо в «Спаме» у получателя.

## Обновление лендинга

1. Изменить файлы только в `terraform/webstudiolab.ru/site/`.
2. Локально открыть `site/index.html` или запустить простой HTTP-сервер.
3. Выполнить `terraform plan`.
4. Убедиться, что меняются только нужные `aws_s3_object.site[...]`.
5. Выполнить `terraform apply`.
6. Открыть `https://webstudiolab.ru` — из-за `Cache-Control: no-cache` чистить
   browser cache не нужно, браузер сверит `ETag` сам.

Terraform не выполняет сборку: в бакет отправляются готовые HTML/CSS/JS-файлы.

## Стоимость

Постоянно тарифицируемых ресурсов в этом root нет. Object Storage, DNS-зона и
управляемый сертификат платятся по факту использования и на таком объёме стоят
копейки; форвардер бесплатен; публичного IPv4 в собственности нет.

Временные тестовые VM после проверки нужно удалять вместе с auto-delete диском.

одинаково у авторитативного `ns1.yandexcloud.net` и у публичного резолвера
`8.8.8.8`. SPF — `"v=spf1 include:spf.improvmx.com -all"`, DMARC —
`"v=DMARC1; p=reject"`; `dig` подтверждает, что оба значения отдаются одной
строкой. Доставка проверена письмом на `hello@webstudiolab.ru`.

**Чистота стенда.** `yc compute instance list` и `yc vpc address list` пусты: ни
виртуальных машин, ни зарезервированных адресов в фолдере нет. Из сервисных
аккаунтов есть только `webstudiolab-site` и `webstudiolab-tfstate`. `./check.sh`
возвращает `0`.

**Исправлено после жалобы «сайт всё ещё not secure».** У объектов не было
`Cache-Control`, поэтому браузер продолжал показывать сохранённый HTTP-ответ,
полученный до выпуска сертификата. Загрузка объектов переведена с
`yandex_storage_object` на `aws_s3_object` через провайдер `aws.storage`, все
четыре файла теперь отдают `Cache-Control: no-cache`. Перенос сделан через
`terraform state rm` без удаления объектов: план `4 to add, 0 to change,
0 to destroy` — прямая замена ресурса дала бы 4 create и 4 destroy на одних и тех
же ключах, а порядок Terraform не гарантирован и destroy мог снести только что
загруженный файл.

**Исправлено при финальной проверке.** SPF и DMARC отдавались испорченными:
Yandex Cloud DNS разбил SPF на три character-string, а из DMARC выбросил всё
после `;`. Значения переписаны с внутренними кавычками (см. раздел про TXT),
применено планом `0 to add, 2 to change, 0 to destroy`.

**Terraform.** `terraform fmt -check -recursive` без замечаний, оба root
проходят `validate`, `plan` в domain root — `No changes`.
