# Testing plan: конвейер `drill`

Пара к `design-plan.md` (ЧТО) и `tech-design.md` (КАК). Ссылки — вида `design §N` / `tech §N`.

Задача плана: сделать так, чтобы **ошибку находил тест, а не пользователь**, и чтобы при этом не
платить деньгами за каждый прогон. Отсюда главный принцип: **почти всё проверяется без LLM и без
XMLRiver**, а платные слои — тонкие и редкие.

---

## 0. Принципы

- **Платное и капризное — в моках.** XMLRiver (деньги + капча) и LLM (деньги) в обычном прогоне не
  вызываются. Живые прогоны — под явными маркерами и не по умолчанию.
- **Сначала контракт, потом интеллект.** Пока обмен джобами не проверен фальшивым воркером,
  любой сбой в реальном прогоне неотличим: сервер виноват или промпт. Поэтому §5 идёт до §6.
- **LLM недетерминистичен → две разные проверки:** *структура* ответа — жёстко по схеме;
  *качество суждений* — по рубрике с допусками, никогда точным равенством.
- **Детерминированное ядро — жёсткие ассерты** (стемминг, лес, FSM, границы порогов).
- **Инварианты важнее конкретных значений** (§10): «ошибка → лог, статус не меняется», «нет
  частичной выдачи», идемпотентность, дедуп по DAG — проверяются на моках.
- **UI тестируется физически.** Кнопки нажимаются в реальном браузере, статусы приходят по
  настоящему WebSocket. Компонентные тесты — дополнение для полноты матрицы, а не замена.

## 1. Что реализация обязана предоставить для тестируемости

Без этих вещей часть плана невыполнима — их нужно заложить сразу, а не задним числом.

| # | Требование | Зачем |
|---|---|---|
| 1 | **Способ поставить джоб с готовыми `params`** без краула и без LLM | иначе чтобы получить `classify`-джоб, надо сначала прокраулить реальное поддерево — шаг 6 нечем проверить |
| 2 | **В логе внутренних вызовов виден вызывающий** (диспетчер или агент) | ключевое правило `tech §6.3` — «диспетчер не забирает данные джоба». Без этого правило не тестируемо, а промпт нарушит его первым |
| 3 | **Стабильные селекторы в UI** (`data-testid` на узлах, кнопках, вкладках, диалоге) | иначе браузерные тесты ломаются от любой правки вёрстки и им перестают верить |
| 4 | **Подменяемые время и идентификаторы** | чтобы сравнивать снимки состояния и не ловить флаки на таймстемпах |
| 5 | **Режим «только кэш»: промах кэша НЕ идёт в сеть** | без него «бесплатный» прогон краула незаметно станет платным — на первом же непокрытом узле (§3.1). Промах = считаем узел листом либо падаем с внятной ошибкой, но не фетчим |

## 2. Уровни и инструменты

Пирамида: много быстрых → мало платных.

| Уровень | Что покрывает | Инструменты | В дефолтном прогоне |
|---|---|---|---|
| unit | чистые функции без I/O | `pytest` | да |
| integration | слой данных, контракты HTTP/WS, обмен джобами | `pytest`, `httpx` MockTransport, `TestClient`, temp SQLite | да |
| компонентный UI | матрица «статус → кнопки», редьюсер событий | Vitest + React Testing Library | да |
| **браузерный E2E** | **реальные клики, живой WS, весь стек** | **Playwright (`pytest-playwright`)** | да |
| llm-контракт | схема ответов агентов | `pytest -m llm` | нет |
| llm-качество | рубрика/голден-сет | `pytest -m llm` | нет |
| live | один сквозной прогон на реальных данных | `pytest -m live` | нет |

Playwright берём в Python-варианте, а не в Node: тестам нужно поднимать сервер с засеянной БД и
фальшивым воркером — это тот же код, что и в остальных фикстурах, дробить его между двумя раннерами
незачем. Компонентные тесты остаются на Vitest — они живут рядом с фронтом.

По умолчанию: `pytest` (маркеры `llm`/`live` выключены) + `npm test` для компонентных.

## 3. Фикстуры и тестовые данные

- **Кэш Wordstat.** Готовые ответы из таблицы `cache` действующей `semcore.db` выгружаются в
  `tests/fixtures/wordstat/`. В тестах фетч бьёт по фикстурам, не в сеть.
- **Выдачи (SERP)** — 5–10 сохранённых, с разными профилями: занято профильным инструментом,
  UGC-форумы, тонкий контент, пусто, только иностранные инструменты. Нужны и для `score`, и для UI.
- **БД-снимки по статусам** — главный enabler для UI: база, где есть **по узлу в каждом из 11
  статусов** (design §2) плюс узел с отчётом и узел с ошибкой. На ней матрица кнопок проверяется
  без прогона пайплайна.
- **Копия реальной БД** — для проверки пересбора модели из кэша (§5) и как источник узких
  покрытых поддеревьев (§3.1). Работаем всегда на копии: `cache` в оригинале — оплаченные данные.
- **Размеченный набор для `classify`** — 40–60 фраз с эталонным `kind`, вручную (для §6.3).
- **Ответы фальшивого воркера** — заготовленные JSON по каждому типу джоба, включая заведомо
  «плохие» (см. §5).
- Фикстуры лежат в репозитории, ключей в них нет.

### 3.1 Бесплатный прогон на реальных данных: чистим дерево, оставляем кэш

Ключевой приём: в `semcore.db` **сырые ответы Wordstat лежат в `cache`, а `node`/`edge` — всего
лишь производная от них**. Значит модель можно снести, кэш оставить — и краул пройдёт **настоящим
кодом**, но каждый фетч попадёт в кэш. Ноль запросов в сеть, ноль денег, при этом проверяются
фронтир, `FLOOR`, дедуп по DAG, параллельность и простановка статусов.

**Три уровня сброса** — три разных бесплатных прогона:

| Чистим | Оставляем | Что гоняем |
|---|---|---|
| только поля пайплайна (`status`, `kind`, `score`, `verdict`, отчёты) | дерево, `cache`, `serp` | весь пайплайн от `classify` и дальше, сколько угодно раз |
| `node` + `edge` | `cache`, `serp` | краул целиком |
| всё, включая `cache` | — | ничего бесплатного: любой краул здесь платный. Так не делаем |

**Сценарий «2–3 узла на всю глубину».** Сносим `node`/`edge`, берём **2–3 небольших узла, чьё
поддерево целиком покрыто кэшем**, и краулим каждый до опустевшего фронтира. Проверяем: краул
завершился, всё поддерево получило `FULLY_LOADED`, ниже `FLOOR` не углублялись (но узлы и связи
записаны), фраза с несколькими родителями взята один раз, повторный запуск не добавил ни узлов, ни
обращений к фетчу.

Подходящие корни (посчитано по текущему кэшу: 155 ответов; в скобках — узлов в поддереве / нужных
фетчей / глубина):

| Корень | Поддерево | Чем хорош |
|---|---|---|
| `поменять фон в видео` | 18 / 3 / **2** | единственный из мелких с **глубиной 2** — проверяет именно рекурсию, а не один уровень |
| `удалить фон нейросетью` | 22 / 9 / 1 | самое крупное полностью покрытое; и почти дубль `удалить фон нейросеть` (22 / 9 / 1) — **пара для проверки дедупа по DAG**: пересекающиеся поддеревья |
| `как убрать фон с видео` | 10 / 4 / 1 | компактный, быстрый |

Всего полностью покрытых поддеревьев — **45**. Список пересчитывается по мере роста кэша, поэтому
конкретные корни в тесте лучше выбирать не хардкодом, а запросом «поддерево, где все узлы
`freq ≥ FLOOR` есть в `cache`».

**Две ловушки, которые надо знать:**

- **Автобэкфилл.** `wscore` при подключении к БД с пустым `node` и непустым `cache` **сам
  перестраивает модель из кэша**. То есть «почистил дерево» не остаётся почищенным. Для фикстур это
  подарок (мгновенный засев одной операцией), но если тесту нужно именно пустое дерево — бэкфилл
  надо отключать, иначе тест проверяет не то, что думает.
- **Покрытие кэша тонкое.** Узлов с `freq ≥ FLOOR` — 13 815, а в кэше из них 49. Поэтому краул
  широкого узла (`нейросеть` — почти 9 800 нужных фетчей, из них 9 773 непокрытых) без режима
  «только кэш» (§1.5) уйдёт в сеть на тысячи запросов. Бесплатны только узкие покрытые поддеревья.

**`serp` — тоже кэш.** Выдача в `cache` не лежит (там только Wordstat), и сейчас таблица пуста:
первое наполнение платное. Но ключ у неё «фраза + движок», поэтому **после первого наполнения
`search` перегоняется бесплатно** сколько угодно — тот же приём, что с Wordstat, с разовой платой
за засев.

**LLM не кэшируется вообще** — каждый реальный прогон стоит денег. Для контракта это закрывает
фальшивый воркер (§5); если понадобится повторно и бесплатно гонять именно настоящие промпты, надо
один раз записать реальные ответы и потом воспроизводить их.

## 4. Unit — детерминированное ядро

Жёсткие ассерты, без I/O:

- `normalize`, `stem`, `words_of` — регистр, пробелы, окончания, минимальная длина основы.
- `build_forest` — вложенность по словам-супермножествам, корни, сортировка, отсутствие циклов.
- `refinements` — только строгие словесные супермножества запроса.
- `parse_popular` — разбор пар «фраза/частота», битые значения → 0.
- **Границы порогов** — самое дешёвое место для off-by-one:
  - `FLOOR = 50`: `49` не бурим вглубь, `50` бурим;
  - порог score: `60` → `LOW_SCORED`, `61` → `SCORED` (`tech §4`);
  - `freq > 30000` → `category` (design §2).
- **Таблица переходов FSM** (design §2): каждый разрешённый переход применяется, любой
  неразрешённый отвергается; терминалы не имеют операций пайплайна.

## 5. Контракт сервера — без LLM (фальшивый воркер)

**Самый ценный слой: ловит большинство ошибок, стоит ноль.** Фальшивый воркер — скрипт, который
ведёт себя как Claude-петля, но вместо интеллекта отдаёт заготовки: встаёт в ожидание, забирает
`job_id`, берёт данные джоба, возвращает заранее заданный ответ.

Его поведение переключаемо — это и есть тест-кейсы:

| Режим воркера | Ожидаемое поведение системы |
|---|---|
| корректный ответ | статусы переходят, данные записаны, события ушли, задача `DONE` |
| ответ с ошибкой | задача `FAILED`, запись в лог, **узел остался как был** |
| невалидный JSON | то же, что ошибка — молча не проглатывается |
| не отвечает вовсе | срабатывает таймаут, задача `FAILED`, узел не тронут, ретрая нет |
| отвечает после таймаута | результат отброшен, предупреждение в лог, **сервер жив** (`tech §6.3`) |
| отвечает на неизвестный `job_id` | `accepted: false`, сервер жив |
| берёт данные джоба «от лица диспетчера» | видно в логе вызывающего (требование §1.2) — основа для проверки правила из `tech §7.1` |
| забрал джоб и умер | таймаут; джоб не вернулся в очередь (резервирования нет, `tech §3`) |

Плюс здесь же:

- **Дробление операций** (`tech §3`): `classify` большого поддерева режется на джобы; операция
  завершается **только когда вернулись все части**; одна операция — одна строка `task`.
- **Время жизни джоба**: данные доступны по `job_id` после выдачи сигнала и недоступны после
  завершения/таймаута.
- **Схема и пересбор из кэша**: на пустой БД и на копии реальной — новые колонки и таблицы
  появляются, модель пересобирается в то же дерево (столько же узлов и связей, статус дефолтный),
  повторный запуск ничего не ломает. Отдельно: **`cache` и `keywords` не изменились** — ни одной
  строки не потеряно и не перезаписано.
- **Слой данных** (`tech §5`): краул не углубляется ниже `FLOOR`, фраза с несколькими родителями
  берётся один раз, повторный краул не дублирует и не тратит запросы, **кэш Wordstat работает при
  параллельном крауле** (проверяется счётчиком обращений к фетчу), по завершении всё поддерево
  `FULLY_LOADED`.
- **`search` без частичной выдачи**: падение одного движка → в БД не попало ничего.
- **Контракты HTTP** (`tech §6.1`): тела запросов/ответов, коды `404` / `409` (занят узел или
  предок) / `422` (недопустимый переход, неизвестный `op`/`kind`).
- **Контракты WS** (`tech §6.2`): `subscribe` → `roots` + хвост лога; `root` → `snapshot`;
  `expand` → `children`; форма каждого события; `progress` может увеличивать `total`; чтение
  ничего не мутирует.
- **Логи** (`tech §6`): каждая строка попадает в файл без открытого браузера; очистка чистит и
  файл, и представление.
- **Отчёт**: файл на диске, строка в `report`, раздача статикой, ссылка приходит в событии.
- **Рестарт**: незавершённые задачи становятся `FAILED`, блокировки узлов снимаются.

## 6. LLM — три разных слоя

Их часто путают, а тестируются они по-разному и стоят по-разному.

### 6.1 Поведение диспетчера (промпт-петля) — дёшево, но нужен настоящий Claude

Проверяется **реальный артефакт**: сессия Claude Code, поднятая с `orchestrator.md` и скиллом.
Суб-агент внутри тестового прогона — это не то же самое, промпт так не проверить.

Как: сервер поднят на засеянной БД, в очередь положены джобы (требование §1.1), `claude`
запускается headless как подпроцесс. Наблюдаем `logs/drill.log`, таблицу `task` и вывод самого
процесса.

Что проверяем:
- петля **крутится**: после пустого ожидания снова становится в ожидание, не спрашивает
  пользователя, не завершает сессию;
- **модель по типу**: `classify` → Sonnet, `score` → Haiku, `analyze` — без указания модели;
- **диспетчер не забирает данные джоба сам** (по логу вызывающего, §1.2);
- **один джоб — один агент**, пачка идёт параллельно;
- ошибка возвращается как ошибка, **без ретрая и без выдуманных данных**;
- падение одного агента не останавливает петлю.

Практическая деталь: headless-сессия **повиснет** на первом запросе разрешения (фоновый Bash,
MCP-инструмент). Для тестового прогона нужен заранее разрешённый список или явный permission-mode —
иначе это выглядит как «петля зависла».

### 6.2 Структура ответов агентов — жёстко по схеме

Каждый ответ по каждому типу джоба валидируется схемой (`prompts/*.md` задают форму): обязательные
поля, диапазоны (`score` и `competition_*` в 0–100, `confidence` 0–1), допустимые значения
(`kind`, `recommendation`), длина массива результатов равна длине входа, выравнивание по `phrase`.
Схема — жёсткий гейт: не прошло, значит промпт сломан.

### 6.3 Качество суждений — рубрика и допуски

- **`classify`**: точность по `kind` на размеченном наборе **≥ 85%**; отдельно спец-кейсы:
  `что такое …` → informational, `скачать photoshop` → navigational, `скачать видео с ютуба` →
  transactional, зонтик с разными детьми → category, `freq > 30000` → category.
- **`score`**: важнее **порядок, чем абсолют**. «Пусто / UGC» должно получать выше, чем «занято
  профильным инструментом»; занято в обоих → низ шкалы, слабо в обоих → верх; гейт-кэп срабатывает
  при профильном инструменте в топ-3 обоих. Повторный прогон того же входа — в пределах допуска.
- **`analyze`**: `verdict_score` согласован с бакетом `recommendation`; отчёт — валидный HTML,
  содержит обязательные разделы шаблона (`templates/report.html`); при скудных данных
  `confidence` понижен, а не выдуман вывод.

Эти проверки — под маркером `llm`, гоняются после правки промптов, а не на каждый коммит.

## 7. UI — компонентные тесты (Vitest)

Быстрое и полное покрытие матрицы, без браузера.

**Матрица «статус → кнопки»** (design §2) — таблица-источник, проверяется целиком: рендерятся
**только** разрешённые кнопки и никаких лишних.

| Статус | Ожидаемые кнопки |
|---|---|
| `NEW` | Load · Full load · Drill |
| `LOADED` | Full load · Drill |
| `FULLY_LOADED` | Classify · Drill |
| `TRANSACTIONAL` | Search · Drill · Fix kind |
| `SEARCHED` | Score · Drill |
| `SCORED` | Analyze · Drill · Search view |
| `CATEGORY` / `INFORMATIONAL` / `NAVIGATIONAL` | Fix kind |
| `LOW_SCORED` | Search view |
| `ANALYZED` | — (только `Link`, см. ниже) |

Плюс:
- **`Link`** виден только при наличии отчёта — при любом статусе, и не виден без него.
- **Блокировка**: узел занят → его кнопки disabled; **и кнопки всего его поддерева** тоже
  (`tech §6` — правило выводится по предкам).
- **Редьюсер событий**: `roots` рисует список отправных фраз; `snapshot` **заменяет** дерево;
  `children` **дописывает** детей узлу; `node` обновляет узел на месте; `progress` не сбрасывает
  прогресс назад при росте `total`; `log_cleared` чистит вкладку Лог.
- **Ошибки команд** (`409`/`422`/`404`) показываются пользователю, а не теряются.

## 8. UI — браузерный E2E (Playwright)

Реальный браузер, реальные клики, живой WebSocket. Фронт берётся **собранный и отданный сервером**
— тот же путь, что в бою. LLM подменён фальшивым воркером (§5), XMLRiver — фикстурами.

| 1 | Открыть приложение | видны корни-кандидаты, 4 вкладки, индикатор LLM-петли |

| 7 | Во время операции | кнопки узла **и поддерева** disabled; по завершении снова активны |
| 8 | Прогресс краула | статусы и прогресс капают **без перезагрузки страницы** |
| 9 | `Classify` → `Search` → `Score` | статусы узла меняются по цепочке в реальном времени |

| 13 | Вкладка Лог | строки капают живьём; при открытии виден хвост; «Удалить всё» очищает |
| 14 | Вкладка Task | строки задач со статусами; групповая задача подписана понятно («фраза +N») |
| 15 | Вкладка Отчёты | сортировка по `verdict_score`; ссылка открывает отчёт |
| 16 | Упавшая операция | ошибка видна в логе, **статус узла не изменился**, кнопки разблокированы |
| 17 | Перезапуск сервера при открытой странице | клиент переподключился, дерево живое, зависших блокировок нет |
| 18 | Петля LLM не запущена | индикатор показывает «офлайн»; поставленная LLM-операция падает по таймауту с внятной записью в логе |

### Как гонять

- По умолчанию headless; для разбора — с открытым браузером.
- **На падении сохраняются трассировка, скриншот и видео** — иначе разбирать флаки в реальном
  времени невозможно.
- Ожидания — по состоянию (появился статус, пришло событие), **никаких пауз по таймеру**: это
  главный источник флаки в тестах вокруг WebSocket.
- Каждый сценарий — на свежей засеянной БД.

## 9. Сквозной прогон на живых данных (`-m live`)

Один `drill` на **узком** реальном поддереве (десятки фраз) — реальный XMLRiver, реальный LLM:

- все листья дошли до одного из терминалов;
- у `ANALYZED` есть файл отчёта, строка в `report` и рабочая кнопка `Link`;
- дерево консистентно, лог непустой, задачи `DONE`;
- **повторный `drill` идемпотентен**: терминальные узлы пропущены, новых запросов почти нет.

Бюджет контролируется узостью корня, а не потолком.

---

## 10. Инварианты (должны держаться всегда)

Проверяются на моках, в идеале property-style:

1. **FSM**: статус меняется только разрешённым переходом; терминал не имеет операций пайплайна.
2. **Нет частичной выдачи**: обе выдачи или ни одной.
3. **Ошибка неразрушающа**: упавший шаг → лог + `FAILED`, **статус узла прежний**, ранее собранные
   данные не затёрты. Ни ретрая, ни отмены.
4. **Идемпотентность**: заведение схемы, пересбор из кэша, загрузка фразы, краул, каждая операция
   и `drill` — повторный прогон не дублирует и не ломает.
5. **Дедуп по DAG**: фраза берётся один раз, связи — от каждого родителя, циклов нет.
6. **Только `transactional` идёт дальше**: остальные интенты в `search`/`score`/`analyze` не
   попадают.
7. **Чтение не мутирует**: `root`/`expand` ничего не подгружают.
8. **Тяжёлые данные не проходят через диспетчера** (по логу вызывающего).

## 11. Прогон и CI

- **Быстрый цикл:** `pytest` + компонентные тесты. Без сети, без денег.
- **Полный локальный:** то же плюс браузерный E2E.
- **После правки промптов:** `-m llm`.
- **Перед вехой:** `-m live`, вручную, с ключами.
- В CI по умолчанию идут все бесплатные слои, включая браузерный; `llm` и `live` — только вручную.

---

## 12. Отладочный цикл (как это гонять и наблюдать)

Отдельно, потому что часть тестов — долгоживущие процессы, и с ними нужно уметь работать:

- Сервер, фальшивый воркер и headless-`claude` запускаются **в фоне**; их вывод и `logs/drill.log`
  читаются по ходу.
- Прогон можно **прибить** в любой момент; после правки промпта или скилла — перезапустить, у новой
  сессии контекст чистый.
- Артефакты падений (трассировки Playwright, лог, снимок БД) складываются в одно место — по ним
  разбирают причину, не воспроизводя вручную.
- Цикл «запустил → посмотрел лог → поправил `orchestrator.md` → перезапустил» — основной способ
  доводить промпт-петлю (§6.1).

## 14. Что не тестируем

- Корректность самих XMLRiver, Яндекса и Google — это внешние системы.
- «Правильность» суждений LLM за пределами рубрики §6.3 — вкусовщина, не тест.
- Вёрстку отчёта пиксель-в-пиксель: проверяем наличие разделов, а не оформление.
- Производительность и нагрузку: инструмент однопользовательский, узкое место внешнее.
