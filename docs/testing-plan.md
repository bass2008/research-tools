# Testing plan: конвейер `drill`

Статус: план тестов (v1). Пара к `design-drill.md` (ЧТО) и `implementation-drill.md` (КАК).
Термины кода — на английском. Ссылки на секции — вида `design §N` / `impl §N`.

## 0. Принципы

- **Внешние платные/капризные зависимости не трогаем в обычном прогоне.** XMLRiver (деньги +
  капча) и LLM (деньги) — только через моки/кэш. Живые прогоны — под явными маркерами
  (`-m live`, `-m llm`) и не в дефолте.
- **LLM недетерминистичен → двухуровневая проверка:** (1) *структура* — ответ ВСЕГДА валидируется
  схемой (жёстко); (2) *семантика* — через рубрику/голден-сет с **допусками** и порогами
  точности, не точным равенством.
- **Детерминированное ядро — жёсткие ассерты** (стемминг, лес, формула score, FSM-переходы).
- **Инварианты важнее конкретных значений** (§8): «ошибка → лог, статус не меняется», «нет
  частичной выдачи», идемпотентность, DAG-дедуп — их проверяем на моках без сети.
- Детерминизм LLM в тестах: `temperature=0`; для голден-сетов фиксируем модель и промпт-файл.

## 1. Уровни и инструменты

Пирамида: много unit → меньше integration → мало LLM/e2e.

| Уровень | Что | Инструменты |
|---|---|---|
| unit | чистые функции без I/O | `pytest` |
| integration | wscore+SQLite, Celery↔Redis↔MCP, WS, endpoints — всё на моках | `pytest`, `fakeredis`, `httpx` MockTransport, FastAPI `TestClient`, temp sqlite |
| llm | схема + рубрика на голден-сете | `pytest -m llm` (реальные вызовы, редко) |
| live | один e2e drill на крошечном реальном поддереве | `pytest -m live` (XMLRiver+LLM, бюджет) |
| frontend | компоненты/взаимодействие + smoke | Vitest + Testing Library; headless-Chrome smoke |

`env`: `conda run -n research3.12 pytest`. Маркеры `live`/`llm` по умолчанию **выключены**
(`addopts = -m "not live and not llm"`).

## 2. Фикстуры и тестовые данные

- **Кэш XMLRiver.** Берём готовые ответы из `cache`-таблицы `semcore.db` → кладём как JSON-файлы
  в `tests/fixtures/wordstat/`. `fetch_wordstat` в тестах бьёт по кэшу/моку, не по сети.
- **SERP-фикстуры** — 5–10 сохранённых выдач (`docs_json`) с разными профилями: занято
  инструментом, UGC-форумы, тонкий контент, пусто, иностранные инструменты.
- **Labeled classify-set** — ~40–60 фраз с эталонным `kind` (transactional/informational/
  navigational/category), вручную размеченные (для accuracy-теста, §5).
- **temp sqlite** — каждый DB-тест на свежей `:memory:`/tmp-БД через `connect()`; изоляция.
- Фикстуры версионируем в репозитории (без ключей; `.env` не коммитим).

## 3. Unit — детерминированное ядро (wscore.py)

Жёсткие ассерты, без сети:
- `normalize` — регистр/пробелы; `stem`/`words_of` — окончания, минимальная длина основы.
- `build_forest` — вложенность по словам-супермножествам; корни; сортировка по freq; отсутствие
  циклов; фраза-супермножество уходит в дети.
- `refinements` — берёт только строгие словесные супермножества запроса.
- `parse_popular` — парсинг `{text,value}`, битые значения → 0.
- `freq_band` — границы 50 / 30000 (`LOW`/`EVAL`/`HEAD`), краевые (`49`,`50`,`30000`,`30001`).
- **score-формула** (см. §5-note): если блендинг+гейты вынесены в код — прямые тесты:
  веса `0.6/0.4`, гейт-кэпы (`≤15`/`≤35`), пустой движок → competition≈15, clamp/округление до 5.
- **FSM** — таблица разрешённых переходов (design §2): валидный переход применяется, невалидный
  отвергается; терминалы (`CATEGORY`/`INFORMATIONAL`/`NAVIGATIONAL`/`LOW_SCORED`/`ANALYZED`) не
  имеют операций пайплайна.

## 4. Integration — на моках (без сети/LLM)

- **`migrate` идемпотентна** — прогон на пустой и на «старой» (этап 1-2) БД; повторный вызов
  не падает; все колонки/таблицы (`node`+, `serp`,`task`,`report`) есть; `_maybe_backfill`
  проставляет `freq_band`/`status`.
- **`load_phrase`/`project`** на замоканном `fetch_wordstat` — узлы+рёбра, `queried`, проекция,
  двухцветные метки (`cached`/`childCount`).
- **`full_load` (краул)** — стаб фетча отдаёт дерево-фикстуру: доходит до `FULLY_LOADED`, не
  бурит ниже `FLOOR=50`, DAG-дедуп (фраза с двух родителей фетчится один раз), прогресс-колбэк
  вызывается. Идемпотентность: повторный `full_load` не дублирует рёбра/фетчи.
- **Celery-задачи (`-P threads`, eager или fakeredis):** `search` пишет `serp` и `TRANSACTIONAL→
  SEARCHED`; при падении движка — **нет частичной выдачи**, узел остаётся `TRANSACTIONAL`, запись
  в лог, `task=FAILED`.
- **Хендовер `Celery↔MCP` (impl §3)** на `fakeredis`: задача `LPUSH taskq` → mock-`watch` `BRPOP`
  → `submit_result` `LPUSH result:{id}` → задача разблокировалась и записала результат; **таймаут/
  `ok:false`** → `FAILED`, узел не тронут, без ретрая.
- **WS (`/ws`)** через `TestClient`: `subscribe` → snapshot; `PUBLISH events` фанится клиенту;
  `expand` — чистое чтение (данные не тянет); типы событий `snapshot/node/log/task/report/
  log_cleared` соответствуют схеме (impl §6).
- **Endpoints (write):** `POST /api/node/{load,full-load,op,drill,kind}` ставят задачу, вешают
  `task_id`, возвращают ack; `POST /api/logs/clear` — `truncate` файла + событие `log_cleared`.
- **Логи в файл (impl §6.1):** каждое `log`-событие дописано в `logs/drill.log`; формат строки;
  запись идёт без открытого WS-клиента; `clear` чистит файл.
- **`report`:** analyze-mock кладёт файл `reports/{id}.html`, строку `report(id,node,link)`;
  `report JOIN node` отдаёт заголовок/вердикт; static-раздача `/reports/{id}.html` возвращает файл.

## 5. LLM / промпты (`-m llm`, редко, деньги)

Всегда — **валидация схемы** ответа; семантика — с допусками.
- **classify (Sonnet):** на labeled-set (§2) — **accuracy ≥ порога** (напр. ≥85%) по `kind`;
  спец-кейсы: `что такое …`→informational, `скачать photoshop`→navigational, `скачать видео с
  ютуба`→transactional, зонтик с разными детьми→category, `freq>30000`→category.
- **score (Haiku):** схема; **монотонность/ранжирование** (важнее абсолютных чисел): «пусто/UGC»
  выше «занято инструментом»; занятые оба → 0–20, слабые оба → 80–100; гейт-кэп срабатывает при
  профильном инструменте в топ-3 обоих; `competition_*` в 0–100. Один и тот же вход при `temp=0`
  — стабильный ±5.
- **analyze (Opus):** схема (`recommendation/verdict_score/confidence/report_html`);
  `verdict_score` 0–100 и согласован с бакетом (`BUILD≈≥70`…); `report_html` — валидный HTML,
  содержит обязательные секции шаблона (design §8, `templates/report.html`).

**Note (тестируемость + перекалибровка):** детерминированную часть score (блендинг весов +
гейт-кэпы) стоит держать **в коде** задачи `score`, а LLM отдаёт только `competition_yandex/
google` + `signals` + ±10-нюанс. Тогда арифметику score покрывают unit-тесты (§3), а
перекалибровка весов/гейтов (design §3) — чистый код без прогона LLM. Если так — отразить в
`impl §6.3`.

## 6. E2E smoke (`-m live`, бюджет)

Один прогон `drill` на **крошечном** реальном поддереве (узкий узел, десятки фраз):
- доходит до терминалов; каждый лист имеет один из `CATEGORY/INFORMATIONAL/NAVIGATIONAL/
  LOW_SCORED/ANALYZED`;
- у `ANALYZED` есть файл-отчёт + строка `report` + кнопка `Link` (появляется по `report_link`);
- дерево консистентно (нет узлов в «полу-статусе»), лог непустой, задачи `DONE`;
- повторный `drill` идемпотентен (уже-терминальные узлы пропускаются, новых запросов ~0).
Ограничить объём (узкий корень) — это и есть контроль бюджета, потолка нет (design §4).

## 7. Frontend

- **Компоненты/взаимодействие (Vitest+TL):** кнопки по статусу (design §2) — рендерятся только
  разрешённые; `task_id≠null` → узел+поддерево disabled; `Link` виден ТОЛЬКО при `report_link`;
  `Drill`/`Full load` → диалог подтверждения с оценкой; 4 вкладки (Главная/Лог/Task/Отчёты).
- **WS-клиент:** применяет `snapshot`/`node`-дельты; реконнект; `log_cleared` чистит вкладку Лог.
- **Отчёты-вкладка:** список из `report`-событий, сортировка по `verdict_score`, `Link` открывает
  файл в новой вкладке.
- **Smoke (headless-Chrome):** сборка поднимается, дерево грузится по WS, раскрытие работает.

## 8. Инварианты (должны держаться ВСЕГДА — property-style)

1. **FSM:** статус меняется только разрешённым переходом; терминал не имеет операций пайплайна.
2. **No-partial:** `search` пишет обе выдачи либо ни одной; нет узла с одним движком.
3. **Ошибка неразрушающа:** любой упавший шаг → запись в лог + `task=FAILED`, **статус узла
   прежний**, поля результата не затёрты. Ни ретрая, ни отмены.
4. **Идемпотентность:** `migrate`, `load_phrase`, `full_load`, каждая задача и `drill` (резюм) —
   повторный прогон на тех же данных не дублирует и не ломает.
5. **DAG-дедуп:** фраза фетчится один раз; рёбра от каждого родителя; циклов нет.
6. **Только `transactional` продолжает пайплайн;** `informational`/`navigational`/`category` —
   терминалы, в `search`/`score`/`analyze` не попадают.
7. **CQRS:** чтение не мутирует (`expand` ничего не грузит); мутации — только через write-эндпоинты.

## 9. Прогон и CI

- Дефолт (быстро, без сети/LLM): `pytest` (маркеры `live`/`llm` исключены).
- Полный: `pytest -m "llm"` (после изменений промптов) и `pytest -m "live"` (перед релизом,
  вручную, с ключами из `.env`).
- Требуется живой `redis` (тест-инстанция) для части integration — либо `fakeredis`.
- Что НЕ тестируем: корректность самого XMLRiver/выдачи Яндекса, «правильность» суждений LLM за
  пределами рубрики, вёрстку отчёта пиксель-в-пиксель.
