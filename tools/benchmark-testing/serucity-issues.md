# Безопасность: найденное

Файл ведётся отдельно от пользовательских багов намеренно. Обычный посетитель сюда не попадёт —
всё перечисленное достигается запросами к API (Postman, curl, скрипт) или требует особых условий.
Пользовательские дефекты живут в отчётах по `plan.md`, здесь — только безопасность и целостность.

Состояние на 22 августа 2026, продукт `project/destiny-matrix`.

## Обязательно до запуска

### S0. На проде открыт приём мок-оплаты

`MOCK_PAYMENTS=1` в `/srv/arcana/.env`, эндпоинт `POST /api/payments/mock` отвечает на боевом
домене без всякой авторизации.

```
curl -X POST https://arcana-sense.ru/api/payments/mock \
  -H 'Content-Type: application/json' \
  -d '{"tariff":"single","email":"…","birth":"1990-01-01","sex":"f"}'
→ 200, аккаунт создан, платёж «оплачен», право выдано, разбор открыт
```

Любой человек получает платный разбор бесплатно и в любом количестве. Проверено запросом на прод
22 августа.

Пока продукт не запущен и терминал тестовый, это осознанное состояние: платящих нет, терять нечего.
Опасность не в сегодняшнем дне, а в том, что в день запуска про это забудут — сайт уже публичный,
5847 адресов в карте сайта, и «бесплатный доступ одним запросом» разойдётся быстрее, чем первый чек.

**Как закрывать:** `MOCK_PAYMENTS=0` на боевой машине; в коде — отказ `404` вместо `503`, когда мок
выключен, чтобы эндпоинт не выдавал своего существования. Мок оставить только для стенда и для
браузерных сценариев, где он и нужен.

## Чек-лист дня запуска

Проверяется на боевой машине, руками, перед первым живым платежом:

- [ ] `MOCK_PAYMENTS=0`, и `POST /api/payments/mock` отвечает отказом;
- [ ] `TBANK_TERMINAL_KEY` — боевой терминал, не `DEMO`; `PAYMENT_PROVIDER` пуст или `tbank`;
- [ ] закрыты S1 и S2 (оплата по чужой почте и доверие полю `email`);
- [ ] стоят пределы попыток входа и писем восстановления (S3);
- [ ] `ADMIN_PASSWORD` — не тот, что на стенде;
- [ ] тестовые аккаунты и платежи из прогонов снесены из боевой базы;
- [ ] `backup.sh` отработал, копия базы лежит в бакете.

### S1. Оплата по чужой почте отдаёт дату рождения владельца

`POST /api/payments/start` публичный по замыслу (покупка гостем). Если указать чужую почту, ответ
содержит `matrix` с датой рождения владельца и его `user` (id, почта, дата регистрации), а на его
аккаунте создаётся платёж и право.

**Как закрывать:** если почта принадлежит существующему аккаунту и сессии нет — отвечать «войдите»,
ничего не создавая и не возвращая ни `matrix`, ни `user`. Поле почты годится только для
автосоздания нового аккаунта.

### S2. Сервер доверяет полю `email` вместо сессии

При наличии куки платёж всё равно оформляется на аккаунт, указанный в теле запроса. В браузере это
видно как «оплата из старой вкладки ушла предыдущему человеку», через API — как способ пополнить
чужой аккаунт или увести свой платёж на чужой.

**Как закрывать:** есть сессия — платить за её владельца, тело игнорировать; чужая почта при живой
сессии — отказ.

## Важно

### S3. Нет предела попыткам входа и письмам восстановления

`POST /api/auth/login` обрабатывает попытки подряд без задержек (проверено: 30 подряд, все мгновенно).
`POST /api/auth/reset/request` рассылает письма на любые адреса без ограничений — 12 подряд прошли.

Следствия: перебор паролей и сбор базы дат рождения; рассылка нашим доменом с чужих рук — выжженная
суточная квота Postbox (200 писем) и испорченная репутация домена, после чего письма о доступе не
доходят до покупателей.

**Как закрывать:** `limit_req` в nginx по IP для `/api/auth/login` и `/api/auth/reset/request`;
в api — не больше трёх писем на адрес в час и общий потолок на эндпоинт. Капча (SmartCaptcha) —
следующий уровень, если поток станет заметным.

### S4. У админа нет второго фактора, и подбор пароля ничем не ограничен

Компрометация одного админского аккаунта равна утечке всей базы: `/admin` показывает все почты, все
платежи и все даты рождения сразу.

**Как закрывать:** сначала S3 (предел попыток) и сильный пароль в `ADMIN_PASSWORD`, затем второй
фактор для админских адресов.

### S5. Гонка на записи: дубли, обход лимита, двойная продажа

Два параллельных запроса проходят проверку «такой даты нет» и «лимит свободен» раньше, чем любой из
них записал строку. Итог: две записи одной даты у аккаунта с лимитом в одну, и каждая продаётся
отдельно — проверено, 500 ₽ за одну и ту же дату. На живом эквайринге те же два запроса дают два
платежа по 250 ₽ (2 прогона из 2).

Человеку в браузере это недостижимо: кнопки блокируются на время запроса. В Postman — одна кнопка.

**Как закрывать:** уникальное ограничение `(user_id, birth, sex)` и обработка конфликта как «нашли
существующую запись»; проверку «дата уже открыта» вести по дате с полом, а не по номеру записи.

### S6. Гонка на печати

Два параллельных `POST /api/reports/pdf` дают два рендера и два файла в хранилище. Цена — процессор
и место, данные не портятся.

**Как закрывать:** блокировка по «пользователь + матрица»: пока задача в работе, отдавать её, а не
запускать новую.

## Проверено и в порядке

- уведомление провайдера без верной подписи отклоняется (`403`), подпись считается тем же кодом, что её проверяет;
- повторные уведомления не выдают второго права; возврат снимает право;
- печать закрытой (неоплаченной) даты — `402`, чужая матрица — `404`;
- служебная страница печати без пропуска — `404`; пропуск действует две минуты и только на одну матрицу;
- `/admin/*` посторонним — `404` (не `403`: существование админских адресов не раскрывается);
- ссылка на готовый PDF подписана и живёт час, бакет закрыт от анонимного чтения;
- `noindex` на `/report`, `/account`, `/pay`, служебных страницах;
- секреты не в репозитории: ключи в `~/.config/arcana/*` и в `/srv/arcana/.env`, в git — только примеры.
