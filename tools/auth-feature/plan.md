# Авторизация через внешних провайдеров (VK / Одноклассники)

Разбор проекта `project/destiny-matrix` и план добавления входа через соцсети с учётом
российского законодательства.

## Что есть сейчас

Один способ входа — **email + пароль**. Токен — JWT в httpOnly-куке `destiny_session`
(в JS недоступен, в localStorage не попадает). Ключевые свойства:

- **Email — универсальный якорь всего продукта:** регистрация, автосоздание аккаунта при
  оплате (`api/app/routers/payments.py:57-60`, `_buyer` заводит `User` по email со случайным
  паролем), список админов (конфиг), сброс пароля. `users.email` — `unique NOT NULL`,
  `password_hash` — `NOT NULL`.
- **JWT привязан к отпечатку пароля** (`pwd = fingerprint(password_hash)`, `api/app/security.py:32`):
  смена пароля гасит все сессии. Механизма гашения без пароля нет.
- **BFF-поток чисто JSON:** `forward/capture` в `web/app/api/_lib/upstream.ts` забирает `token`
  из ответа api и ставит куку. Редирект-флоу OAuth сюда не ложится как есть.
- **Схема аддитивная:** новые таблицы — через `create_all`, новые колонки — через
  `add_missing_columns()` (ALTER, `api/app/schema.py:36`). Ронять ничего не надо.

Хостинг: домен `arcana-sense.ru`, Yandex Cloud `ru-central1`, почта Yandex Postbox, эквайринг
Т-Банк. **Это однозначно российский ресурс.**

## Юридическая часть

Закон реальный: **ФЗ-406 от 31.07.2023** внёс поправки в **ФЗ-149 «Об информации»** (ст. 10),
**действует с 01.12.2023**. Российский сайт/сервис может авторизовывать пользователей **только**
через:

1. номер телефона (оператор РФ);
2. Госуслуги (ЕСИА);
3. Единую биометрическую систему (ЕБС);
4. **иную ИС, принадлежащую гражданину/юрлицу РФ с данными на территории РФ**.

По провайдерам:

| Провайдер | Статус | Почему |
|---|---|---|
| **VK ID** | ✅ можно | рос. юрлицо, данные в РФ |
| **Одноклассники** | ✅ можно | холдинг VK |
| **Яндекс ID, Mail ID, Сбер ID, T-ID** | ✅ можно | рос. ИС |
| **email + пароль (ваш)** | ✅ можно | вы сами — рос. ИС, данные в Yandex Cloud РФ |
| **Google, Apple** | ❌ нельзя | иностранная ИС |
| **Facebook/Instagram** | ❌ нельзя | вдобавок Meta признана экстремистской в РФ |
| **Telegram** | ⚠️ серая зона | не рос. юрлицо, данные не в РФ — как явный «вход через» не рекомендуется |

Ответственность — через РКН/КоАП (штрафы, вплоть до блокировки). Точные суммы штрафа уточнить
у юриста; сам **запрет действующий**.

### Нужны ли две логики для РФ и Казахстана/СНГ?

**Нет.** Закон применяется к сервису, **доступному из РФ**, независимо от местоположения
пользователя. Сервис российский → закон действует на всех.

- Один набор рос.-совместимых провайдеров (VK / OK / Яндекс / email) **закрывает и РФ, и весь
  СНГ** — VK и Яндекс популярны в Казахстане, Беларуси, Средней Азии. Отдельная логика не нужна.
- **Гео-ветвление «Google для не-РФ» не рекомендуется:** не даёт надёжной защиты (VPN, ошибки
  IP-геолокации), а ресурс всё равно российский — риск остаётся. Сложность высокая, выгода
  почти нулевая.
- Google/Apple имели бы смысл **только** под заметную дальнезарубежную аудиторию — тогда это
  отдельное решение с юристом. По умолчанию — **не добавлять, гео-ветвление не строить.**

**Рекомендация по составу:** VK ID (обязательно) + Одноклассники (аудитория 35+ женщины совпадает
с «матрицей судьбы») + опционально Яндекс ID. Email/пароль оставить.

## Технические сложности именно в этом коде

Главное — не «прикрутить кнопку», а пять мест трения:

1. **OAuth часто не отдаёт email, а на нём держится всё.** VK/OK возвращают email только если он
   есть у пользователя и тот дал разрешение; часто приходит только телефон или ничего. Нельзя
   просто `User(email=...)`. → нужна таблица `identities (provider, provider_uid, user_id)`; при
   отсутствии email — экран дозаполнения email на первом входе.
2. **JWT завязан на отпечаток пароля, а у OAuth-юзера пароля нет.** `password_hash NOT NULL`.
   → добавить `users.token_version` и гасить сессии по нему; `password_hash` сделать nullable.
3. **OAuth — редирект-флоу, а не JSON POST.** Новые маршруты `start`/`callback`; `client_secret`
   держать на FastAPI (не в Next); backend обменивает код → профиль → upsert user+identity →
   выдаёт **тот же** app-JWT → BFF ставит **ту же** куку `destiny_session`. Модель «токен в
   httpOnly-куке» сохраняется, ломать ничего не надо.
4. **Слияние с оплатой.** Купил по email → вошёл через VK с тем же email → должен попасть в тот
   же аккаунт. Без email авто-слияние невозможно → дубль и «оплатил, но доступа нет». Нужна
   стратегия matching по email + ручная привязка в кабинете.
5. **Согласие на ПД.** Сейчас чекбокс в форме (`web/components/AuthForm.tsx:77`). У OAuth-кнопки
   его нет — согласие всё равно обязательно. → текст «Нажимая, принимаете политику и оферту» рядом
   с кнопками до редиректа.

## Раздел 0 — что достать по провайдерам (заполнить перед реализацией)

Здесь два приложения: **VK ID** (даёт VK + Одноклассники + Mail разом) и **Яндекс ID**
(отдельная система). Значения вписывать в поля ниже.

> ⚠️ **Секреты (`client_secret`) в этот файл коммитить нельзя** — это утечка. В доке держать
> только локально/незакоммиченно; в приложение они попадают через `.env` / переменные окружения,
> не через репозиторий. `client_id`, `redirect_uri`, `scopes` — не секретны, их вписывать можно.

Callback ведёт на фронт (BFF ставит куку). Адреса:

- prod: `https://arcana-sense.ru/api/auth/oauth/<provider>/callback`
- dev: `http://localhost:<порт фронта>/api/auth/oauth/<provider>/callback`  ← уточнить порт локального Next

## Подготовительный рефакторинг (до реализации, отдельным коммитом)

Большого рефактора не нужно — структура ложится хорошо. Но две мелочи сделать заранее:

1. **Единый хелпер «найти-или-создать пользователя + выдать токен».** Сейчас создание `User`
   живёт в двух местах — `auth.register` и `_buyer` (`api/app/routers/payments.py:56`). OAuth
   станет третьим. Без общего хелпера логика создания расползётся копипастой по трём местам.
   Выделить один источник правды **до** добавления провайдеров.

2. **BFF-роуты OAuth — статическими файлами на каждого провайдера**
   (`web/app/api/auth/oauth/vk/start`, `.../vk/callback`, `.../yandex/start`, `.../yandex/callback`),
   а не динамическим сегментом `[provider]`. Причина в самом коде — комментарий в
   `web/app/api/_lib/routes.ts`: динамический сегмент в `/api/auth` уезжает мимо BFF из-за порядка
   rewrites (файловые маршруты проверяются до динамических, но rewrites — после файловых). Повторяем
   приём остального auth: по файлу на провайдера.

## План внедрения

- **Этап 0 — решения (нужны от владельца):** состав провайдеров; регистрация VK ID / OK как
  приложений (нужны юрлицо, домен, redirect_uri, модерация — внешний срок); политика email-less
  аккаунтов.
- **Этап 1 — модель:** таблица `identities`, `users.token_version`, `password_hash` → nullable,
  перенос гашения сессий с отпечатка пароля на `token_version`.
- **Этап 2 — backend:** конфиг `client_id/secret` по провайдерам; сервис обмена кода и получения
  профиля; upsert user+identity; выдача JWT.
- **Этап 3 — BFF:** маршруты `/api/auth/oauth/{provider}/start|callback`, state/PKCE в куке,
  установка `destiny_session`.
- **Этап 4 — фронт:** кнопки провайдеров на `/login` и `/register`, экран дозаполнения email,
  согласие ПД у кнопок.
- **Этап 5 — кабинет:** привязка/список привязок в `web/components/AccountView.tsx`.
- **Этап 6 — тесты:** контрактные (callback, upsert, слияние по email, email-less), e2e с моком
  провайдера.

**Главный риск не в коде, а в email-less аккаунтах и их слиянии с оплатой** — продумать до
реализации.
