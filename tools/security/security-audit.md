# Журнал безопасности (`security_audit`)

Служебный журнал попыток аутентификации: кто, откуда и с каким исходом пытался войти,
зарегистрироваться или сбросить пароль. Виден только админу. Нужен, чтобы **видеть перебор**
до того, как он что-то вскроет, и разбирать инциденты постфактум.

Таблица живёт в базе приложения `destiny-matrix` (SQLAlchemy, `api/app/models.py`). Новую
таблицу подхватывает `create_all` (`api/app/schema.py`), миграция не нужна.

## Схема таблицы

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | int, PK | — |
| `at` | datetime (UTC), индекс | когда произошло событие |
| `action` | str(16) | что пытались: `login` / `register` / `reset` |
| `outcome` | str(16), индекс | исход: `success` / `failed` / `throttled` |
| `email` | str(320), индекс, nullable | адрес-субъект попытки (по нему видно, какой аккаунт перебирают) |
| `ip` | str(64), nullable | адрес источника, best-effort |

Индексы на `at`, `outcome`, `email` — под выборки админки (фильтр по исходу, сортировка по
времени, поиск по аккаунту).

### Про почту и IP

- **`email` хранится намеренно** — в отличие от `error_log`, где ПД нет сознательно. Здесь адрес
  и есть смысл журнала: без него не видно, какой аккаунт под перебором. Журнал admin-only, почты
  и так видны в остальных разделах админки.
- **`ip` — best-effort.** За `nginx → BFF → FastAPI` реальный адрес клиента приедет только когда
  добавят проброс `X-Forwarded-For` (см. `tools/security/bruteforce-plan.md`, контракт реального
  IP). До этого в колонке может быть адрес прокси. Колонка заведена заранее, чтобы схема была
  готова.

## Что логируем

Три исхода на каждое из трёх действий:

| `action` \ `outcome` | `success` | `failed` | `throttled` |
|---|---|---|---|
| `login` | верный пароль | неверный пароль или неизвестная почта | отсечён лимитом |
| `register` | создан новый аккаунт | почта уже занята | отсечён лимитом |
| `reset` | адрес найден, письмо отправлено | адрес не найден | отсечён лимитом |

- `success` / `failed` пишутся **сейчас** — из хендлеров `api/app/routers/auth.py` через
  `api/app/audit.py` (отдельная сессия, чтобы отметка ставилась и на отказе, и не роняла ответ).
- Исход `reset` журналируется **внутренне**: наружу ответ по-прежнему одинаков для существующей и
  чужой почты (перечисление не течёт), но в журнал пишется реальный исход.
- `throttled` пишет слой ограничения частоты (L2 из `bruteforce-plan.md`), когда он будет
  добавлен; хелпер `audit.record` уже принимает этот исход.

## Ретенция

Автоочистки нет — при низком трафике мелкого сайта таблица растёт медленно, а полная история
попыток ценна для разбора инцидентов. Если понадобится — добавить обрезание по возрасту/числу
строк по образцу `errors._trim`. Именно из-за роста выдача в админке постраничная.
