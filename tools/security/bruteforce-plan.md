# Защита от перебора (login / register / reset)

План простой многоуровневой защиты от перебора для трёх auth-ручек проекта
`project/destiny-matrix`. Цель — **обрубить банальщину, которая реально прилетает мелкому
сайту, минимумом кода и без влияния на живого пользователя**. Не «защита на все случаи
жизни»: осознанно закрываем распространённое, редкое и дорогое оставляем за скобками.

## Что защищаем и от чего

| Ручка | Что такое «перебор» тут | Ущерб |
|---|---|---|
| `POST /api/auth/login` | подбор пароля к аккаунту | угон (доступ к оплаченным отчётам) |
| `POST /api/auth/reset/request` | долбёж запросами на один адрес | письма = деньги SMTP + репутация домена |
| `POST /api/auth/register` | перечисление: какие почты зарегистрированы | приватность + список целей, спам-аккаунты |

Сейчас защиты **нет вообще**: ни в приложении, ни в nginx (`limit_req`/`limit_conn` — пусто),
ни fail2ban, ни WAF/CDN спереди.

## Архитектура (важное для плана)

- Единая дверь — nginx (`infra/nginx/arcana.conf`), всё уходит на Next-BFF (`127.0.0.1:3000`).
  FastAPI (`:8010`) наружу не смотрит — прямого пути к auth-ручкам из интернета нет.
- Браузер ходит только на свой origin `/api/*`; BFF форвардит на FastAPI.
- FastAPI — один процесс uvicorn (без `--workers`), Redis нет → in-memory состояние безопасно
  (паттерн уже используется: `api/app/presence.py`).
- Auth-хендлеры — `api/app/routers/auth.py`: `register` (стр. 22), `login` (стр. 40),
  `reset/request` (стр. 68). Хеш пароля — `bcrypt_sha256` (сам по себе медленный).

## Три уровня

Уровни независимы, каждый бьёт свой класс. Простейший (ноль кода) — первый.

### L1 — грубый: `limit_req` в nginx по IP

Отсекает основную массу — тупой скрипт, долбящий с одного/нескольких IP. **Ноль кода в
приложении**, ~10 строк конфига (деплой штатным скриптом). Не трогает страницы/404 — только
auth-ручки, поэтому прежней логике «глобальный лимит вреден» (`conf.d/arcana-filters.conf`)
не противоречит.

Итоговые лимиты — единообразно на все три ручки:

```
login          5r/m  burst 5
register       5r/m  burst 5
reset/request  5r/m  burst 5
```

- `5r/m` = 1 запрос раз в 12 с (установившийся темп на IP).
- `burst 5` = всплеск до 5 подряд мгновенно, потом жёсткое 1/12с. Подушка под
  почти-одновременные легитимные запросы (двойной клик, перезагрузка+ресабмит, две вкладки,
  двое за одним NAT). Живого не задевает.
- Обязательно `nodelay` (иначе лишнее не отбрасывается, а задерживается очередью → лаг живому)
  и `limit_req_status 429` (дефолт 503 семантически неверен).

Скетч (зона — в http-контексте `conf.d/`, локации — в server-блоке `arcana.conf`):

```nginx
limit_req_zone $binary_remote_addr zone=auth:10m rate=5r/m;
limit_req_status 429;

location = /api/auth/login         { limit_req zone=auth burst=5 nodelay; proxy_pass http://127.0.0.1:3000; }
location = /api/auth/register      { limit_req zone=auth burst=5 nodelay; proxy_pass http://127.0.0.1:3000; }
location = /api/auth/reset/request { limit_req zone=auth burst=5 nodelay; proxy_pass http://127.0.0.1:3000; }
```

Хвосты, чтобы не сломать: в каждую локацию продублировать `proxy_set_header` как в текущем
`location /`; свериться с фактическими путями BFF (`web/app/api/auth/**/route.ts`); для IPv6
(nginx слушает `[::]:80`) ключевать по **/64** через `map`, иначе бот крутит младшие биты
адреса.

### L2 — точный: счётчик по email в FastAPI

Ловит то, что IP-лимит пропускает: одну цель долбят, меняя IP. **Ключ — email из тела
запроса**, не IP — поэтому не нужен проброс реального IP через nginx→BFF (упрощение), и бонусом
бьётся распределёнка (IP меняют, аккаунт-цель один).

- Механизм: один мелкий in-memory модуль (напр. `api/app/throttle.py`), словарь
  `email → метки времени`, скользящее окно + порог, чистка старых ключей. Паттерн как
  `presence.py`. Пороги — в `api/app/config.py`, env-override.
- `login`: **5 неудач** на email за 15 мин → `429`; **успех обнуляет** ключ.
- `reset/request`: **6 запросов** на email за час → `429`.
- Считать по **любому** присланному адресу (есть он в базе или нет) — тогда `429` не начинает
  отличать существующие почты от чужих и не становится оракулом перечисления.

Влияние на живого: упрётся только тот, кто сам 5 раз промахнулся паролем → видит «повторите
через N минут или сбросьте пароль» (это же подталкивает к сбросу, а не к бесконечному гаданию).

### L3 — гигиена `register`

Перебор здесь = перечисление, «какие почты существуют». Лимитом не чинится — только формой
ответа. Сейчас `register` палит существование: `«Эта почта уже зарегистрирована»`
(`auth.py:23-24, 29-31`), тогда как `reset/request` существование сознательно скрывает.

- Правка: `register` всегда отвечает одинаково (`200 «проверьте почту»`), а разница
  («добро пожаловать» / «у вас уже есть аккаунт») уходит **в письмо** — как уже сделано в reset.
- Затрагивает один хендлер (`auth.py:register`) + ветку письма (`api/app/mail.py`).
- Юзер не видит ничего.

## UX ошибки 429 (общее)

`429` **не** должен быть тихой ошибкой в консоли. Форма уже показывает `ApiError`
(`web/components/AuthForm.tsx`, `web/components/ForgotForm.tsx`, `web/lib/api.ts`) — нужно лишь
вернуть на `429` человеческий `detail` + заголовок `Retry-After` (из него берётся «через N
минут»). Нового механизма не требуется.

## Что этот план даёт (обоснование чисел)

- **Вскрыть конкретный аккаунт — практически 0.** L2 держит 5 попыток / 15 мин = **480/сутки на
  аккаунт**, независимо от числа IP. Против нормального пароля (даже слабый 8-значный ≈ 2·10¹¹
  вариантов) это ~10⁹ лет. Целевой подбор мёртв.
- **С одного IP — 5/мин = 7 200/сутки**, но их нельзя слить в один аккаунт (L2). Годятся только
  на спрей вширь; на мелкой базе один IP за день-другой проходит частыми паролями по всем — но
  находит **только слабые пароли**.

## Что осознанно НЕ входит

Это <10% для мелкого сайта либо не чинится rate-limit’ом в принципе:

- **кука «пришёл через браузер»** — не ограничивает перебор (один GET и реплей), это фильтр
  шума, не защита от подбора;
- **капча** — нужна как эскалация против headless/solve-ферм, для банальщины избыточна;
- **распределённый спрей** (один пароль × тысячи аккаунтов × тысячи IP) — L2 по email почти не
  видит, L1 по IP обходится ротацией; настоящая защита тут — качество пароля / 2FA, а не лимиты.

## Отдельная задача (НЕ этот план, но зафиксировать)

**DoS через bcrypt-усиление.** `register` на каждый свежий email безусловно зовёт
`hash_password` (bcrypt, десятки мс CPU), без авторизации. Хендлеры — sync `def` → крутятся в
threadpool (~40 потоков); на маленькой машине несколько десятков параллельных
`POST /register` со случайными email кладут CPU и подвешивают весь API. Лечится порядком
«проверка лимита до bcrypt» + L1, но это **защита от DoS, а не от перебора** — отдельная задача.

## Порядок внедрения

Уровни независимы. По убыванию «выхлоп на усилие»:

1. **L1** — nginx (ноль кода, максимум покрытия).
2. **L2** — счётчик по email.
3. **L3** — гигиена `register` + человеческий `detail`/`Retry-After` на 429.
