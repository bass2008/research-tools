# План доработок сайта под SEO (код, не контент)

Тексты статей — отдельный фронт (`article-plans/`, пишут копирайтеры/LLM). Здесь — **что нужно
сделать в приложении**: роуты, шаблоны, схема данных, техническое SEO, пайплайн «текст → страница».

**Короткий ответ:** да, сайт допиливать надо. Часть работ (раздел 1) не зависит от контента и
чинит домен уже сейчас; часть (2–4) обслуживает новые категории и обогащение.

---

## 1. Техническое SEO — делать в любом случае (не ждёт контента)

- **Матрица день-месяц-год (5544):** проставить `noindex, follow` и убрать из `sitemap.ts`
  (оставить как страницу результата + перелинковку). Сейчас все 5544 в карте сайта — это массив
  почти-дублей, тянет домен вниз.
- **Schema:** добавить `BreadcrumbList` во все шаблоны (крошки визуально есть, разметки нет) и
  `FAQPage` там, где будет блок Q&A. Сейчас только `Article` местами.
- **Арканы — title/H1:** шаблон под точную форму «N в матрице судьбы» (сейчас H1 = только имя
  аркана). Правится в `lib/encyclopedia.ts`/генераторе SEO.
- **Калькулятор (CalcPromo) на все инфо-шаблоны:** сейчас `CalcPromo` стоит только на странице
  аркана; на чакрах, сочетаниях и позициях входа в расчёт нет — инфо-трафик уходит без действия.
  Добавить компонент в `chakra/[key]`, `combination/[pair]`, `position/[key]` (~3 файла). Конверсия,
  не SEO, но content-independent и дёшево.
- **Sitemap:** пересобрать под новые категории (хвосты, на год, хабы), убрать матрицы.
- **Robots / canonical** — перепроверить после изменений.
- **Ops (из `plan.md` P0):** Яндекс.Вебмастер + Google Search Console, отправка sitemap,
  Метрика с настоящим ID и целями. Частично дев, частично администрирование.

## 2. Новые типы страниц — роут + шаблон + данные (под новые категории)

- **Кармические хвосты:** роут `/encyclopedia/karmic-tail/[triple]` + хаб
  `/encyclopedia/karmic-tail`. До кода — решить URL-схему и канонический порядок тройки
  (иначе один хвост = два URL). + sitemap + перелинковка + источник данных (JSON троек).
- **Матрица судьбы на год:** хаб `/na-god` + `/na-god/[n]` (22 «аркана на год») + страница
  год-штампа. Если нужен калькулятор персонального года — интеграция в расчёт. + данные.
- **Концепт-хабы:** статические роуты `/programmy`, `/karmicheskaya-matrica`, `/energii` и т.п.
  + данные/контент.

## 3. Обогащение существующих шаблонов (дев-часть под контент арканов/позиций)

- **Арканы:** расширить модель контента — поле `faq[]`, отдельные секции под грани спроса
  («в отношениях/совместимость» 33k, «деньги», «в центре»); шаблон под новые секции; `FAQPage`;
  кросс-ссылка на «N на год». Сами тексты — контент, но **поля и разметку добавляет код**.
- **Позиции:** место в шаблоне под расширенный текст.

## 4. Контент-формат — схема данных категории (не «разрыв»)

Разрыва нет: статьи пишутся **сразу как JSON по схеме категории** (проза в полях, шаблон строит
вёрстку/ссылки/схему — см. `article-requirements.md` Часть D). Markdown в `tools/seo/out/*.md` —
только предпросмотр для ревью.

Дев-задача — при постройке каждого нового шаблона **задать его схему контента и загрузчик**
(в семье `content/*.json`): какие поля (`seo`, `short`, `sections[]`, `faq[]`, `related[]`) и откуда
берётся файл. То есть это часть раздела 2, а не отдельный конвертер.

### 4.1. Хранение — вариант A (принято): JSON в репозитории

Контент read-only и почти статика — **БД не нужна**. Храним как сейчас: `content/*.json` в репо,
Next читает их **на сборке** (`generateStaticParams`) и выдаёт статические страницы. Ноль новой
инфраструктуры.

- **Жёсткое правило:** рендер только на сборке/сервере (SSG). **Никаких клиентских `fetch` за JSON** —
  иначе краулер получит пустой HTML и SEO умрёт. S3/CDN может раздавать уже готовый HTML, но не
  быть источником данных для браузера.
- **Контент вшит в артефакт сборки:** `content/*.json` копируется в `.next/standalone/content/`,
  то есть запекается в **образ web** (или standalone-бандл при rsync-деплое). Плюс `api.Dockerfile`
  делает `COPY web/content` — контент дублируется **и в образ api**. Следствие: **публикация статьи =
  пересборка + редеплой** (в Docker — обоих образов). По размеру ок (там уже `matrices.json` 11,5 МБ).
- **S3 (вариант B) — на будущее:** JSON в S3, билд забирает на сборке (или ISR revalidate). Уходит
  от пересборки образа на каждую статью. Осмыслен, когда статьи публикуются часто и отдельно от кода.
  Сейчас не нужен.
- Динамическое ядро (калькулятор, авторизация, оплата, админка) остаётся на Python-API + БД — это к
  контенту не относится.

### 4.2. Что обновить в пайплайнах под новую категорию

1. **Данные:** завести `content/<категория>.json` (напр. `content/karmic-tails.json`) — массив `items`
   по схеме категории; статьи из пайплайна дописываются сюда объектами (Часть D).
2. **Загрузчик:** функция в `lib/` — читает файл, отдаёт item по `key` (в духе `lib/content.ts`).
3. **Роут + шаблон:** `generateStaticParams` из ключей файла + TSX, который строит вёрстку, ссылки,
   `CalcPromo` и JSON-LD из полей.
4. **Sitemap:** добавить ключи категории в `sitemap.ts`.
5. **Сборка/деплой:** контент едет с кодом — изменение `content/*.json` требует `npm run build` +
   деплой. Отдельного шага «залить контент» нет.
6. `tools/seo/out/*.md` в пайплайн не входит — это предпросмотр для ревью.

## 5. Развилки, которые гейтят дев

- **URL-схема хвостов** и канонический порядок тройки (блокер раздела 2).
- **Формула хвоста** (движок считает `[год, наследие, сумма]`, а ниша ищет другие тройки) —
  нужна сверка, если хотим, чтобы калькулятор показывал тот же хвост, что ищут.
- **Нужен ли расчёт «персонального года»** в калькуляторе — от этого зависит объём работ по
  категории «на год».

## Порядок

1. **Тех-SEO (разд. 1)** — не ждёт контента, чинит домен: noindex матриц, schema, title арканов, sitemap, вебмастеры.
2. **Обогащение арканов (разд. 3)** — топ-приоритет по трафику (505k).
3. **Новые категории (разд. 2)** — хабы → на год → хвосты; схему контента (разд. 4) задаём при постройке каждого шаблона, после развилок разд. 5.
