# Переезд Arcana Sense на единый домен

План составлен 29.10.2026. Приоритет — сохранение русского поискового трафика из Яндекса.
Ожидание индексации Google не блокирует этапы. Сохраняем корректные общие SEO-сигналы
для всех поисковиков.

Чекбоксы отмечаются только после фактического выполнения и записи результата проверки.
Этот документ содержит план и текущий статус со ссылками на доказательства. Сам по себе
он не разрешает новые релизы или изменения инфраструктуры.

Итоговая структура:

```text
https://arcana-sense.com/ru/       — русская главная
https://arcana-sense.com/ru/…      — русские публичные страницы
https://arcana-sense.com/en/       — английская главная
https://arcana-sense.com/en/…      — английские публичные страницы
https://arcana-sense.com/          — 301 на /ru/ по умолчанию
```

Нейтральная страница выбора языка в план не входит. На страницах остаётся доступный
переключатель языка. Язык публичного HTML определяется URL, без принудительного выбора
по IP, cookie или User-Agent.

Оценка активной работы — примерно 6–10 рабочих дней, распределённых между этапами.
Сроки предварительные: объём доработок платёжных и служебных маршрутов уточняется при
подготовке. Оценки Release 2 и 3 предполагают заранее подготовленную и проверенную
реализацию; дополнительные исправления в них не включены. Календарный срок зависит от
обработки Яндексом и может составить несколько месяцев.

### Яндекс: что известно и что неизвестно

1. Неисправность подтверждена **для POST постановки на переобход через API**: 504 на старый
   и на новый URL. GET чтения работает, но свежесть данных неполная. Состояние веб-интерфейса
   не проверено; говорить, что весь Вебмастер или индексирующий робот остановлен, нельзя.
2. Принятых заданий не подтверждено: **0/85**. Попытки сделаны для пары
   `/encyclopedia/chakra/energy-field` и `/ru/encyclopedia/chakra/energy-field`.

   неопределённость обработки запроса, поэтому перед повтором сверить очередь.
3. Sitemap уже зарегистрирован. API показывает обход от 01.10 и 460 URL вместо нынешних 336.
   Не выдавать это за актуальное состояние карты на сайте и не удалять/добавлять её вслепую.
4. Ручной переобход помогает сообщить об изменениях, но не является обязательным условием
   обнаружения 301. При обычном посещении старой страницы робот может прочитать редирект
   и перейти на новый URL. [Справка Яндекса](https://yandex.ru/support/webmaster/ru/yandex-indexing/removing-from-index).
5. **Фактические заходы подтверждённого YandexBot после релиза пока не исследованы.** Это
   ближайшая отдельная проверка серверных access-логов. Старые отчёты API не заменяют её.
   HTTP 200/301 и даже посещение робота сами по себе не доказывают включение нового URL в поиск.
6. Причина 504 неизвестна; связь с атаками или авариями ЦОД не проверялась.

## Этапы 2–3. Реализация и тестовое окружение

По уточнению пользователя языковые префиксы распространяются на все пользовательские
страницы, включая кабинет, вход, оплату, разборы и печать. Исключения — технические
маршруты API, банковские callback, статика, health, version, robots и sitemap; русская
главная пока остаётся в корне. На всех пользовательских страницах оба языка доступны на текущем домене,
чтобы переключение сохраняло сессию и платёжный профиль. Старые приватные URL дают 302
на языковой путь с сохранением параметров; префикс имеет приоритет над `?lang=` и cookie.
Новые письма и банковские возвраты сразу используют языковые пути.

Подготовить:

- серверный HTML нужного языка, метаданные, OpenGraph и структурированные данные;
- canonical на актуальный адрес страницы и взаимные `hreflang` только для существующих
  переводов; согласованное назначение `x-default` для каждой фазы;
- внутренние ссылки, хлебные крошки, переключатель языка и ссылки из калькуляторов;
- sitemap только с актуальными индексируемыми URL, отвечающими 200;
- robots и `noindex`: запреты должны учитывать новые префиксы, а персональные страницы
  не должны случайно открыться для индексации; старые публичные URL с редиректами доступны роботу;
- обработку исторических ссылок, параметров расчётов и платёжных возвратов без потери данных;
- корректное разделение API, банковских уведомлений, статических файлов и публичных URL.

Платёжные заказы хранят исходный `site_origin`, а обработчики уведомлений проверяют профиль
сайта и адрес callback. Нельзя просто удалить профиль `.ru` или перенаправить POST банка
на другой домен. Сохранить возможность обслуживать старые заказы, повторные уведомления,
возвраты и проверку статуса. База аккаунтов и покупок общая, но браузерные cookie между
`.ru` и `.com` не переносятся: существующему пользователю может потребоваться повторный вход.

**Проверка перед Release 1:**

- Все URL карты проверены автоматически: назначение, статус, отсутствие циклов и ошибочного языка.
- Проверены все sitemap URL и исключения robots, выборочно — HTML и canonical всех типов страниц.
- Проверены расчёт, смена языка, регистрация/вход, сохранённые разборы и PDF. Письма на тесте
  проверяются в логе: текст, адрес назначения, локализованные ссылки и их работа;
  доставка настоящих писем в ящик не входит в согласованный объём приёмки.
- На тестовом эквайринге проверены покупка, отказ/отмена, возврат из банка и уведомление;
  старые заказы доступны. Не создавать реальные списания ради проверки без отдельного разрешения.
- Неизвестные адреса сохраняют 404; тестовый стенд закрыт от индексации.
- Пройдены штатные проверки проекта, относящиеся к изменениям, и обязательный release gate.

Каждый релиз проходит тест → проверку → production → проверку. Использовать существующий
release workflow. Не менять CI/CD, зависимости, аналитику, эквайринг, дизайн и тексты статей
ради миграции. Не повторять уже успешный длительный прогон на неизменённом коде только
ради нового отчёта: использовать имеющееся evidence согласно AGENTS.md.

## Release 1. Языковые пути

Публичные русские внутренние страницы:

```text
.ru/encyclopedia/arcanum/4 → 301 → .ru/ru/encyclopedia/arcanum/4 → 200
.ru/                     → 200, прежняя русская главная
```

Русскую главную `/ru/` пока не публиковать второй индексируемой копией: при обращении
к `.ru/ru/` направлять временным 302 на `.ru/`. Это исключение позднее меняется в Release 3.

Английские страницы:

```text
.com/encyclopedia/arcanum/4 → 301 → .com/en/encyclopedia/arcanum/4 → 200
.com/                     → 302 → .com/en/ → 200
```

Для английской главной используется временный 302: в Release 2 корень `.com/` займёт
русская главная. Не выдавать это временное назначение корня за постоянный редирект.
Старые английские внутренние адреса сохраняют 301 в `/en/` и после следующих релизов.

**Сразу после публикации:**

- Проверить production по той же карте URL и выполнить короткую проверку основных сценариев.
- Проверить главные, robots, sitemap, canonical, `hreflang`, отсутствие запрета индексации.
- Проверить, что внутренние ссылки ведут сразу на новые адреса, а не через редиректы.
- Убедиться, что существующие счётчики и цели продолжают работать, не создавать новые события.
- Обновить sitemap в Вебмастере; отправить контрольные новые URL на переобход в пределах квоты.
- Зафиксировать дату и время переключения. Первые дни проверять ошибки и переходы ежедневно.

## Release 2. Смена домена

```text
.ru/ru/encyclopedia/arcanum/4 → 301 → .com/ru/encyclopedia/arcanum/4 → 200
.ru/                        → 301 → .com/ → 200, прежняя русская главная
.com/en/…                   → 200, английская версия без изменений
```

На `.com/ru/` временно сохранить 302 на `.com/`, пока русская главная находится в корне.
Старые непрефиксные русские адреса сохраняют работоспособность, например:

```text
.ru/encyclopedia/arcanum/4 → 301 → .com/ru/encyclopedia/arcanum/4
```

В Release 2 старые публичные адреса направлять сразу на конечный URL, без дополнительного
перехода через `.ru/ru/…`, как указано в карте всех фаз. Не направлять старый русский
адрес на `.com/encyclopedia/arcanum/4`: этот адрес принадлежал английской версии и ведёт в `/en/`.
Фактические цепочки для более старых URL заранее перечислить и проверить на отсутствие циклов.

**Публикация и проверки:**

- Сначала обеспечить готовность новых `.com/ru/…`, затем согласованно включить редиректы
  и новые ссылки/метаданные. Не оставлять период с редиректами на несуществующие страницы.
- На `.com/` сохранить содержание и функции прежней русской главной, а не страницу выбора языка.
- Проверить совпадение содержания каждой пары русских страниц; меняются адреса, а не статьи.
- На `.com` включить согласованные способы оплаты и юридический профиль русского сценария;
  не считать наличие русского перевода подтверждением готовности оплаты.
- Проверить старые заказы, callback на `.ru`, повторный вход на `.com`, доступ к покупкам,
  письма и банковские возвраты. Не обещать автоматический перенос браузерной сессии.
- Проверить robots обоих доменов: робот должен читать старые редиректы и новые страницы.
  Не закрывать `.ru` через `Disallow: /` или `noindex` вместо перенаправления.
- Обновить sitemap, ссылки и языковые альтернативы на новые адреса.
- Из ресурса `.ru` отправить заявку `.ru` → `.com` в инструменте «Переезд сайта» Яндекса.
  Проверить результат валидации и сохранить статус заявки.
- Если заявка отклонена, разобраться с конкретной причиной. Не удалять все canonical
  вслепую и не запускать Release 3 в обход проблемы.

После Release 2 показатели русского трафика собирать по старому и новому доменам вместе.
Счётчики привязаны к доменным профилям: падение старого счётчика само по себе ожидаемо.
Проверить непрерывность существующих целей; исторические ряды не переписывать.

## Этап 7. Допуск к Release 3

**Все обязательные условия:**

1. Вебмастер подтверждает, что `.com` стал главным адресом, а `.ru` — неглавным.
   Одного факта отправки или принятия заявки недостаточно.
2. Новая русская главная `.com/` и страницы контрольного набора `.com/ru/…` участвуют
   в поиске Яндекса. Поисковые переходы на новый домен подтверждены Метрикой.
3. После подтверждения нового главного адреса прошло не менее двух полных недель
   наблюдений без критических технических проблем. Проверены сумма переходов на оба
   домена и наиболее важные посадочные.
4. Нет необъяснённого устойчивого падения по тому же правилу 20% за две недели подряд.
   Для этой фазы исходный уровень — последние две полные недели до Release 2; дополнительно
   сверить с исходным срезом до Release 1, чтобы последовательные потери не скрывались.
5. Главная `/ru/` подготовлена на тесте, проверены ссылки, расчёт, метаданные и отсутствие
   цикла между `/` и `/ru/`. Существующие платёжные сценарии работают на `.com`.

Пока условия не выполнены, русская главная остаётся на `.com/`. Это рабочее состояние
продукта, поэтому нет необходимости менять её адрес ради формального завершения плана.

## Release 3. Окончательный адрес русской главной

```text
.com/ru/ → 200, прежняя русская главная
.com/    → 301 → .com/ru/
.ru/     → 301 → .com/ru/
```

Одновременно убрать временный 302 с `.com/ru/` на `.com/`; иначе возникнет цикл.
Перенести содержание главной без сокращения и смены назначения, обновить canonical,
языковые альтернативы, ссылку на главную в шапке/крошках, sitemap и структурированные данные.
Внутренние русские ссылки ведут сразу на `/ru/`, английские — на `/en/`.

**После Release 3 проверить:**

- `/ru/` и `/en/` отвечают 200 и отдают правильный язык без зависимости от cookie;
- `/` отдаёт ровно предусмотренный редирект на `/ru/`, нет циклов или выбора по IP;
- старая `.ru/` ведёт к русской главной, старые статьи — к соответствующим статьям;
- главная, калькулятор, вход и оплата работают; метаданные указывают на конечные URL;
- sitemap содержит `/ru/` вместо перенаправляемого корня, а робот может прочитать 301;
- после переобхода Яндекс показывает новую главную и продолжает считать `.com` главным доменом.

Переезд считать завершённым после технических проверок и подтверждения обработки главной
Яндексом. Само наличие 301 не доказывает, что поисковик уже перенёс сигналы.

## Сопровождение и фиксация результатов

Для каждого релиза записывать: commit/версию, время публикации, карту редиректов,
результаты проверок, даты данных Метрики/Вебмастера, статус заявки и обнаруженные ошибки.
Отдельно записывать решение о допуске к следующему релизу со ссылками на доказательства
по каждому критерию. Пороговые значения из этого плана нельзя менять задним числом,
чтобы признать неудачный результат успешным.

Технические дефекты исправлять в рамках согласованной задачи. При существенном падении
трафика остановить дальнейшие изменения URL и исследовать причину. Не делать обратный
доменный переезд автоматически: уже обработанную группировку Яндекса нельзя считать
мгновенно обратимой. План аварийного восстановления перед релизом должен учитывать
существующие процедуры проекта и не подменяться обещанием «просто откатить SEO».

Продлевать `.ru` и сертификаты, сохранять DNS, редиректы и необходимые старые callback.
Не удалять старый доменный профиль, пока от него зависят исторические платежи.
Дальнейшие русские внешние размещения после переезда должны вести сразу на `.com/ru/…`,
английские — на `.com/en/…`.
