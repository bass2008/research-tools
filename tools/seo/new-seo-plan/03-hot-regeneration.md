# 03. Горячая перегенерация без остановки продаж

**Приоритет:** P0  
**Релиз:** единый — локальная подготовка производных данных; deploy только в плане 10  
**Зависимости:** [02 — исправленный движок](02-engine-parity.md)  
**Блокирует:** только признание нового релиза проверенным  
**Оплата:** работает непрерывно  
**Риск до → после:** высокий → средний; производные данные пересчитаны новым движком

## Цель

Пересобрать локальный статический корпус и PDF-примеры новым движком. Test/prod не менять до
единого deploy плана 10; при будущей выкладке не останавливать регистрацию, создание счетов,
callback банка и выдачу прав.

Живых пользовательских матриц сейчас нет. Поэтому не нужна миграция результата: `SavedMatrix`
хранит вход — дату, пол и название — а значения рассчитываются движком. После релиза существующий
вход автоматически открывается уже с исправленным расчётом.

## Что не делаем

- не вводим режим обслуживания;
- не выключаем оплату и не блокируем `POST /api/payments/start`;
- не очищаем продовую БД целиком;
- не удаляем пользователей, платежи или права широким запросом;
- не поддерживаем параллельно старую и новую формулу;
- не добавляем служебные поля в пользовательские записи.

## Быстрый preflight

Это диагностический снимок, а не блокировка релиза:

- количество `users`, `matrices`, `payments`, `entitlements`, `report_jobs`;
- число успешных и невозвращённых оплат;
- точный перечень известных тестовых аккаунтов и PDF;
- commit/tag текущего релиза;
- backup БД штатным скриптом.

Если неожиданно находится новый пользователь или платёж, его **не удалять**. Релиз формулы всё
равно продолжается, потому что сохранённый вход пересчитывается динамически. Точечная чистка
затрагивает только заранее идентифицированные тестовые записи.

## Перегенерация

- Пересобрать [`web/content/matrices.json`](../../../project/destiny-matrix/web/content/matrices.json)
  исправленным Python-движком.
- Обновить golden fixtures Python и TypeScript только по подписанным примерам.
- Перегенерировать эталонные PDF и screenshots.
- Старые тестовые PDF удалить по точному списку object keys.
- Текущие и новые PDF всегда строить через исправленный движок.
- Проверить все 5544 продуктовые страницы: они остаются `noindex, follow`, вне sitemap и совпадают
  с калькулятором.

## Точечная чистка

При необходимости удалить только документированные тестовые данные:

1. получить точные user ids;
2. показать dry-run по `report_jobs`, `entitlements`, `payments`, `matrices`, `users`;
3. удалить связанные строки в порядке внешних ключей;
4. удалить только перечисленные object keys PDF;
5. повторно вывести агрегаты.

Новая запись, появившаяся после preflight, не входит в список удаления. Для неё релиз просто начнёт
использовать исправленный движок.

## Порядок горячего релиза

1. Собрать исправленный commit.
2. Выложить на тест через
   [`release-test.sh`](../../../project/destiny-matrix/compose/scripts/release-test.sh).
3. Прогнать golden/parity, browser smoke, mock и тестовый банк.
4. Сделать prod backup и диагностический снимок.
5. Выложить тот же commit через
   [`release-prod.sh`](../../../project/destiny-matrix/compose/scripts/release-prod.sh).
6. Немедленно проверить расчёт, кабинет, оплату, callback, отчёт и PDF.
7. Наблюдать первые 60 минут. Создание счетов продолжает работать на всех шагах.

Сборка и push выполняются до переключения контейнеров. Окно недоступности — только штатное время
перезапуска сервиса; отдельной платёжной паузы нет.

## Тесты

- все golden-даты совпадают на тесте и проде;
- Python ↔ TypeScript parity зелёный;
- сохранённая дата до/после reload совпадает с калькулятором;
- платёж, появившийся во время релиза, не теряется и выдаёт право на точный `matrix_id`;
- callback во время переключения безопасно повторяется;
- точечный cleanup не затрагивает неизвестного пользователя;
- новый PDF совпадает с экраном;
- 5544 результата совпадают с движком и не индексируются.
