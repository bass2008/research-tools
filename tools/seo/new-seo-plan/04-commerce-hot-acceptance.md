# 04. Сквозная коммерческая приёмка перед единым релизом

**Приоритет:** P0  
**Релиз:** единый — локальная приёмка RC и повторный smoke после deploy плана 10  
**Зависимости:** планы [01](01-methodology-contract.md)–[03](03-hot-regeneration.md)  
**Блокирует:** только статус «коммерческая часть исправления подтверждена»  
**Оплата:** работает непрерывно до, во время и после релиза  
**Риск до → после:** средний → низкий коммерческий внутри RC; prod меняется одним релизом

## Цель

Подтвердить сквозным сценарием до deploy, что покупатель создаёт счёт, платит именно за выбранную
матрицу, получает правильное право, согласованный разбор и PDF. После единого deploy тот же
сценарий повторяется как prod-smoke.

Этот план не включает, не выключает и не ограничивает оплату. Он проверяет уже работающую
коммерческую цепочку и задаёт быстрый откат к предыдущему релизу, если новый код нарушил её.

## Обязательные условия нового релиза

- метод подписан;
- Python/TypeScript parity зелёный;
- статический корпус и PDF-примеры пересобраны;
- полный штатный test suite зелёный;
- сохранён предыдущий image tag для быстрого отката кода.

Ни одно из условий не реализуется блокировкой новых счетов. Проверки сначала выполняются на тесте,
после чего тот же commit сразу выкладывается на прод.

## Матрица сквозных сценариев

Проверить на mock, тестовом терминале и production smoke:

| Сценарий | Что обязано произойти |
|---|---|
| Гость считает дату → покупает | создаётся одна сохранённая матрица и один платёж на неё |
| Вошедший считает сохранённую дату | открывается её право, повторная продажа не предлагается |
| Две даты и оба пола | подписи однозначны, `matrix_id` платежа совпадает с выбором |
| Одинаковая дата разных полов | платёж нельзя привязать к другой карте |
| Повторный клик/две вкладки | возвращается существующая попытка, двойного списания нет |
| Callback во время релиза | повторная доставка завершается идемпотентно, право выдаётся один раз |
| Callback раньше браузера | доступ уже активен, экран корректно синхронизируется |
| Возврат | право отозвано, финансовая история сохранена |
| Неуспех/таймаут банка | право не выдаётся, повторная попытка безопасна |
| PDF | числа и тексты совпадают с экраном |

## Коммерческая честность

Проверить первый экран, тарифы, оплату, чек и письмо:

- дата и пол цели названы однозначно;
- обещанный объём совпадает с реально открываемыми разделами;
- энциклопедия дополняет, а не заменяет оплаченный ответ;
- цена не показывается рядом с «уже оплачено»;
- CTA оплаченной даты ведёт в разбор, неоплаченной — в корректную оплату;
- страница метода честно описывает формулу и характер интерпретаций.

## Порядок проверки

### До prod

- Запустить [`compose/scripts/run-tests.sh`](../../../project/destiny-matrix/compose/scripts/run-tests.sh).
- Прогнать bank-marked E2E на тестовом терминале.
- Проверить создание счёта, callback, доступ, PDF и возврат.
- Выполнить browser smoke всех route types, авторизации, кабинета и отчёта.

### Сразу после prod

1. Проверить health и commit.
2. Рассчитать golden-дату на главной.
3. Создать контролируемый минимальный боевой счёт и завершить платёж.
4. Проверить точный `matrix_id`, entitlement, отчёт, PDF и письмо.
5. Проверить повторный callback и отсутствие второго права.
6. Наблюдать ошибки и платежные метрики минимум 60 минут.

Рабочие пользовательские счета в этот период создаются и обрабатываются обычным образом.

## Откат

Если новый код ломает формулу или коммерческую цепочку:

- быстро вернуть предыдущий image tag;
- продолжить принимать callback уже созданных счетов;
- не удалять платежи, права и пользователей;
- сопоставить затронутые платежи по времени релиза и вручную проверить их `matrix_id`;
- исправить причину и повторить test → prod тем же порядком.

Откат кода не требует выключать платёжный API.

## Автоматические тесты

- API: идемпотентность, точный `matrix_id`, notify, sync, refund, duplicate callback;
- DB: уникальность активного права на матрицу;
- E2E: все строки таблицы сценариев;
- browser: покупка продолжает работать во время rolling restart/retry;
- PDF data test на golden-дате;
- monitoring test: ошибка оплаты и расхождение результата создают тревогу.
