# Ночной прогон: тестовый эквайринг → прод → проверка под нагрузкой

План на ночь без человека. Главное требование: **ни одного места, где работа встаёт и ждёт ответа.**
Поэтому у каждого шага заранее задан числовой критерий, а у каждого возможного отказа — готовое
решение «что делать вместо того, чтобы спрашивать».

Продукт: `project/destiny-matrix` (Arcana Sense, `arcana-sense.ru`).
Метод цикла: `tools/benchmark-testing/testing-cycle.md`. Отчёты: `tools/benchmark-testing/out/`.

---

## 0. Правила ночи

1. **Вопросов не задавать.** Любая неясность решается по правилам ниже; если правило не покрывает
   случай — выбирается вариант, который **ничего не ломает и не тратит деньги**, и это пишется в
   отчёт шага.
2. **Отчёт пишется сразу после шага**, а не в конце ночи. Обрыв на середине не должен оставить
   работу без следа.
3. **Git не трогать.** Ни `commit`, ни `push`, ни ветки, ни `reset`. Только чтение (`status`, `diff`,
   `log`). Релиз идёт `release.sh` и не требует коммита: тег собирается из `HEAD` + метка времени.
4. **Реальные платёжные ключи не заводить.** Терминал только DEMO — тот, что уже лежит в
   `~/.config/arcana/tbank.env` и в `/srv/arcana/.env`. Настройки в личном кабинете банка не менять.
5. **Данные прода не удалять без бэкапа.** Перед любой чисткой — `compose/scripts/backup.sh`.
   Живых пользователей на сайте пока нет, поэтому прод — это ещё стенд: **откатывать релизы не нужно**,
   сломанное состояние допустимо, его чинят вперёд, а не назад.
6. **Порядок ступеней не нарушать:** локальный мок → локальный тестовый терминал → прод. Ступень 3
   разрешена этим планом на DEMO-терминале и только на нём.
7. **Дефекты исправляются локально**, проверяются тестами и уезжают на прод релизом. Правок прямо на
   машине не делать (кроме `.env`, если это прямо предписано шагом).
8. **Если время вышло** (см. §8) — дописать `out/FinalStep.md` с тем, что успели, и остановиться.

## 2. Шаг 1 — ступень 2 локально: тестовый эквайринг

**Отчёт: `out/step1-0.md`.**

Подготовка стенда (мок выключается на время шага):

```bash
cd project/destiny-matrix/compose
set -a; . ~/.config/arcana/tbank.env; . ~/.config/arcana/reports.env; . ~/.config/arcana/smtp.env; set +a
PAYMENT_PROVIDER=tbank MAIL_TO_LOG=1 scripts/run.sh
```

Проверка, что переключилось: `docker compose exec -T api python -c "from app import payments;
print(payments.active().name)"` → должно быть `tbank`.

Сценарии — **последовательно, один платёж за раз** (`testing-cycle.md §15`): пауза ≥3 с между
началами, до 30 платежей за прогон, два одновременных `Init` только в сценарии гонки.

| # | Сценарий | Инвариант |
|---|---|---|
| 1 | оплата картой `…0777` | доступ открыт ровно к выбранной дате, платёж `CONFIRMED`, письмо о покупке в логе |
| 2 | отказ картой `…0785` | доступ не открыт, платёж не `CONFIRMED`, экран `/pay/fail` объясняет |
| 3 | уход со страницы до возврата | доступ открывается досверкой (`app/sweep.py`), очередь `payment_sweeps` пополняется |
| 4 | уведомление изнутри (`selfnotify`) | подпись проверяется, повтор идемпотентен, права не удваиваются |
| 5 | отмена оплаченного платежа из админки | `refunded_at` выставлен, право снято, письмо о возврате |
| 6 | отмена неоплаченного (холд снят) | это неудача, а не возврат: прав не было и не появилось |
| 7 | гонка двух вкладок (ровно 2 `Init`) | одна дата — один платёж; если два — это дефект уровня «деньги» |
| 8 | повторная оплата уже открытой даты | форма не даёт платить, кнопка неактивна |

Готовые сценарии на живом терминале уже лежат в `e2e/test_bank_chain.py` (маркер `bank`):

```bash
cd project/destiny-matrix/e2e
SSL_CERT_FILE=~/.config/arcana/ca-bundle.pem \
/home/sergey/miniconda3/envs/research3.12/bin/python -m pytest -m bank -q
```

Чего в них нет — дописать разово в тот же файл (правило §6 цикла: расширять, а не плодить).

**Отказы и что делать вместо вопроса:**

| Отказ | Решение |
|---|---|
| `Init` возвращает ошибку банка | 2 повтора с паузой 10 с; если не ушло — ступень 2 помечается «недоступна», причина в отчёт, идём к §3 и решение принимаем по мок-циклам |
| форма банка не открывается / вёрстка изменилась | правится селектор в `flows.py::pay_on_bank_form`, одна попытка; иначе — как выше |
| TLS-ошибка | `SSL_CERT_FILE=~/.config/arcana/ca-bundle.pem` (в образе api сертификат уже есть) |
| висящие `AUTHORIZED` после прогона | отменить через админку или дождаться исхода; незакрытых не оставлять |

**Финал шага обязателен:** вернуть стенд на мок — `PAYMENT_PROVIDER=mock MAIL_TO_LOG=1 scripts/run.sh`
и убедиться, что `payments.active().name == "mock"`. Иначе следующий локальный цикл уйдёт в банк.

## 3. Шаг 2 — решение о деплое (числовой порог, без обсуждения)

Считаем по последнему завершённому циклу и по итогу ступени 2.

**Деплоим, если выполнены все четыре условия:**

1. критичных дефектов — **0**. Критичный = деньги (списание не за то, двойное списание, потеря
   оплаченного доступа), утечка персональных данных, полная неработоспособность покупки;
2. подтверждённых дефектов всего — **не больше 3**, и все они категории «низкая/средняя»;
3. `compose/scripts/run-tests.sh` — **зелёный целиком**;
4. ступень 2 пройдена или честно помечена недоступной (см. §2).

**Иначе:** ещё один локальный цикл (§4). Лимит — **три дополнительных цикла** (`step1-1`,
`step1-2`, `step1-3`). Если после третьего порог не достигнут — **деплой не делаем**, пишем
`FinalStep.md` с перечнем того, что мешает, и заканчиваем ночь. Это не провал, а честный результат.

Решение и его обоснование пишутся в конец отчёта того цикла, после которого принимались.

## 4. Шаг 3 — дополнительные локальные циклы

Каждый цикл — полностью по `testing-cycle.md`: ступень 1 (мок), 10 маршрутов + опровергатели,
трезвый отсев, красные тесты, правки, зелёный прогон. Отчёты: `out/step1-1.md`, `out/step1-2.md`,
`out/step1-3.md`.

Ограничения ночи:

- маршруты можно сузить до тех, где были правки (после первого круга это честнее, чем гонять всё);
- если цикл нашёл **только** пограничное и пожелания — порог §3 считается достигнутым, идём дальше;
- если цикл нашёл дефект, правка которого затрагивает платежи, — после правки обязателен повторный
  прогон ступени 2 (сокращённый: сценарии 1, 2, 5 из §2).

## 6. Шаг 5 — цикл на проде (ступень 3)

**Отчёты: `out/Step3-0.md`, при повторе — `out/Step3-1.md` и далее.**

Разрешено этим планом: DEMO-терминал, тестовые карты, только те аккаунты, которые создаём сами.

Жёсткие ограничения (машина 2 vCPU / 2 ГБ):

- **один платящий исполнитель**, пауза ≥3 с, **не больше 12 платежей** за прогон (меньше, чем
  локальный лимит: живая база);
- почты только вида `night-<hex>@example.ru` — по этой маске потом чистим;
- печать PDF — **не больше двух одновременно** (контейнер браузера ограничен 512 МБ);
- никаких массовых веерных прогонов: до 3 агентов на не-платящих маршрутах.

Что проверяем на проде (то, чего нет локально):

1. настоящий домен и TLS: покупка целиком, письмо о покупке **реально уходит** через Postbox;
2. разовая сверка статуса при возврате на `/pay/done` открывает доступ;
3. обработчик уведомления через `selfnotify` (канал из банка недоступен — см. §1);
4. печать PDF на слабой машине: время, размер файла, ссылка из Object Storage;
5. письма о возврате после отмены платежа из админки;
6. `robots.txt`, `sitemap.xml`, заголовки 404, юридические страницы — на живом домене.

**После прогона:**

1. отменить или довести до исхода все созданные платежи — висящие `AUTHORIZED` в чужой системе не
   оставляем (это про банк, а не про наш сайт, поэтому делается всегда);
2. тестовые аккаунты убрать для гигиены базы: написать `compose/scripts/cleanup-test-users.sh` —
   аргументов нет, маска `night-%@example.ru` внутри, по умолчанию сухой прогон, удаление с `APPLY=1`,
   перед удалением ещё один `backup.sh`. Если скрипт не получается — не тратить на него время: данных
   живых пользователей всё равно нет, достаточно записать в отчёт, сколько тестовых записей осталось.

**Критичные дефекты на проде** (деньги, утечка, недоступность покупки) → правка локально + тест +
релиз (§5) + новый отчёт `Step3-1.md`. Некритичные — в отчёт, без релиза ночью.

Останов: когда очередной прод-цикл не находит критичных. Число циклов — по обстановке, но не больше
трёх.

## 7. Шаг 6 — базовая проверка под нагрузкой

**Отчёт: `out/Step5.md`. Здесь ничего не исправляем — только наблюдаем и записываем.**

Цель не предел, а ответ на один вопрос: **держит ли машина десяток одновременных посетителей без
заметной деградации.**

Порядок — тремя волнами, между волнами пауза 2 минуты:

| Волна | Кто | Что делают |
|---|---|---|
| 1 | 3 агента | расчёт на главной, чтение разбора, энциклопедия, каталог матриц |
| 2 | 5 агентов | то же + вход/регистрация + одна покупка на DEMO-карте у одного из них |
| 3 | 10 агентов | то же; печать PDF — **максимум у двух одновременно** |

Что снимать на каждой волне:

- время ответа `/`, `/api/health`, `/encyclopedia/arcanum/7`, `/report` — минимум, медиана,
  максимум (сравнивать с базовыми числами из §1);
- время расчёта матрицы и время печати PDF;
- `docker stats --no-stream` (CPU и память по трём контейнерам) и `uptime` (load average) на машине;
- ошибки: любые 5xx, таймауты, перезапуски контейнеров (`docker compose ps`).

**Порог тревоги (не дефект, а сигнал остановиться):** максимум времени ответа выше 3 с, появление
5xx, перезапуск контейнера, свободная память меньше 150 МБ. При любом из них — снизить волну до
предыдущей, дать машине 2 минуты и записать наблюдение. Ломать прод нельзя: он живой.

Вывод отчёта — одной фразой на каждый вопрос: держим ли 10, где начинается деградация, что в ней
узкое место (CPU api, память браузера, диск), и стоит ли поднимать машину до нормального
нагрузочного теста.

## 8. Бюджет времени и точки выхода

| Шаг | Оценка |
|---|---|
| §2 ступень 2 локально | 40–60 мин |
| §3 решение | 5 мин |
| §4 один дополнительный цикл (если нужен) | 60–90 мин с правками |
| §5 релиз с проверками | 20–30 мин |
| §6 прод-цикл + чистка | 45–60 мин |
| правки после прод-цикла + повторный релиз (если нужны) | 60–90 мин |
| §7 нагрузка тремя волнами | 30–40 мин |
| §9 финальный отчёт | 10 мин |

Итого **6–9 часов** при одном-двух дополнительных циклах. Совпадает с оценкой заказчика.

Точки выхода (после каждой — сразу `FinalStep.md`):

1. порог §3 не достигнут после трёх дополнительных циклов → без релиза;
2. релиз не встал после четырёх попыток → оставляем как есть, продовые шаги помечаем пропущенными;
3. прод недоступен по ssh → только локальные результаты;
4. время вышло → фиксируем достигнутое.

## 10. Чего в эту ночь не делаем

- не подключаем реальный терминал банка и не меняем настройки в его ЛК (в том числе Notification URL);
- не возвращаем прод на мок-оплату к утру: DEMO-терминал там остаётся осознанно, живых покупателей нет;
- не ищем дефекты безопасности: это отдельный режим (`serucity-issues.md`), у него свой запуск;
- не делаем нагрузочное тестирование «до предела» — только §7;
- не переписываем архитектуру и не начинаем новые фронты (SEO-контент, вход через VK) — их планы
  лежат отдельно и ночью не трогаются;
- не коммитим и не пушим: утром человек сам посмотрит дерево и решит.
