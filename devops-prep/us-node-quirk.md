## Краткая суть

В `us-node` контейнере неправильно настроена маршрутизация: весь его исходящий трафик, включая служебные запросы (STUN для определения публичного IP), идёт через `us-corp` → EU Azure.

Из-за этого `us-node` думает что его публичный IP — это `40.69.0.186` (EU Azure), и рекламирует этот IP в Headscale. Клиенты пытаются подключиться по этому адресу, но физически `us-node` находится в нашей VM в Яндекс Облаке. Получается кривой hairpin-путь через Европу и обратно с двойной инкапсуляцией WireGuard.

Результат: пакеты большого размера дропаются (MTU issues), интернет работает нестабильно, клиенты сидят по 10 секунд в зависании пока Tailscale сам не детектит проблему и не откатится на DERP.

## Базовая теория

### NAT (Network Address Translation)

**Что это:** механизм подмены IP-адресов на границе сетей. Роутер берёт пакет с приватным адресом из внутренней сети (например `192.168.1.5`) и подменяет source address на свой публичный IP (например `158.160.123.87`), чтобы интернет мог ответить роутеру, а не недостижимому приватному адресу.

**Зачем нужен:** IPv4 адресов мало, поэтому один публичный IP делится между многими устройствами через NAT.

**Как работает:**

```
Твой ноут (192.168.1.5) → Роутер (192.168.1.1 / 78.25.100.1) → Интернет → Сервер (8.8.8.8)

Ноут отправляет:   src=192.168.1.5:54321   dst=8.8.8.8:80
Роутер превращает: src=78.25.100.1:54321   dst=8.8.8.8:80 (source заменён на публичный IP роутера)
Сервер получает:   src=78.25.100.1:54321   dst=8.8.8.8:80

Ответ сервера:     src=8.8.8.8:80          dst=78.25.100.1:54321
Роутер смотрит NAT-таблицу: "порт 54321 принадлежит 192.168.1.5"
Роутер превращает: src=8.8.8.8:80          dst=192.168.1.5:54321
Ноут получает ответ.
```

**Важное свойство NAT:** запись в NAT-таблице создаётся когда **исходящий** пакет проходит через NAT. Если кто-то снаружи попытается достучаться до `192.168.1.5` первым — не получится, NAT не знает куда направить пакет.

**Типы NAT:**
- **Full cone** — соединения в обе стороны после первого исходящего
- **Symmetric** — NAT-запись привязана к конкретному destination, сложно для hole-punching
- **Port-restricted** — строже чем full cone, но мягче symmetric

В случае двойного NAT (несколько слоёв) поведение становится сложнее.

### STUN (Session Traversal Utilities for NAT)

**Что это:** простой протокол "пожалуйста, скажи мой публичный IP и порт".

**Зачем нужен:** устройство за NAT не знает своего публичного адреса. Локально видит `192.168.1.5`, но для мира оно `78.25.100.1:54321`. STUN-сервер видит пакет из интернета и возвращает "твой public IP и port — такие-то".

**Как работает:**

```
Клиент отсылает STUN-запрос:
  src=192.168.1.5:54321 → NAT → src=78.25.100.1:54321 → dst=stun.server.com:3478

STUN-сервер отвечает:
  "Твой публичный адрес: 78.25.100.1:54321"
```

**Это используется Tailscale** для того чтобы узнать — куда клиенты должны слать пакеты чтобы меня найти.

### MTU и фрагментация

**MTU (Maximum Transmission Unit)** — максимальный размер пакета в байтах, который сеть может передать за один раз.

**Обычный Ethernet:** MTU 1500 байт.

**Что внутри 1500 байт:**
- Ethernet header: 14 байт
- IP header: 20 байт (IPv4)
- TCP/UDP header: 20 байт (TCP) или 8 байт (UDP)
- **Data payload: до 1460 байт (TCP) или 1472 байт (UDP)**

### Инкапсуляция и overhead

Когда ты используешь VPN (WireGuard), каждый пакет заворачивается в другой пакет. Это добавляет overhead:

**WireGuard overhead: ~80 байт** (UDP header + WG header + MAC)

```
Обычный пакет:                [Eth 14][IP 20][TCP 20][Data 1460]   = 1500 B

WireGuard обёрнутый пакет:    [Eth 14][IP 20][UDP 8][WG 60][Data ?][pad]
                                                            ↑
                              Внутри Data лежит: [IP 20][TCP 20][Data 1420]
                                                                    ↑
                                                       полезная нагрузка 1400

Итого полезного: 1400 байт вместо 1460. MTU внутри туннеля = 1420.
```

**Двойная инкапсуляция (VPN внутри VPN):**

```
Внешний Ethernet:  [14][20][UDP 8][WG 60 #1][payload ??]
                                              ↓
                                         [20][UDP 8][WG 60 #2][payload]
                                                                  ↓
                                                             [20][TCP 20][Data ~1340]

Полезной нагрузки: ~1340 байт. Это меньше обычных 1460. 
Если приложение шлёт 1500-байтный пакет — он может быть фрагментирован или дропнут.
```

**Что происходит когда пакет слишком большой:**

1. **Путь поддерживает фрагментацию:** большой пакет разбивается на 2 меньших, долетают, собираются обратно. Медленно, но работает.
2. **WireGuard не делает фрагментацию:** молча дропает слишком большие пакеты. Отправитель не получает ответа — вся TCP-сессия зависает.
3. **ICMP "Fragmentation needed":** в идеале NAT/роутер сообщает отправителю "сделай пакет меньше". Но ICMP часто блокируется файрволами — это **Path MTU Discovery Blackhole**.

### Маршрутизация (routing)

Когда ядро получает пакет для отправки, оно смотрит в **routing table**, чтобы решить — в какой интерфейс и на какой next-hop отправить.

**Пример routing table:**

```
$ ip route
default via 192.168.1.1 dev wlan0     ← всё что не знаем куда — шлём на роутер
192.168.1.0/24 dev wlan0              ← локальная сеть — напрямую
10.8.0.0/24 dev tun0                  ← подсеть VPN — через туннель
```

**Default route** — куда идёт пакет если нет специфичного маршрута. Обычно — на роутер (шлюз в интернет).

### Policy-based routing

**Проблема:** обычная routing table умеет выбирать маршрут только по **destination IP**. Но иногда хочется выбирать маршрут по другим признакам — source IP, интерфейс, метка пакета.

**Решение:** **policy-based routing** — несколько routing tables + правила (`ip rule`) выбирающие какую таблицу использовать для каких пакетов.

**Пример:**

```bash
# Обычная таблица (main) — default route через провайдера
default via 192.168.1.1 dev wlan0

# Отдельная таблица (номер 200) — default через VPN
ip route add default via 10.8.0.1 dev tun0 table 200

# Правило: если source IP 192.168.1.100 — использовать таблицу 200 (через VPN)
ip rule add from 192.168.1.100 table 200

# Правило: если fwmark на пакете = 1 — использовать таблицу 200
ip rule add fwmark 1 table 200
```

Это как говорить: *"для этих пакетов используй вот этот маршрут, для остальных — обычный"*.

### iptables marks (fwmark)

**Что это:** метка (целое число) которую можно повесить на пакет внутри ядра. Она не передаётся по сети, живёт только пока пакет обрабатывается ядром.

**Зачем:** связка iptables и policy-based routing. iptables может пометить пакет → ip rule посмотрит метку → выберет routing table.

**Пример:**

```bash
# Пометить все пакеты которые пришли на интерфейс tun0 маркой 1
iptables -t mangle -A PREROUTING -i tun0 -j MARK --set-mark 1

# Правило: пакеты с меткой 1 → routing table 200
ip rule add fwmark 1 table 200
```

Это базовые кирпичики для нашего фикса.

## Как работает Tailscale

Tailscale — это WireGuard VPN с автоматическим управлением ключами и маршрутами. Строится из трёх компонентов:

### 1. Координационный сервер (control plane)

**Что делает:** хранит информацию о всех устройствах в сети, их публичных ключах, IP-адресах, правах. **Не видит твой трафик** — только метаданные.

У Tailscale это облачный сервис. У нас — self-hosted **Headscale**.

### 2. DERP серверы (Designated Encrypted Relay for Packets)

**Что делает:** relay для WireGuard трафика в случае если два клиента не могут установить прямое UDP-соединение.

Например, оба клиента за симметричным NAT, или UDP заблокирован — тогда трафик пойдёт **через DERP сервер** по TCP/443 (обычный HTTPS).

DERP не расшифровывает трафик — просто перебрасывает зашифрованные WireGuard пакеты между клиентами. Конечные клиенты расшифровывают.

### 3. Клиенты

**Что делают:** устанавливают WireGuard туннели с другими клиентами. Шифруют/расшифровывают трафик.

### Как клиенты находят друг друга

Когда клиент A хочет отправить пакет клиенту B:

1. **A спрашивает у координационного сервера** "где B?"
2. **Сервер отвечает** списком возможных endpoint'ов B:
   - Публичный IP:port (через STUN discovery)
   - LAN IP:port (если в одной сети)
   - DERP endpoint (запасной)
3. **A пробует endpoint'ы** по очереди, от лучшего к худшему:
   - Сначала direct UDP (быстро, 1 хоп)
   - Если не получилось — fallback на DERP (медленно, но работает)

### Как endpoint'ы определяются

**Каждый клиент запускает STUN discovery:**
1. Посылает STUN-запрос на один из STUN-серверов (Google, etc.)
2. Получает ответ "твой публичный IP:port такой-то"
3. **Рекламирует этот endpoint** координационному серверу
4. Координационный сервер сохраняет и отдаёт другим клиентам

**Тут и зарыта наша проблема.** Если STUN-запрос идёт через неправильный сетевой путь, он возвращает неправильный IP. Клиент рекламирует "приходите по адресу X", но физически находится не там.

### UDP vs DERP

**UDP direct (идеально):**
```
Клиент А → Публичный интернет по UDP → Клиент B
Задержка минимальная. MTU 1420 (один слой WireGuard).
```

**DERP relay (fallback):**
```
Клиент А → TCP/443 HTTPS к DERP серверу → TCP/443 HTTPS к Клиенту B
Задержка выше (лишний хоп). MTU меньше (WireGuard внутри TLS).
Но работает через любой файрвол, потому что выглядит как обычный HTTPS.
```

Tailscale старается использовать UDP, падает на DERP если UDP не работает.

## Наша архитектура

### Компоненты

Всё крутится в одной VM в Яндекс Облаке (`158.160.123.87`) в Docker Compose:

```
┌──────────────────────────────────────────────────────────────┐
│ VM в Яндекс Облаке (158.160.123.87)                           │
│                                                                │
│ ┌─────────────┐    ┌──────────┐    ┌─────────────┐            │
│ │   caddy     │    │headscale │    │  authelia   │            │
│ │(reverse-proxy)│  │(координ.  │    │   (OIDC)    │            │
│ │             │    │ сервер +  │    │             │            │
│ │             │    │ DERP)     │    │             │            │
│ └─────────────┘    └──────────┘    └─────────────┘            │
│                                                                │
│ ┌─────────────┐    ┌──────────┐    ┌─────────────┐            │
│ │   yc-node   │    │ us-node  │◄───│  us-corp    │            │
│ │(exit node,  │    │(exit node│    │(клиент корп │            │
│ │ прямой      │    │, через   │    │ Tailscale в │            │
│ │ интернет)   │    │ us-corp) │    │ EU exit)    │            │
│ └─────────────┘    └──────────┘    └─────────────┘            │
│                                                                │
└──────────────────────────────────────────────────────────────┘
```

### Роли

- **caddy** — reverse proxy с автоматическим HTTPS (Let's Encrypt). Принимает запросы снаружи, маршрутизирует к headscale и authelia.
- **headscale** — координационный сервер (наша замена Tailscale). Хранит ноды, ключи, правила. Включает в себя **встроенный DERP сервер**.
- **authelia** — OIDC провайдер (логин/пароль при регистрации новых клиентов).
- **yc-node** — exit node. Клиенты через него выходят в интернет с IP нашей YC VM.
- **us-node** — exit node. Клиенты через него выходят **через двойной VPN в EU** (Мой YouTube → EU вместо Яндекс Облака РФ).
- **us-corp** — клиент корпоративного Tailscale (`vpn.invent.us`). Подключён к их `apptrium-prod-vm-eu-1` как exit node. `us-node` отправляет через него всё наружу.

### Сеть Docker

Все контейнеры в Docker bridge network `docker_us-net` (условно `172.18.0.0/16`):

```
us-node:   172.18.0.2
us-corp:   172.18.0.3
gateway:   172.18.0.1 (виртуальный роутер Docker, через него все выходят на eth0 VM)
```

### Почему такая архитектура

Хотим:
- **yc-node** — выходить в РФ-сегмент с IP нашей VM (для российских сервисов)
- **us-node** — выходить в EU-сегмент с нерусским IP (для YouTube, OpenAI, etc.)

Для `us-node` использовали корпоративный Tailscale как proxy в EU, потому что:
- Бесплатно (у тебя есть рабочий доступ)
- **Белые списки мобильных операторов РФ** блокируют большинство зарубежных IP, но корпоративный Tailscale работает

## Проблема

### Что криво

`us-node` в текущей конфигурации имеет **один default route** — через `us-corp`:

```bash
us-node:~# ip route
default via 172.18.0.3 dev eth0   ← всё в us-corp
172.18.0.0/16 dev eth0             ← локально в Docker bridge
```

Это значит **весь** исходящий трафик `us-node` идёт через `us-corp`:
- Трафик от клиентов (exit-node) — это правильно, их мы хотим гнать через EU
- **Служебный трафик Tailscale (STUN, heartbeats) — это неправильно!** Он должен идти напрямую, а не через EU.

### Что происходит с STUN

Tailscale в `us-node` стартует и хочет узнать свой публичный IP:

```
1. us-node генерирует STUN запрос: "stun.l.google.com, what's my IP?"
   Source IP пакета: us-node eth0 = 172.18.0.2
   Destination: stun.l.google.com:19302

2. Routing lookup: dest не в локальной сети → default route → 172.18.0.3 (us-corp)

3. us-corp получает пакет, видит destination в интернете. Но у us-corp default route через
   корпоративный Tailscale → EU Azure (apptrium-prod-vm-eu-1, 40.69.0.186)
   
4. Пакет идёт: us-node → us-corp → [корп Tailscale туннель] → EU Azure → интернет
   
5. EU Azure NAT подменяет source IP на свой: 40.69.0.186
   
6. STUN-сервер получает пакет от 40.69.0.186, отвечает "твой IP: 40.69.0.186"

7. Ответ приходит обратно тем же путём: STUN → EU Azure NAT → корп Tailscale →
   us-corp → us-node

8. us-node записывает у себя: "мой публичный endpoint — 40.69.0.186:54321"

9. us-node рекламирует это Headscale: "я доступен по 40.69.0.186:54321"
```

**Итог:** us-node рекламирует `40.69.0.186` как свой публичный IP, хотя физически он живёт в Докере на VM в Яндекс Облаке (`158.160.123.87`).

### Что происходит когда клиент пытается достучаться

Клиент (ноут, телефон) хочет подключиться к `us-node`:

```
1. Клиент спрашивает Headscale: "где us-node?"
2. Headscale отвечает: "us-node на 40.69.0.186:54321 и через DERP"
3. Клиент пробует direct UDP на 40.69.0.186:54321
```

**Что происходит физически:**

```
Ноут (дома в РФ) → отправляет WG-пакет на 40.69.0.186:54321

Куда физически идёт пакет? На 40.69.0.186 — это EU Azure сервер!

Пакет летит из Москвы в Лондон/Ирландию (где стоит Azure), ~50ms задержки.

EU Azure получает пакет. Его NAT смотрит: "ага, есть существующая запись для
us-corp с UDP портом 54321 — пакет пришёл в ответ, надо переслать".

EU Azure обратно через корпоративный Tailscale отправляет пакет нашему us-corp.

us-corp через Docker bridge передаёт в us-node.

us-node получает WG-пакет, расшифровывает, отвечает.

Ответ идёт обратно тем же путём: us-node → us-corp → [корп Tailscale] →
EU Azure → интернет → ноут.
```

**Путь пакета:**

```
Ноут (RU) → EU Azure (EU) → корп Tailscale → us-corp (RU) → us-node (RU)
         50ms             ~30ms              <1ms             <1ms
         Итого RTT: около 120-150ms
```

Пакет **делает крюк через Европу** чтобы достучаться до соседнего контейнера в Москве.

### Почему это работает вообще

Это работает только благодаря **NAT hairpinning** — когда NAT видит что destination IP это его собственный внешний IP, он "заворачивает" пакет обратно.

EU Azure NAT делает это потому что `40.69.0.186:54321` — это существующая запись для исходящих пакетов от us-corp. NAT знает: "этот порт принадлежит us-corp, перешли ответ обратно".

Но это очень хрупко:
- Работает пока us-corp постоянно шлёт keepalive пакеты (иначе NAT-запись истечёт)
- Один пакет задержался → NAT запись уже другая → разрыв
- Не работает если NAT symmetric (а он часто symmetric в корпоративных сетях)

### Проблема 1: двойная инкапсуляция MTU

Когда ноут шлёт пакет к `us-node` через этот путь, пакет оборачивается в WireGuard два раза:

```
Layer 1 (нашей сети): [Ethernet 14][IP 20][UDP 8][WG hdr 60][...payload inside WG #1...]
Layer 2 (корп Tailscale внутри): [внутри WG #1] [IP 20][UDP 8][WG hdr 60][...payload...]

Итого overhead: ~160 байт
Полезный MTU: 1500 - 160 = 1340 байт
```

**Что происходит с большими пакетами:**
- Пакет 1500 байт (обычный HTTP-ответ) не влезает в 1340-байтный туннель
- WireGuard не делает фрагментацию → молча дропает
- Отправитель ждёт ответа, не получает → retry → снова дроп
- **Сайты зависают на загрузке**

**Что происходит с маленькими пакетами:**
- Ping 64 байта — влезает, летит, возвращается
- DNS запрос 100 байт — влезает, резолвится
- Потому симптомы были "ping работает, сайты не открываются"

### Проблема 2: кривая география

Даже если бы MTU не был проблемой — пакеты **физически ходят в Европу и обратно**, только чтобы достичь соседнего контейнера. Это добавляет ~100ms RTT на каждый пакет.

Для TCP с 3-way handshake это означает: установление соединения занимает 300-400ms вместо 10ms.

### Проблема 3: fragile NAT hairpin

EU Azure NAT может:
- Сменить мапинг портов
- Протухнуть запись если us-corp молчал слишком долго
- Переключиться на симметричный режим

Любое из этого ломает путь. Клиент сидит и ждёт ответов которые не приходят.

## Как мы это выяснили

### Симптомы

Что мы наблюдали в разное время:

1. **На телефоне с мобильной сетью:** всё работало нормально. Подключение к `us-node`, интернет через него — норм.

2. **На телефоне на Wi-Fi:** intermittent — иногда работает сразу, иногда 10+ секунд зависает, потом оживает.

3. **На ноутбуке через `us-node`:** интернет вообще не работал. Пинг проходил, но сайты не открывались.

4. **Переключаешь с `yc-node` на `us-node` и обратно:** зависание на 10 секунд каждый раз.

5. **На корпоративном Tailscale всё работало как часы.** Та же VM, тот же клиент, тот же endpoint EU — но через корпоративный координационный сервер — без проблем.

### Первая гипотеза: зависание DERP

Сначала думали что DERP тормозит. Написали `check-relay.sh` который проверяет здоровье DERP, контейнеров, memory/CPU. Всё было зелёным — контейнеры up, DERP отвечает HTTP 426 (правильный ответ для WebSocket upgrade), CPU 0%.

**Вывод:** проблема не в DERP сервере.

### Вторая гипотеза: DNS

После ребута телефон на Wi-Fi — вообще нет интернета даже с выключенным VPN. В браузере "DNS probe started — не удалось определить адрес сервера".

Проверили настройки Tailscale — включён MagicDNS. При активном exit-node все DNS-запросы тоже идут через туннель. Если туннель глючит — DNS не работает.

**Фикс:** `tailscale set --accept-dns=false` (не принимать DNS настройки от Headscale). После этого DNS работает через домашний роутер, независимо от состояния туннеля.

### Третья гипотеза: direct UDP сломан

Посмотрели `tailscale status` на ноуте:

```
100.64.0.1  us-node  sergey  linux  active; exit node; direct 40.69.0.186:54973, tx 400028 rx 465976
```

Заметили: `direct 40.69.0.186:54973`. Это EU Azure IP. Почему клиент коннектится на EU Azure IP если `us-node` в Яндекс Облаке?

Запустили `tailscale netcheck`:

```
Report:
        * UDP: false
```

Ага, у ноутбука UDP **не блокирован** (netcheck показывает false — но тут сложно, иногда netcheck говорит false даже когда UDP работает).

Сделали `tcpdump` на ноуте:

```bash
sudo tcpdump -i any udp port 41641 -c 20
```

Увидели что пакеты реально идут на `40.69.0.186:54973`. То есть **direct UDP работает**, но к неправильному endpoint'у.

### Четвёртая гипотеза: MTU

Проверили ping с разными размерами:

```bash
ping -c 3 -M do -s 1000 8.8.8.8   # работает
ping -c 3 -M do -s 1400 8.8.8.8   # работает
ping -c 3 -M do -s 1472 8.8.8.8   # не работает
```

На определённом размере пакеты перестают проходить. Это **MTU blackhole** — пакеты больше 1340 байт теряются без уведомления.

### Пятая гипотеза (подтвердилась): кривой endpoint

Сопоставили все данные:
- us-node рекламирует `40.69.0.186` (EU Azure)
- Физически us-node в Яндекс Облаке
- Путь клиент→40.69.0.186→us-node hairpin через NAT
- Двойная инкапсуляция → MTU проблемы
- Это и есть причина всех симптомов

**Проверили**: почему для телефона на мобильной сети работает? Потому что мобильный оператор блокирует UDP → Tailscale автоматически использует DERP через `sergey-vpn.crabdance.com` → один слой WireGuard внутри HTTPS/TCP → MTU в порядке.

### Тест исключения

Заблокировали UDP на ноуте:

```bash
sudo iptables -A OUTPUT -d 40.69.0.186 -p udp -j DROP
```

Это форсит fallback на DERP. После этого `tailscale status` показал:

```
100.64.0.1  us-node  ... active; exit node; relay "yc"
```

`relay "yc"` = через наш DERP. Проверили — сайты открываются, интернет через `us-node` работает.

**Диагноз подтверждён:** проблема в кривом direct UDP пути через EU NAT hairpin. DERP-путь работает нормально.

## Как это сделано у Invent

Из `tailscale status` на корпоративном видно:

```
100.64.0.1 headplane-agent            ← управляющий агент (Headplane UI)
100.64.0.2 apptrium-prod-vm-us-1      ← exit node в США
100.64.0.3 apptrium-prod-vm-eu-1      ← exit node в EU
100.64.0.4 apptrium-prod-vm-eu-1-derp ← ВЫДЕЛЕННЫЙ DERP в EU
100.64.0.8 s24ultra                   ← твой телефон
```

**Ключевые наблюдения:**

### Отдельный DERP сервер

У них есть **отдельная нода** `apptrium-prod-vm-eu-1-derp`. Это выделенный DERP сервер, не встроенный в координационный сервер.

**Зачем:** DERP не конкурирует за ресурсы с Headscale/Headplane. Если нагрузка на relay растёт — она не влияет на координацию (регистрация новых нод, изменения ACL и т.д.).

У нас всё в одном процессе Headscale — встроенный DERP. При росте нагрузки может тормозить всё.

### Отдельные exit nodes

`apptrium-prod-vm-us-1` и `apptrium-prod-vm-eu-1` — это **отдельные физические VPS** в США и Европе соответственно.

**Что значит "отдельные":**
- Каждый имеет свой публичный IP
- Каждый запускает свой tailscaled
- У каждого **прямой выход в интернет** (default route → свой eth0)
- STUN для каждого возвращает его реальный публичный IP

Когда клиент хочет подключиться к `apptrium-prod-vm-eu-1`:
1. STUN рекламирует: "я на `13.80.125.42:41641`" (реальный IP машины в Дублине)
2. Клиент делает direct UDP к `13.80.125.42:41641`
3. **Пакет физически прилетает в Дублин**, где и находится сервер
4. Один слой WireGuard, MTU 1420, всё норм

### Headplane

**Headplane** — это **веб-UI для Headscale**. Даёт management через браузер вместо CLI.

У нас нет, мы управляем через `docker compose exec headscale headscale ...`. Можно поставить, если надоест.

### Архитектура в целом

```
              ┌──────────────────┐
              │ Headplane + API  │ ← координация
              │ (свой VPS в EU?)  │
              └──────────────────┘
                       │
      ┌────────────────┼────────────────┐
      │                │                │
      ▼                ▼                ▼
┌──────────┐    ┌──────────┐    ┌──────────┐
│DERP в EU │    │Exit EU    │    │Exit US   │
│(свой VPS)│    │(свой VPS) │    │(свой VPS)│
│прямой IP │    │прямой IP  │    │прямой IP │
└──────────┘    └──────────┘    └──────────┘
```

Каждая функция на отдельной машине со своим публичным IP. Чисто, масштабируемо, без NAT hairpin'ов.

### Почему у них нет зависаний

- Каждая нода рекламирует свой реальный IP
- Клиент коннектится напрямую к нужной ноде (нет hairpin)
- Один слой WireGuard → MTU в порядке
- Отдельный DERP → нет конкуренции за ресурсы с координатором

Короче — у них **правильная distributed архитектура** без компромиссов.

## Можем ли применить их подход?

**Казалось бы — просто!** Купить VPS в Европе (Hetzner, OVH, €3-5/мес), поставить туда Tailscale → подключить к нашему Headscale → получить чистый EU exit node без всех этих костылей.

Но есть **критический блокер: белые списки мобильных операторов РФ.**

### Что такое белые списки

В современной РФ мобильные операторы блокируют/ограничивают доступ ко многим зарубежным IP адресам. Пользователь может достучаться только до **белого списка** разрешённых сервисов (российские соцсети, государственные сайты, некоторые популярные зарубежные).

Наша VM в Яндекс Облаке (`158.160.123.87`) — в белом списке (потому что российское облако, yandex.ru).

Корпоративный Tailscale `vpn.invent.us` — в белом списке (не знаю как они этого добились, возможно через SNI, возможно платное whitelisting).

**Случайный Hetzner VPS в Германии** — **НЕ в белом списке**. С мобильной сети до него не достучаться.

### Что случится если мы поднимем свой EU VPS

```
Телефон на мобильной сети → хочет к eu-node (VPS в Hetzner)
Оператор блокирует: "этого IP нет в белом списке"
Клиент не может подключиться
Всё сломано на мобильной сети
```

Это **неприемлемо** — мобильный интернет через VPN это наш главный use case (например, YouTube из кафе).

### Почему Wi-Fi тоже не вариант

Казалось бы, дома Wi-Fi — нет белых списков, можно подключаться куда угодно. Но:
- Дома работает любой VPN, можно просто использовать корпоративный напрямую
- Проблема именно с мобильной сетью — наш VPN нужен там
- Если фикс работает только дома — он бесполезен

### Поэтому нам нужна VM в Яндекс Облаке

Наша YC VM — это **точка входа в белом списке**. Клиенты коннектятся к ней, дальше уже через наш внутренний туннель можно ходить куда угодно (включая EU через корпоративный Tailscale).

Мы **обязаны** иметь как минимум:
- Одну VM в whitelisted сети (у нас — Яндекс Облако)
- Через неё — proxy в EU/US (у нас — корпоративный Tailscale)

Это **не каприз архитектурный**. Это технологическое ограничение нашего окружения.

### Что из подхода Invent всё же можно применить

1. **Headplane** — можно поставить на ту же VM, получить веб-UI. Не решит нашу проблему, но улучшит удобство.

2. **Разделение DERP и координации** — можно разделить на два контейнера, но поскольку они всё равно в одной VM и делят ресурсы — смысла мало. Разве что для лучшей наблюдаемости.

3. **Идея правильной рекламации endpoint'ов** — вот это можно и **нужно** применить! Не обязательно иметь отдельный VPS, чтобы получить правильный IP — достаточно настроить роутинг внутри контейнера так, чтобы STUN видел правильный IP.

## Правильный фикс — policy-based routing

### Основная идея

В `us-node` контейнере сделать **два разных маршрута** для **двух типов трафика**:

1. **Свой служебный трафик `tailscaled`** (STUN, keepalive, control plane) — через **Docker gateway** → eth0 VM → прямой интернет → STUN видит **IP YC VM** (`158.160.123.87`)

2. **Клиентский трафик для exit-node** (forwarded пакеты клиентов, которые хотят выйти в EU) — через **`us-corp`** → корпоративный Tailscale → EU Azure

Таким образом:
- STUN ответит `us-node`: "твой публичный IP — `158.160.123.87`"
- `us-node` зарекламирует это в Headscale
- Клиенты будут коннектиться **к нашей YC VM** (в белом списке!) напрямую
- Только exit-node трафик (конкретно пакеты YouTube) будут проходить через корпоративный Tailscale в EU

### Как различать эти два трафика на уровне Linux ядра

Трафик `us-node`'а можно разделить по признаку **"откуда пришёл пакет в ядро"**:

- **Служебный трафик `tailscaled`** — создаётся самим процессом в user space → ядро обрабатывает его в цепочке **OUTPUT** (исходящий локальный)
- **Клиентский forward-трафик** — приходит ИЗ сетевого интерфейса `tailscale0` (WireGuard туннель) → ядро обрабатывает в цепочке **PREROUTING** (входящий), потом **FORWARD** (транзит) → **POSTROUTING**

Вот это различие "приходит с локали vs приходит из интерфейса" — можно использовать с помощью iptables.

### План реализации

```
1. Default route → через Docker gateway (172.18.0.1) — прямой интернет
2. Отдельная routing table (номер 200) → default через us-corp (172.18.0.3)
3. iptables: пакет пришёл на tailscale0 (из WG-туннеля от клиентов)
   → метка 1 (fwmark=1)
4. ip rule: если fwmark=1 → использовать таблицу 200 (через us-corp)
```

### Как будет работать после фикса

#### Служебный трафик tailscaled (STUN discovery)

```
tailscaled запускается, хочет сделать STUN запрос:

1. tailscaled создаёт UDP socket, шлёт пакет на stun.l.google.com:19302
2. Ядро обрабатывает пакет (OUTPUT цепочка — локально сгенерирован)
3. iptables mangle: нет правила меток для OUTPUT — пакет без метки
4. ip rule lookup: fwmark=0, используем main table (обычную)
5. Main table default: via 172.18.0.1 (Docker gateway)
6. Пакет идёт через Docker gateway → eth0 VM → в интернет
7. STUN видит source IP нашей YC VM: 158.160.123.87 (после Docker + VM NAT)
8. STUN отвечает: "твой публичный IP — 158.160.123.87"
9. tailscaled запоминает и рекламирует это Headscale
```

✓ `us-node` рекламирует правильный IP нашей YC VM!

#### Клиентский трафик exit-node (forwarded пакеты)

```
Клиент хочет YouTube, шлёт через us-node:

1. Пакет клиента приходит в us-node через tailscale0 (WG-туннель)
2. Ядро обрабатывает пакет (PREROUTING цепочка — входящий из интерфейса)
3. iptables mangle PREROUTING: "пакет с tailscale0 → метка 1"
4. Routing decision: у пакета destination в интернете (не локально)
5. ip rule lookup: fwmark=1 → использовать таблицу 200
6. Таблица 200 default: via 172.18.0.3 (us-corp)
7. Пакет идёт в us-corp
8. us-corp через корпоративный Tailscale → EU Azure → YouTube
9. Ответ приходит тем же путём
```

✓ Клиентский трафик всё так же идёт через EU

#### Клиент подключается к us-node

```
Клиент (ноут/телефон) хочет начать сессию с us-node:

1. Клиент спрашивает Headscale: "где us-node?"
2. Headscale: "на 158.160.123.87:41641 и через DERP"
3. Клиент пробует direct UDP к 158.160.123.87:41641
4. Пакет идёт: клиент → интернет → наша YC VM → Docker NAT → us-node
5. us-node получает пакет, расшифровывает WG, устанавливает сессию
6. Direct UDP работает! Один слой WireGuard, MTU 1420, всё чисто
```

**Нет кривого пути через EU!** Нет NAT hairpin! Нет двойной инкапсуляции!

### Почему это поможет

1. **Клиент коннектится к правильному серверу** — пакет физически летит в нашу YC VM где реально живёт us-node
2. **Один слой WireGuard** — MTU 1420, большие пакеты проходят
3. **Быстрый путь** — RTT ~20ms до us-node (до нашей VM в РФ) вместо ~150ms (через Европу)
4. **Нет зависаний** — Tailscale сразу устанавливает direct UDP, не надо ждать fallback на DERP
5. **Белые списки всё ещё работают** — клиенты идут на `158.160.123.87` (YC IP), который в белом списке
6. **YouTube всё так же через EU** — клиентский exit-node трафик проходит через us-corp

### RTT после фикса

Ноут → us-node → YouTube:
- Ноут → our YC VM: ~20ms (direct UDP)
- us-node → us-corp: <1ms (Docker bridge)
- us-corp → EU → YouTube: ~150ms

**Total RTT: ~170ms** vs текущие 420ms. В 2.5 раза быстрее.

## Реализация фикса

### Обновлённый `us-node/entrypoint.sh`

```sh
#!/bin/sh
set -e

# Ждём us-corp чтобы быть уверенными что он поднят (для DNS resolve)
echo "Waiting for us-corp..."
while ! ping -c1 -W1 us-corp >/dev/null 2>&1; do sleep 1; done

# Узнаём IP us-corp (через Docker DNS резолвим имя сервиса)
CORP_IP=$(getent hosts us-corp | awk '{print $1}')

# Узнаём IP Docker gateway (обычно первый адрес в сети, типа 172.18.0.1)
DOCKER_GW=$(ip route | awk '/default/ {print $3; exit}')

# В старой версии default route уже мог быть через us-corp, убираем
# Делаем default route через Docker gateway (прямой путь в интернет через eth0 VM)
echo "Setting default route via Docker gateway ($DOCKER_GW)"
ip route del default 2>/dev/null || true
ip route add default via "$DOCKER_GW"

# Создаём отдельную routing table для exit-node трафика
# Файл /etc/iproute2/rt_tables содержит имена таблиц (для удобства)
# Добавляем "200 via_us_corp" если ещё не было
if ! grep -q '^200' /etc/iproute2/rt_tables 2>/dev/null; then
  echo "200 via_us_corp" >> /etc/iproute2/rt_tables
fi

# Заполняем таблицу 200: default через us-corp
# Это будет использоваться для пакетов с меткой 1
ip route flush table 200 2>/dev/null || true
ip route add default via "$CORP_IP" table 200

# Настройка iptables mangle для меток
# Очищаем старые правила чтобы скрипт был идемпотентным
iptables -t mangle -F PREROUTING

# Метим пакеты, которые пришли на tailscale0 (из WG-туннеля от клиентов)
# Эти пакеты — forwarded exit-node трафик от клиентов
iptables -t mangle -A PREROUTING -i tailscale0 -j MARK --set-mark 1

# Сохраняем метку в conntrack чтобы ответы тоже шли правильным путём
# CONNMARK сохраняет метку в состоянии соединения
iptables -t mangle -A PREROUTING -i tailscale0 -j CONNMARK --save-mark

# Для возвратного трафика (от us-corp обратно к клиенту) восстанавливаем метку
# чтобы правильно маршрутизировать ответ обратно через tailscale0
iptables -t mangle -A PREROUTING -i eth0 -j CONNMARK --restore-mark

# Правило маршрутизации: если метка пакета = 1 → использовать таблицу 200
# Удаляем старое правило если есть, добавляем новое (идемпотентность)
ip rule del fwmark 1 table 200 2>/dev/null || true
ip rule add fwmark 1 table 200 priority 100

# Запускаем tailscaled в фоне
echo "Starting tailscaled..."
tailscaled --state=/var/lib/tailscale/tailscaled.state &
sleep 3

# Регистрируемся в Headscale через TS_EXTRA_ARGS (authkey, hostname и т.д.)
echo "Connecting to Headscale..."
tailscale up $TS_EXTRA_ARGS

# Держим контейнер живым
wait
```

### Объяснение каждого блока

#### Блок 1: Ожидание us-corp

```sh
while ! ping -c1 -W1 us-corp >/dev/null 2>&1; do sleep 1; done
```

Ждём чтобы `us-corp` был доступен по Docker DNS. Если мы стартанём раньше — getent hosts ничего не найдёт.

#### Блок 2: Default route через Docker gateway

```sh
ip route del default 2>/dev/null || true
ip route add default via "$DOCKER_GW"
```

Убираем старый default route (который был через us-corp в предыдущей версии entrypoint). Устанавливаем default через Docker gateway — это стандартный путь наружу.

**После этого:** любой трафик без явного маршрута идёт через Docker gateway → eth0 VM → интернет.

#### Блок 3: Отдельная routing table

```sh
echo "200 via_us_corp" >> /etc/iproute2/rt_tables
ip route flush table 200
ip route add default via "$CORP_IP" table 200
```

Создаём **вторую routing table** (номер 200, имя `via_us_corp`). В ней — один маршрут: default через `us-corp`.

**Эта таблица пока не используется.** Правило (ip rule) укажет когда её применять.

#### Блок 4: iptables метки

```sh
iptables -t mangle -A PREROUTING -i tailscale0 -j MARK --set-mark 1
```

В цепочке **PREROUTING** таблицы **mangle** — если пакет пришёл с интерфейса `tailscale0` (от клиентов через WG-туннель) — ставим ему метку `1`.

**Почему PREROUTING:** эта цепочка обрабатывает пакеты **до** принятия решения о маршрутизации. Мы ставим метку, а потом ip rule при выборе таблицы увидит эту метку.

#### Блок 5: CONNMARK для ответного трафика

```sh
iptables -t mangle -A PREROUTING -i tailscale0 -j CONNMARK --save-mark
iptables -t mangle -A PREROUTING -i eth0 -j CONNMARK --restore-mark
```

**Зачем:** пакет запроса от клиента промаркирован 1. Он идёт → us-corp → EU → YouTube → ответ от YouTube → EU → us-corp → us-node. Ответный пакет **входит через eth0**, и без специальных усилий у него нет метки 1.

**CONNMARK** сохраняет метку в conntrack-запись (таблица соединений Linux). При ответе мы восстанавливаем метку из conntrack — теперь ответ тоже промаркирован и пойдёт правильным путём.

Без этого: запрос пошёл бы через us-corp, а ответ вернулся бы через Docker gateway, NAT стал бы несогласован, пакеты потерялись бы.

#### Блок 6: правило маршрутизации

```sh
ip rule add fwmark 1 table 200 priority 100
```

"Если у пакета метка = 1 → использовать routing table 200 (через us-corp)".

**Priority 100** — высокий приоритет, это правило проверяется до обычных правил. Если метка есть — используется table 200. Если нет — продолжается обычная обработка (main table → через Docker gateway).

### Как проверить что правила применились

```bash
# Убедиться что default route через Docker gateway
docker exec docker-us-node-1 ip route

# Посмотреть таблицу 200
docker exec docker-us-node-1 ip route show table 200

# Проверить правила
docker exec docker-us-node-1 ip rule

# Проверить iptables правила
docker exec docker-us-node-1 iptables -t mangle -L PREROUTING -v
```

После фикса:
- `ip route` показывает `default via 172.18.0.1` (Docker gateway)
- `ip route show table 200` показывает `default via 172.18.0.3` (us-corp)
- `ip rule` показывает `100: from all fwmark 0x1 lookup 200`
- `iptables -t mangle -L PREROUTING -v` показывает MARK правила

### Что если не заработает

Возможные проблемы при применении:

**Проблема 1: tailscaled использует tailscale0 для исходящих**

Некоторые версии Tailscale могут пытаться делать свой трафик через `tailscale0`. Тогда правила пометки сработают неправильно.

**Решение:** добавить исключение — если source IP пакета совпадает с eth0 IP нашего us-node, не метить.

```sh
# Получаем IP eth0 us-node
US_NODE_IP=$(ip -4 addr show eth0 | awk '/inet / {print $2}' | cut -d/ -f1)

# Не метим пакеты от самого us-node (свои исходящие)
iptables -t mangle -I PREROUTING -s "$US_NODE_IP" -j RETURN
```

**Проблема 2: ts-postrouting цепочка Tailscale мешает**

Tailscale создаёт свою цепочку `ts-postrouting` которая может делать MASQUERADE или другие вещи. Может конфликтовать.

**Решение:** после запуска tailscaled проверить `iptables -L -t nat` и убедиться что нет конфликтов. Возможно понадобится добавить собственный MASQUERADE.

**Проблема 3: ответные пакеты через Docker gateway не возвращаются**

Если CONNMARK не работает — ответы могут теряться.

**Решение:** проверить `conntrack -L` — есть ли записи с меткой, восстанавливается ли она.

*"В мультиконтейнерной VPN-инфраструктуре обнаружил проблему: exit-node контейнер рекламировал неправильный WireGuard endpoint из-за того что все исходящие пакеты (включая STUN для endpoint discovery) шли через соседний контейнер (корпоративный Tailscale proxy) в EU. Это приводило к NAT hairpin через Европу, двойной инкапсуляции WireGuard и MTU-проблемам у клиентов. Диагностика через tcpdump, tailscale netcheck и MTU тесты. Починил через policy-based routing с iptables connection marks — разделил трафик tailscaled (свой трафик идёт напрямую через VM) и forwarded traffic (клиентский трафик идёт через EU proxy). Это показывает:
- Понимание сетей на уровне ядра Linux (iptables mangle, policy routing, conntrack)
- Знание Tailscale/WireGuard внутренностей (STUN, endpoint discovery, DERP fallback)
- Умение диагностировать сложные сетевые проблемы (не только "перезагрузи")
- Архитектурное мышление (увидел корневую причину, не просто костыль наложил)

### Если не реализовывать

**Workaround'ы:**

1. **Подождать 10 секунд** при переключении exit-node — Tailscale сам fallback на DERP
2. **На ноуте использовать block-udp** — форсит DERP сразу
3. **На телефоне** — при зависании toggle VPN off/on

Всё это мы уже используем. Работает, просто неэлегантно.
